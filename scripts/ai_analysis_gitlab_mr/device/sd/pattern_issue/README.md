# `pattern_issue` —— 刻意是一個空的種類目錄

標題寫 `[Pattern Issue]` 的 Merge Request 對應到這裡（映射見 `../mr_type.py`）。

**這個目錄裡沒有任何擴充腳本，而那正是要的結果。** 這個種類的 `summary` 與
`merge_to_md` 就是 sd 的通用版，而擴充腳本的回退是**逐支**的：

```
  sd/pattern_issue/   ->   sd/            ->   default/
       （空的）           ✔ 用這兩支         （輪不到）
```

所以什麼都不放，拿到的就是 `sd/summary.py` 與 `sd/merge_to_md.py` 當下的那兩支。

## 為什麼不在這裡再複製一份

複製一份「與 sd 通用版一模一樣」的檔案，等於宣告「從今天起這個種類與它無關」——
之後 sd 的 prompt 或版面改了，這份複本不會跟著動，而且**不會有任何徵兆**。要的是
「一模一樣」，而回退永遠一模一樣，複本只在複製的那一刻一模一樣。

## 那為什麼還要有這個目錄

**種類是靠掃目錄認得的，沒有註冊表。** 目錄不存在的話，`mr_type.py` 擷取出的
`pattern_issue` 會被入口腳本判定為「認不得」而回退成空字串 —— 產物與報告出處的 `Type`
都會是空的，將來若開了 `STRICT_TYPE = True` 更會讓每一筆這種 MR 在步驟 2 失敗。

目錄一存在，這個種類就被認得。載入器明文支援這種用法：
「一個沒有任何擴充腳本的空目錄仍算一個認得的種類」（`device/__init__.py` 的
`known_types()`）。

這份 README 本身只是為了讓 git 留得住一個空目錄 —— git 不追蹤空目錄。它不會被當成
擴充腳本，載入器只找 `<種類>/<擴充腳本>.py`。

## 要客製的時候

把 `../summary.py` 或 `../merge_to_md.py`（sd 的通用版）複製進這個目錄再改
（**不要**從 `device/_template/` 複製 —— 範本裡那兩支是會回傳假內容的示意實作）。
只放要改的那一支，另一支繼續回退。
