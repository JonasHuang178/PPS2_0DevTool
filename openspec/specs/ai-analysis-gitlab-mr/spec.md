# ai-analysis-gitlab-mr Specification

## Purpose

AI Analysis GitLab MR 讓使用者在工具裡瀏覽某個 GitLab 專案的 Merge Request，挑一筆交給
AI 分析，並把結果連同人工的程式碼審閱總表組成一份可以貼回 MR 討論串的 markdown 報告。

它是本工具第一個需要對外連線的功能，因此這份能力同時定義了三件事：五步流程如何編排而
仍能被持續整合以相同順序直接呼叫、各條產品線如何用 device 機制客製分析邏輯而不必分岔出
第二份腳本，以及失敗如何呈現 —— 一份看起來完整、實際上少了幾段的報告，比一個錯誤訊息
糟得多。
## Requirements
### Requirement: 畫面配置

功能 tab 的標題 SHALL 為 `AI Analysis GitLab MR`，其設定區塊在設定檔 `Function` 底下的鍵名 SHALL 與標題相同。

畫面 SHALL 分為左右兩欄。左欄由上而下為 `AI Mode`、`Analysis Parameter`、`Repository` 三個群組；右欄為 `Merge Requests` 群組。右下角 SHALL 提供 `AI Analysis` 動作按鈕。

`Analysis Parameter` 群組內 SHALL 包含除錯分析檔的勾選方塊、分析檔存放目錄的輸入框與瀏覽鈕，以及巢狀的 `JIRA Key` 群組。

`Merge Requests` 群組內 SHALL 包含兩個互斥的取得方式、巢狀的 `Merge Request Parameter` 查詢條件群組，以及 Merge Request 表格。

#### Scenario: 顯示功能畫面

- **WHEN** 使用者切換到 AI Analysis GitLab MR
- **THEN** 左欄顯示 AI Mode、Analysis Parameter、Repository 三個群組
- **AND** 右欄顯示 Merge Requests 群組
- **AND** 右下角顯示 AI Analysis 按鈕

### Requirement: 進入功能不執行任何腳本

進入本功能（切換到本分頁，或啟動時本分頁即為當前分頁）SHALL NOT 啟動任何腳本。

Repository 清單 SHALL 於功能建立時自設定檔填入。Merge Request 表格 SHALL 保持在「尚未取得」的狀態，直到使用者按下重新整理。

理由：本功能的每一次載入都是一次對外部服務的請求。若比照「進入即載入」，使用者每次切換到這個分頁都會被一個應用程式互斥的處理中對話框擋住並等待網路回應。

#### Scenario: 切換到本功能

- **WHEN** 使用者從其他功能切換到本功能
- **THEN** 沒有任何腳本被啟動，也沒有處理中對話框出現
- **AND** Repository 清單已填入設定檔中的項目

#### Scenario: 啟動時本功能即為當前分頁

- **WHEN** 應用程式啟動且本功能是當前分頁
- **THEN** Repository 清單已填入，Merge Request 表格顯示尚未取得的提示
- **AND** 沒有任何腳本被啟動

### Requirement: Repository 清單

Repository 清單 SHALL 列出功能設定中 `Repo_List` 的所有項目，每項為 `namespace/project` 形式的字串，並以該字串原樣顯示。

清單 SHALL 為單選。

`Repo_List` 不存在或為空時，清單 SHALL 為空，MUST NOT 視為錯誤，也 MUST NOT 顯示訊息框。

#### Scenario: 顯示設定中的 repository

- **WHEN** 設定的 `Repo_List` 含兩個項目
- **THEN** 清單顯示這兩個項目，內容與設定完全相同

#### Scenario: 單選

- **WHEN** 使用者已選取一個 repository，接著點選另一個
- **THEN** 只有後者處於選取狀態

#### Scenario: 設定中沒有 repository

- **WHEN** 設定中沒有 `Repo_List` 或其為空陣列
- **THEN** 清單為空
- **AND** 不顯示任何訊息框

### Requirement: Merge Request 的兩種取得方式互斥

`Merge Requests` 群組 SHALL 提供兩個互斥的取得方式：手動輸入 Merge Request 編號，或依查詢條件取得清單。

選定其中一種時，另一種所屬的所有控件 SHALL 為停用狀態。

#### Scenario: 選擇取得清單

- **WHEN** 使用者選擇依查詢條件取得清單
- **THEN** 手動輸入編號的輸入框為停用狀態
- **AND** 查詢條件群組、重新整理鈕與表格皆可操作

#### Scenario: 選擇手動輸入

- **WHEN** 使用者選擇手動輸入 Merge Request 編號
- **THEN** 輸入框可編輯
- **AND** 查詢條件群組、重新整理鈕與表格皆為停用狀態

### Requirement: 手動輸入的 Merge Request 編號

手動輸入的編號 SHALL 只接受數字。

貼上以 `!` 開頭的字串或一整條 Merge Request 網址時，SHALL 自其中取出編號，MUST NOT 直接拒絕。

理由：使用者最自然的動作是從瀏覽器複製，完全擋死只會逼他們手動刪字。

#### Scenario: 輸入數字

- **WHEN** 使用者輸入 `123`
- **THEN** 輸入框接受該值

#### Scenario: 貼上含驚嘆號的編號

- **WHEN** 使用者貼上 `!123`
- **THEN** 輸入框的內容成為 `123`

#### Scenario: 貼上完整網址

- **WHEN** 使用者貼上一條指向某個 Merge Request 的網址
- **THEN** 輸入框的內容成為該 Merge Request 的編號

#### Scenario: 輸入非數字

- **WHEN** 使用者鍵入字母
- **THEN** 輸入框不接受該字元

### Requirement: Merge Request 的查詢條件

查詢條件 SHALL 包含「只取尚未關閉的」與「只取指定天數內建立的」兩個可各自開關的條件，天數 SHALL 以數值輸入控件呈現，範圍 1 至 365，預設 7。

理由：以純文字輸入框承載天數會讓負數、零、空字串與超大值各自需要一段檢查；數值輸入控件免費處理掉全部。

#### Scenario: 天數的範圍

- **WHEN** 使用者嘗試把天數設為 0 或大於 365 的值
- **THEN** 控件不接受該值

#### Scenario: 預設值

- **WHEN** 使用者第一次進入本功能
- **THEN** 兩個條件皆為開啟，天數為 7

### Requirement: 取得 Merge Request 清單

按下重新整理 SHALL 以目前選取的 repository 與查詢條件執行取得清單的腳本。

未選取 repository 時，重新整理 SHALL 為停用狀態。

腳本成功時 SHALL 以回傳的資料一次填入表格；失敗時表格 SHALL 被清空並顯示錯誤訊息說明原因。

取得到零筆 SHALL 視為成功而非失敗：表格為空，MUST NOT 顯示錯誤訊息框。

#### Scenario: 成功取得

- **WHEN** 使用者選取 repository 後按下重新整理，腳本成功回傳三筆
- **THEN** 表格顯示這三筆
- **AND** 不顯示任何訊息框

#### Scenario: 沒有符合條件的結果

- **WHEN** 腳本成功回傳零筆
- **THEN** 表格為空並顯示「沒有符合條件」的提示
- **AND** 不顯示錯誤訊息框

#### Scenario: 取得失敗

- **WHEN** 腳本回報失敗
- **THEN** 表格被清空
- **AND** 顯示錯誤訊息說明腳本回報的原因

#### Scenario: 未選取 repository

- **WHEN** Repository 清單沒有任何項目處於選取狀態
- **THEN** 重新整理鈕為停用狀態

### Requirement: Merge Request 表格

表格 SHALL 有五個欄位，依序為：編號、狀態、標題、作者、建立日期。MUST NOT 有 repository 欄 —— 表格的內容一律屬於當前選取的那一個 repository。

標題欄 SHALL 為唯一會隨視窗寬度伸縮的欄位，其餘四欄寬度固定。標題過長時 SHALL 截斷顯示，並以整列的提示文字提供完整標題。

建立日期 SHALL 以絕對日期顯示，排序 SHALL 依該日期的實際先後。

表格 SHALL 為單選。

表格 SHALL 區分兩種空白狀態：尚未取得，以及已取得但沒有符合條件的結果。

理由：兩種空白在畫面上完全相同，但使用者該採取的下一步不同 —— 前者要按重新整理，後者要放寬條件。

#### Scenario: 標題欄取得剩餘寬度

- **WHEN** 表格顯示資料
- **THEN** 編號、作者、建立日期、狀態四欄為固定寬度
- **AND** 標題欄佔用其餘的全部寬度

#### Scenario: 標題過長

- **WHEN** 某筆的標題長度超過標題欄的寬度
- **THEN** 顯示的標題被截斷
- **AND** 該列提供完整標題的提示文字

#### Scenario: 兩種空白狀態可區分

- **WHEN** 使用者尚未按下重新整理
- **THEN** 表格顯示「尚未取得」的提示
- **AND** 該提示與「沒有符合條件」的提示不同

#### Scenario: 單選

- **WHEN** 使用者已選取一筆，接著點選另一筆
- **THEN** 只有後者處於選取狀態

### Requirement: 清單於條件改變後失效

切換 repository，或改動任何一項查詢條件，SHALL 清空 Merge Request 表格並使其回到「尚未取得」的狀態。

理由：清單的內容屬於取得它時的那一組條件。若保留，畫面上顯示的會是前一個 repository 的 Merge Request，而按下 AI Analysis 時採用的卻是當前選取的 repository。

#### Scenario: 切換 repository

- **WHEN** 使用者已取得 repository A 的清單並選取其中一筆，接著改選 repository B
- **THEN** 表格被清空並顯示「尚未取得」的提示
- **AND** `AI Analysis` 變為停用

#### Scenario: 改動查詢條件

- **WHEN** 使用者已取得清單，接著改動天數
- **THEN** 表格被清空並顯示「尚未取得」的提示

### Requirement: AI Mode 選單

`AI Mode` 下拉選單 SHALL 列出設定中 `AI_Mode_List` 每一項的 `Name`，順序與設定相同，預設選取第一項。

外殼與功能 MUST NOT 在畫面上呈現該項目的其他欄位（端點、金鑰、模型名）。

`AI_Mode_List` 不存在或為空時，選單 SHALL 為空。

#### Scenario: 列出設定中的模式

- **WHEN** 設定的 `AI_Mode_List` 含一項且其 `Name` 為 `Open AI`
- **THEN** 選單顯示 `Open AI` 且為選取狀態

#### Scenario: 順序即預設

- **WHEN** 設定的 `AI_Mode_List` 含多項
- **THEN** 選單的順序與設定相同
- **AND** 預設選取第一項

### Requirement: 除錯分析檔的開關與存放目錄

`Analysis Parameter` 群組的除錯分析檔勾選方塊 SHALL 決定本次分析的中間產物是否保留在使用者指定的目錄中。未勾選時中間產物仍會產生，但寫在暫存目錄裡，流程結束即移除。

未勾選時，存放目錄的標籤、輸入框與瀏覽鈕 SHALL 一併為停用狀態。

存放目錄的初始值 SHALL 取自功能設定，瀏覽鈕 SHALL 開啟目錄選擇對話框。

#### Scenario: 未勾選時停用整列

- **WHEN** 使用者取消勾選除錯分析檔
- **THEN** 存放目錄的輸入框與瀏覽鈕皆為停用狀態

#### Scenario: 初始值來自設定

- **WHEN** 使用者第一次進入本功能，而設定中的存放目錄有值
- **THEN** 輸入框顯示該值

### Requirement: JIRA Key 的三種模式

`JIRA Key` 群組 SHALL 提供三個互斥的模式：不使用、手動指定、自動取得。預設 SHALL 為自動取得。

只有選擇手動指定時，其輸入框 SHALL 可編輯；其餘模式下 SHALL 為停用狀態。

模式與手動輸入的值 SHALL 傳給流程，由腳本決定最終採用哪一個。功能 MUST NOT 在 Qt 端
先行決定。

三種模式的分派 SHALL 由入口腳本執行：不使用時不呼叫抽取的鉤子並記為「沒有」；手動指定
時採用使用者輸入的值；自動取得時呼叫該 device 的抽取鉤子。

理由：三選一是政策而非演算法。若交給每個 device 各自實作，同一段判斷會出現多次並可能
寫歪 —— 例如某個 device 在自動模式下卻採用了手動輸入的值。device 只負責「怎麼從 Merge
Request 抽出來」。

模式 SHALL 一併傳給 AI 分析那一步，使該步能分辨 key 是抽取而來或由使用者輸入。

理由：若在 Qt 端解析這三種模式，以命令列或持續整合呼叫同一批腳本時就必須重寫一次相同的判斷，兩份實作必然漂移。

#### Scenario: 預設為自動

- **WHEN** 使用者第一次進入本功能
- **THEN** JIRA Key 的模式為自動取得
- **AND** 手動輸入框為停用狀態

#### Scenario: 手動模式才可編輯

- **WHEN** 使用者選擇手動指定
- **THEN** 輸入框可編輯

#### Scenario: 三個值一併傳入

- **WHEN** 使用者以自動模式執行分析
- **THEN** 抽取的鉤子被呼叫，其結果成為該次採用的值
- **AND** Qt 端沒有依模式挑選其中之一

#### Scenario: 不使用模式不呼叫抽取

- **WHEN** 使用者選擇不使用 JIRA Key
- **THEN** 抽取的鉤子不被呼叫
- **AND** 後續步驟收到的狀態為「沒有」

### Requirement: AI Analysis 的啟用條件

`AI Analysis` SHALL 只在下列條件全部成立時為啟用狀態：已選取一個 repository；已指定一個 Merge Request（手動輸入的編號非空，或表格中已選取一筆）；勾選除錯分析檔時存放目錄非空；選擇手動指定 JIRA Key 時其輸入框非空。

停用時 MUST NOT 顯示任何說明原因的提示文字或提示框。

理由：與既有功能的作法一致。已知代價是使用者無從得知缺少什麼，緩解方式是讓範本設定檔提供可用的預設值。

#### Scenario: 條件齊備

- **WHEN** 使用者選取了 repository 與一筆 Merge Request，且其餘條件皆滿足
- **THEN** `AI Analysis` 為啟用狀態

#### Scenario: 未選取 Merge Request

- **WHEN** 使用者選取了 repository 但表格中沒有任何一筆處於選取狀態
- **THEN** `AI Analysis` 為停用狀態

#### Scenario: 勾選除錯但存放目錄為空

- **WHEN** 除錯分析檔為勾選狀態而存放目錄為空
- **THEN** `AI Analysis` 為停用狀態
- **AND** 畫面上沒有任何說明原因的文字

### Requirement: 工作目錄於流程啟動前建立

功能 SHALL 在流程啟動之前備妥一個工作目錄，並把流程每一個步驟的產物寫進去。該目錄的絕對路徑 SHALL 併入每一步的輸出路徑參數。

勾選除錯分析檔時，工作目錄 SHALL 位於存放目錄之下，名稱含 repository、Merge Request 編號與時間戳記，並在流程結束後保留。

未勾選時，工作目錄 SHALL 為一個暫存目錄，並在流程結束後連同其中的檔案一併移除。

除錯輸出目錄的參數（即腳本寫出除錯日誌的位置）SHALL 只在勾選時傳入該目錄的絕對路徑，未勾選時 SHALL 傳入空字串。

工作目錄建立失敗時 SHALL 顯示錯誤訊息框，且流程 MUST NOT 啟動。

時間戳記 SHALL 只產生一次，使所有步驟寫入同一個目錄。

理由：合併為 markdown 的那一步以**檔案路徑**為輸入，因此中間產物落檔不能是「除錯才開啟」的選項 —— 否則未勾選除錯時最後一步沒有東西可以合併。以暫存目錄承接未勾選的情況，使兩種情況下腳本的契約完全一致，而使用者的磁碟上仍然不留任何東西。在流程啟動前建立，則使路徑錯誤或權限不足在任何工作開始之前就被發現，而不是在耗費了時間與外部服務的費用之後才失敗。

#### Scenario: 勾選時建立目錄並保留

- **WHEN** 使用者勾選除錯分析檔並按下 `AI Analysis`
- **THEN** 在存放目錄之下建立一個含 repository、Merge Request 編號與時間戳記的目錄
- **AND** 每一個步驟收到的輸出路徑都位於該目錄之下
- **AND** 流程結束後該目錄與其中的檔案仍然存在

#### Scenario: 未勾選時走暫存目錄

- **WHEN** 使用者未勾選除錯分析檔並按下 `AI Analysis`
- **THEN** 存放目錄之下沒有任何目錄被建立
- **AND** 每一個步驟收到的除錯輸出目錄參數為空字串
- **AND** 流程結束後暫存目錄與其中的檔案一併被移除

#### Scenario: 目錄建立失敗

- **WHEN** 存放目錄指向一個無法寫入的位置
- **THEN** 顯示錯誤訊息框
- **AND** 沒有任何腳本被啟動

#### Scenario: 所有步驟寫入同一個目錄

- **WHEN** 一次分析的五個步驟都產生檔案
- **THEN** 五個步驟的檔案位於同一個目錄中

### Requirement: 分析流程的組成

按下 `AI Analysis` SHALL 啟動一條固定五步的流程，依序為：取得 Merge Request 描述、取得相關資訊、AI 分析、取得程式碼審閱報告、合併為 markdown。

五個步驟 SHALL 全部執行，MUST NOT 由 Qt 端依條件跳過任何一步。「是否真的執行工作」SHALL 由該步的腳本依收到的參數自行決定，不執行工作時 SHALL 回傳空結果並回報成功。

各步驟的腳本路徑 SHALL 固定，MUST NOT 取自任何步驟的回傳資料。

理由：同一批腳本必須能被持續整合以相同順序直接呼叫。若分支判斷寫在 Qt 端，持續整合那一側就成為第二份編排實作，兩份必然漂移；把判斷壓進腳本後，兩邊都只是固定順序的線性呼叫，判斷邏輯只有一份。

哪一段運算因 device 而異 SHALL 由環境變數決定（見 device 的來源與解析），MUST NOT 取自任何步驟的回傳資料。

「不執行工作」的判定依據 MUST NOT 為一個獨立的布林開關。取得程式碼審閱報告那一步 SHALL
依收到的 JIRA key 與其狀態自行決定是否向外取得，使「要不要做」與「對誰做」由同一個值
承載。

#### Scenario: 五步依序執行

- **WHEN** 使用者按下 `AI Analysis` 且每一步皆成功
- **THEN** 五個步驟依序各執行一次
- **AND** 同一時刻沒有一支以上的腳本在執行

#### Scenario: 不需要工作的步驟仍被執行

- **WHEN** 取得程式碼審閱報告那一步收到的 JIRA key 為空，或其狀態不是有效
- **THEN** 該步驟仍被啟動
- **AND** 它不向外發出任何請求，回報成功且不產生任何產物

#### Scenario: 腳本路徑不受回傳資料影響

- **WHEN** 任何步驟的回傳資料中含有名稱或路徑形式的字串
- **THEN** 後續步驟執行的仍是固定的腳本
- **AND** 該資料 MUST NOT 被用來決定要執行哪一支腳本或載入哪一個模組

### Requirement: 流程步驟的參數組裝

功能 SHALL 依已完成步驟的結果組裝下一步的參數，且該組裝 MUST NOT 包含任何業務判斷 —— 只做挑選欄位、更名與轉送。

AI 模式的端點、金鑰與模型名 SHALL 經由參數傳入，MUST NOT 出現在命令列。

#### Scenario: 前一步的結果轉送至下一步

- **WHEN** 取得相關資訊的步驟成功結束
- **THEN** 其回傳的資料被原樣放入需要它的後續步驟的參數
- **AND** 功能沒有對該資料做任何解讀或分支

#### Scenario: AI 設定經由參數傳入

- **WHEN** AI 分析步驟被啟動
- **THEN** 選定模式的端點、金鑰與模型名出現在該步的參數中
- **AND** 不出現在行程的命令列上

### Requirement: 服務憑證經由環境變數傳遞

功能 SHALL 把設定中的 GitLab 與 JIRA 服務端點與存取權杖，注入為每一個步驟的環境變數，變數名為設定鍵名的全大寫形式。

腳本 SHALL 只從環境變數取用這些值，MUST NOT 自 `config` 取用。

AI 服務的端點、金鑰與模型名稱為例外：它們 SHALL 經由步驟參數傳遞（見「AI 服務的憑證與
傳輸」）。理由是這三項隨使用者在畫面上選的 AI 模式而變，屬於該次執行的參數，而非跨執行
不變的服務設定。兩種方式都不上命令列。

理由：持續整合以相同名稱設定環境變數即可執行同一批腳本，腳本端因此只有一條取值路徑，兩個呼叫端對它而言完全相同。

腳本 MUST NOT 將整包 `config` 輸出至診斷訊息 —— 合併後的 `config` 仍含有這些權杖。

#### Scenario: 環境變數被注入

- **WHEN** 流程的任一步被啟動
- **THEN** 該行程的環境中含有 GitLab 與 JIRA 的服務端點與存取權杖

#### Scenario: 命令列不含憑證

- **WHEN** 流程的任一步被啟動
- **THEN** 該行程的命令列參數中不含任何權杖

#### Scenario: 以命令列直接執行

- **WHEN** 開發者在已設定相同環境變數的環境中直接執行其中一支腳本
- **THEN** 該腳本取得相同的服務端點與權杖
- **AND** 不需要在請求檔案中填入任何憑證

### Requirement: 腳本的輸出入雙軌

流程中每一支腳本的完整結果 SHALL 放在回應的 `data` 中。當參數指定了輸出路徑時，SHALL 額外寫出對應的檔案；未指定時 MUST NOT 寫出任何檔案。

每一支腳本 SHALL 同時接受兩種輸入形式：參數中直接帶入的內容，以及指向前一步產物的路徑。兩者皆提供時 SHALL 以內容為準。

寫出的中間產物 SHALL 以兩位數序號前綴命名，使目錄的列出順序即為流程的執行順序。

理由：圖形介面呼叫端不觸碰檔案系統，因此需要 `data`；持續整合以 shell 串接，檔案是它的原生形式。兩者皆支援使得同一批腳本服務兩個呼叫端，而協定本身是加法式的。

#### Scenario: 圖形介面呼叫時取得結果

- **WHEN** 流程的某一步成功結束
- **THEN** 其結果完整地存在於回應的 `data` 中
- **AND** 功能不需要開啟任何檔案即可取得該結果

#### Scenario: 未指定輸出路徑時不寫檔

- **WHEN** 開發者以命令列執行某一步而未給輸出路徑
- **THEN** 該步成功結束且檔案系統中沒有任何檔案被建立或修改

#### Scenario: 以路徑作為輸入

- **WHEN** 開發者以命令列執行某一步，參數中只提供指向前一步產物的路徑
- **THEN** 該步讀取該檔案作為輸入並正常執行

#### Scenario: 中間產物的命名

- **WHEN** 執行整條流程
- **THEN** 目錄中的檔案帶有兩位數序號前綴
- **AND** 依檔名排序的順序即為五個步驟的執行順序

### Requirement: 失敗即結束流程

流程中任一步回報失敗時，功能 SHALL 結束整條流程，MUST NOT 執行後續步驟，也 MUST NOT 執行補救步驟。

流程結束後 SHALL 顯示一個錯誤訊息框，內容 SHALL 指出失敗發生在第幾步，並包含該步腳本回報的原因。

畫面上的任何元素 MUST NOT 因此改變。

#### Scenario: 第三步失敗

- **WHEN** 流程的第三步回報失敗
- **THEN** 第四、第五步不被啟動
- **AND** 顯示一個錯誤訊息框，指出第三步失敗與該步回報的原因
- **AND** Repository 清單與 Merge Request 表格的內容不變

#### Scenario: 啟動前失敗

- **WHEN** 某一步的腳本檔案不存在
- **THEN** 顯示錯誤訊息框指出該腳本路徑
- **AND** 流程結束，畫面不變

### Requirement: 結果呈現

流程的所有步驟皆成功時，功能 SHALL 以結果視窗顯示最後一步回傳的 markdown 內容，並附上整條流程的耗時。

顯示的內容 SHALL 取自回應的 `data`，功能 MUST NOT 為此開啟任何檔案。

#### Scenario: 成功後顯示結果

- **WHEN** 流程的五個步驟皆成功
- **THEN** 結果視窗顯示最後一步回傳的 markdown 內容與整條流程的耗時

#### Scenario: 未勾選除錯時仍能看到結果

- **WHEN** 使用者未勾選除錯分析檔而執行整條流程且全部成功
- **THEN** 結果視窗仍顯示完整的 markdown 內容
- **AND** 流程結束後使用者指定的存放目錄之下沒有任何檔案

#### Scenario: 取消後畫面不變

- **WHEN** 使用者在流程執行中按下取消
- **THEN** 不顯示結果視窗，也不顯示錯誤訊息框
- **AND** 畫面上沒有任何元素改變

### Requirement: 最終報告的組成

合併為 markdown 的那一步產出的報告 SHALL 由原始描述、本次的 AI 分析、（取得了的話）
程式碼審閱報告，以及末尾的出處資訊依序組成。**每一段的標題都 SHALL 由這一步寫出**，
包含程式碼審閱那一段 —— 產生該段內容的步驟 MUST NOT 自行寫出它的標題。

理由：報告有哪幾節、各在第幾層，只應該有一個地方決定。由產生內容的步驟自帶標題時，
它無從知道自己會被放在哪一層，結果是程式碼審閱那一段縮在 AI 分析之下，讀起來像是
分析的子節，而它在語意上與分析並列。

報告 MUST NOT 包含報告標題與產生時間，段落之間 MUST NOT 加入分隔線。

理由：使用者要看的就是這幾段內容本身，多一層框架只是噪音。需要知道報告何時產生時，
勾選除錯分析檔的情況下可由工作目錄名稱的時間戳得知。

原始描述為空時，該段 SHALL 不出現在報告中。

理由：一段空白會讓人以為內容漏掉了，而實際上是那筆 Merge Request 沒有填寫描述。

報告中的原始描述那一段 SHALL 冠上一個標題，該標題由合併那一步寫出。

理由：報告裡有兩段以上的內容，沒有標題就看不出哪裡是人寫的、哪裡是 AI 產生的。
這個標題屬於**報告**而不屬於描述 —— 取得描述那一步的產物仍然不冠標題（見該需求），
否則那一行會跟著報告被貼回描述，變成工具自己製造出來、之後要再清理的東西。

該標題 SHALL 與取得描述那一步用來去除它的字串為同一個，且 SHALL 只有一份來源。

AI 分析那一段的標題 SHALL 與取得描述那一步用來切出原始描述的標題為同一個字串，且
該字串在實作中 SHALL 只有一份來源，比對規則 SHALL 由它導出而非另外手寫。

理由：兩者是同一個邊界的兩側 —— 一邊寫出那一段，另一邊靠同一個字串把它切掉。各自
維護一份而漂移時，下一輪切不到邊界，先前的分析會被當成原始描述留下來，報告於是疊出
兩段 AI 分析，而每一個步驟都回報成功。

報告 SHALL 只用於呈現給使用者，功能 MUST NOT 將其寫回 GitLab 的 Merge Request 描述。

報告末尾 SHALL 附上出處資訊，內容至少包含產生它的腳本名稱與版本、所使用的 device 及其
版本、使用者選定的 AI 模式，以及該次採用的 JIRA key 與其狀態。在持續整合環境中 SHALL
另外附上該次的 pipeline 與 commit，並在可組出網址時連回對應的頁面；由工具執行時 SHALL
改為附上工具名稱與版本。

出處中的每一個值 SHALL 帶有說明它是什麼的標示 —— 兩個版本號並列時，沒有標示就分不出
哪一個是腳本的、哪一個是 device 的。

JIRA 的呈現 SHALL 依其狀態而異：有效時顯示該 key（可組出網址時連回該頁面）；沒有時
顯示「沒有」；無效時顯示**被拒絕的原值**並標示為無效。

理由（顯示原值）：顯示原值直接指出問題所在 —— 例如看到被拒絕的值是 `WIP`，就知道標題
的第一個方括號放的不是 JIRA key。只顯示「沒有」則只說明失敗了。

理由（狀態要能區分）：持續整合環境只有自動取得一種模式，而自動取得正是唯一會抽錯的
模式。在該環境中診斷訊息與中間步驟的訊息都不會被人看到，出處是唯一會被看到的訊號。

該狀態 SHALL 隨分析結構傳遞至合併那一步，MUST NOT 由該步重新判定。

理由：判定規則屬於 AI 分析那一步的 device 鉤子。由合併那一步重新判定就會有第二份規則，
兩份必然漂移。

理由：報告被貼到 Merge Request 的討論串之後就脫離了產生它的環境。日後要回答「這段
分析是哪一版產生的、為什麼與現在跑出來的不同」，這段資訊是唯一的依據。

出處資訊 MUST NOT 被計入「是否有可合併的內容」的判斷。

AI 分析的結果 SHALL 以一份帶版本的結構交給合併那一步，由**該步**渲染成 markdown。
渲染端 SHALL 依版本決定如何讀取；認不得的版本 SHALL 明確失敗，MUST NOT 自行猜測。

版本的比對 SHALL 容許數值與純數字字串的差異（同一個版本寫成數字或字串皆可），但
MUST NOT 接受非整數的值。

理由：報告長什麼樣是報告那一步的決定，而產生分析的那一步之後還會長出與 AI 供應商
往來的邏輯。結構是唯一的真相，markdown 是它的呈現 —— 只留一份真相，就不會出現
結構與文字互相矛盾的產物。猜測版本的結果則是一份看起來正常、實際上少了幾段的報告，
而它會回報成功。

渲染 diff 時所用的程式碼區塊界線 SHALL 依內容決定長度，使內容本身含有界線字元時
區塊不會提前結束。

AI 分析那一段標題底下的內容 SHALL 由該 device 的鉤子產生。以下版面為預設 device 的
行為，其他 device MAY 自行決定；標題本身、其餘各段與出處則不因 device 而異。

AI 分析那一段的版面 SHALL 為：總覽自成一節，各檔案的發現在另一節之下，每個檔案
依序編號並以路徑為標題，其下每一筆發現為一個條目（標題、理由，以及該筆自己的
diff）。某個檔案沒有任何可呈現的發現時，該檔案 SHALL 整個不出現，且編號 SHALL 只
計入實際出現的檔案。

檔案路徑 SHALL 以等寬樣式呈現。每一筆發現的理由 SHALL 縮排於該筆之下，其 diff SHALL 以可收合的區塊呈現。

理由：一筆發現的 diff 可能有數十行，全部攤開會讓報告難以掃讀，而閱讀者多半先看標題
與理由、需要時才展開。

結構中的模式名稱與 JIRA 連結 SHALL NOT 出現在報告中 —— 它們留在資料裡供其他消費者
使用。

#### Scenario: 報告的組成與順序

- **WHEN** 原始描述與 AI 分析都有內容，且未取得程式碼審閱報告
- **THEN** 報告依序包含原始描述那一段與 AI 分析那一段
- **AND** 兩段之間沒有分隔線

#### Scenario: 不含報告標題與產生時間

- **WHEN** 流程成功結束並顯示報告
- **THEN** 報告的開頭是原始描述那一段的標題，而非另一個涵蓋全篇的報告標題
- **AND** 報告中沒有產生時間

#### Scenario: 原始描述為空時整段不出現

- **WHEN** 該 Merge Request 沒有填寫描述，而 AI 分析有內容
- **THEN** 報告不含該段的任何佔位文字
- **AND** 報告以 AI 分析那一段的標題開頭

#### Scenario: 報告可被再次切段

- **WHEN** 使用者把一份產出的報告貼回 Merge Request 的描述，之後再執行一次分析
- **THEN** 取得描述那一步認得報告中 AI 分析那一段的標題並將其切掉
- **AND** 新的報告中 AI 分析只有一段，先前那一段不再出現

#### Scenario: 結構化的分析被渲染成報告

- **WHEN** AI 分析結果是一份認得的結構，內含總覽與數個檔案的發現
- **THEN** 報告依序呈現總覽那一節、檔案那一節，以及每個檔案底下的每一筆發現
- **AND** 每個檔案有序號與路徑，每一筆發現的 diff 緊接在該筆之下

#### Scenario: diff 以可收合的區塊呈現

- **WHEN** 某一筆發現帶有 diff
- **THEN** 該 diff 位於一個可收合的區塊之內
- **AND** 該區塊縮排於該筆發現之下，而非與檔案標題同層

#### Scenario: 沒有 diff 的發現

- **WHEN** 某一筆發現沒有 diff
- **THEN** 該筆不產生任何可收合的區塊

#### Scenario: 某個檔案沒有任何發現

- **WHEN** 結構中某個檔案的發現清單為空
- **THEN** 該檔案不出現在報告中
- **AND** 其餘檔案的序號連續，不因此跳號

#### Scenario: diff 內含程式碼區塊的界線字元

- **WHEN** 某一筆發現的 diff 內容本身含有程式碼區塊的界線字元
- **THEN** 該區塊不會提前結束，diff 完整呈現

#### Scenario: 認不得的結構版本

- **WHEN** AI 分析結果的版本不是渲染端認得的
- **THEN** 這一步回報失敗，MUST NOT 產出一份省略了該段的報告
- **AND** 訊息指出讀到的版本與實作認得的版本

#### Scenario: 版本寫成字串

- **WHEN** 結構的版本欄位是與目前版本相同的純數字字串
- **THEN** 該結構被正常渲染，MUST NOT 因為型別不同而失敗

#### Scenario: AI 分析結果不是一段文字

- **WHEN** AI 分析結果檔中放 markdown 的那個欄位不是字串（例如是一個巢狀物件）
- **THEN** 這一步回報失敗，MUST NOT 把該值硬轉成文字放進報告
- **AND** 訊息指出檔案位置、欄位名稱、實際的型別，以及該檔案現有的欄位

#### Scenario: 出處載明 device

- **WHEN** 以某個 device 產出報告
- **THEN** 出處中載明該 device 的名稱與版本
- **AND** 每一個版本號都有說明它屬於什麼的標示

#### Scenario: JIRA key 無效

- **WHEN** 該次採用的 JIRA key 被判定為無效
- **THEN** 出處顯示被拒絕的原值並標示為無效

#### Scenario: 程式碼審閱那一段的標題

- **WHEN** 報告含有程式碼審閱那一段
- **THEN** 該段的標題與 AI 分析那一段同層，而非其下一層

#### Scenario: 報告附上出處

- **WHEN** 流程成功結束並產出報告
- **THEN** 報告末尾有一段出處資訊，載明腳本名稱、版本與使用者選定的 AI 模式

#### Scenario: 在持續整合環境中產生

- **WHEN** 報告產生於持續整合環境，該環境提供了 pipeline 與 commit 的資訊
- **THEN** 出處資訊另外載明該次的 pipeline 與 commit
- **AND** 兩者可連回對應的頁面

#### Scenario: 由工具產生

- **WHEN** 報告產生於圖形介面工具，而非持續整合環境
- **THEN** 出處資訊改為載明工具名稱與版本
- **AND** 腳本名稱與版本那一行與持續整合環境中相同

#### Scenario: 只有出處資訊不算有內容

- **WHEN** 三段輸入都沒有給，或內容都是空的
- **THEN** 這一步回報失敗，MUST NOT 只產出一段出處資訊

#### Scenario: 不寫回 GitLab

- **WHEN** 流程的五個步驟皆成功
- **THEN** 報告顯示在結果視窗中
- **AND** 該 Merge Request 在 GitLab 上的描述沒有被修改

### Requirement: 取得 Merge Request 清單的 GitLab 連線

取得 Merge Request 清單的腳本 SHALL 連線至設定的 GitLab 伺服器並取回實際的 Merge Request。

專案 SHALL 以 `namespace/project` 字串識別，腳本 SHALL 對其做 URL 編碼後再組成請求。

畫面上的查詢條件 SHALL 對應到實際的查詢參數：只取尚未關閉的、以及只取指定天數內建立的。

憑證無效與專案不存在 SHALL 給出彼此不同且可行動的失敗訊息：前者 SHALL 指向存取權杖所在的環境變數，後者 SHALL 指向設定中的專案名稱。

理由：兩者的使用者下一步完全不同 —— 一個要去換權杖，一個要去改設定檔的拼字。給同一句「取得失敗」等於要使用者自己猜。

單次取回的筆數 SHALL 以 100 筆為上限，MUST NOT 跟著分頁連結往下翻。取回筆數達到上限時 SHALL 讓使用者知道結果可能未完整。

理由：表格是單選的，使用者要從中挑出一筆。取回上千筆不會讓那個動作更容易，只會讓等待變長、讓表格更難掃；範圍過大時正確的操作是調緊查詢條件。

HTTPS 連線的憑證驗證 SHALL 由設定中的一個開關控制，未設定時 SHALL 視為**不驗證**。

此預設值是明確的取捨：目標環境是否使用自簽憑證尚不確定，而驗證失敗會使功能完全無法使用。代價是關閉驗證時存取權杖會暴露於連線中間人，且被攔截時沒有任何徵兆。

驗證為開啟且憑證無法通過驗證時，錯誤訊息 SHALL 指出可將受信任的 CA 憑證指給對應的環境變數，或關閉該設定開關。

該開關 MUST NOT 寫死在程式碼中 —— 它必須在設定檔中看得見，且可逐台機器調整。

GitLab REST 的呼叫 SHALL 置於共用模組的 GitLab 分組中，並遵守共用模組的既有規則；存取權杖 SHALL 由入口腳本自環境變數取出後明著傳入。

#### Scenario: 取回實際的 Merge Request

- **WHEN** 使用者選取一個確實存在的 repository 並按下重新整理，而環境中的存取權杖有效
- **THEN** 表格顯示該專案實際的 Merge Request
- **AND** 顯示的編號、標題、作者、建立日期與狀態來自 GitLab 的回應

#### Scenario: 專案名稱含斜線

- **WHEN** 選取的 repository 為 `namespace/project` 形式
- **THEN** 請求中的專案識別為該字串的 URL 編碼形式
- **AND** 請求成功

#### Scenario: 查詢條件生效

- **WHEN** 使用者開啟「只取尚未關閉的」並將天數設為 7
- **THEN** 取回的內容不含已關閉或已合併的 Merge Request
- **AND** 不含建立於 7 天之前的 Merge Request

#### Scenario: 存取權杖無效

- **WHEN** 環境中的存取權杖無效或未設定
- **THEN** 表格被清空
- **AND** 錯誤訊息指出存取權杖的問題並點名該環境變數

#### Scenario: 專案不存在

- **WHEN** 設定中的專案名稱在伺服器上不存在
- **THEN** 表格被清空
- **AND** 錯誤訊息指出找不到該專案並點名設定中的專案名稱
- **AND** 該訊息與存取權杖無效時的訊息不同

#### Scenario: 取回筆數達到上限

- **WHEN** 符合查詢條件的 Merge Request 超過 100 筆
- **THEN** 表格顯示 100 筆
- **AND** 使用者被告知結果可能未完整
- **AND** 腳本沒有為了取回其餘筆數而發出額外的請求

#### Scenario: 未設定驗證開關時連上自簽憑證的伺服器

- **WHEN** 設定中沒有驗證開關，而伺服器使用自簽憑證
- **THEN** 請求成功
- **AND** 表格顯示取回的 Merge Request

#### Scenario: 明確開啟驗證且憑證無法通過

- **WHEN** 設定中的開關被設為開啟驗證，而伺服器的憑證無法通過驗證
- **THEN** 表格被清空
- **AND** 錯誤訊息指出可指定受信任的 CA 憑證，或關閉該設定開關

### Requirement: 取得 Merge Request 描述的 GitLab 連線

取得 Merge Request 描述的腳本 SHALL 連線至設定的 GitLab 伺服器，取回指定 Merge
Request 的描述。專案與編號的識別、憑證的來源、以及 HTTPS 憑證驗證的開關 SHALL 與
取得清單那一支相同。

Merge Request 的描述可能同時含有人寫的原始描述與先前某一輪的 AI 分析。這一步 SHALL
以 AI 分析的標題為界，切出它**之前**的原始描述，MUST NOT 把先前的 AI 分析一併往下傳。

理由：不切的話，先前的分析會被當成原始描述交給後續步驟，最後的報告於是疊出兩段 AI
分析，而先前那一段永遠不會被換掉。

切出的原始描述 MUST NOT 被冠上任何由工具產生的標題 —— 產出 SHALL 是 Merge Request
描述扣掉先前的 AI 分析之後剩下的內容本身。

標題的比對 SHALL 容許標題階層、英文大小寫，以及詞與詞之間和行首行尾空白的差異。

理由：描述是使用者在 GitLab 網頁上編輯的內容，這些都可能被改動，而改動不該讓邊界
消失。

合併那一步寫進報告的那個描述標題，SHALL 在切段時被去除，使報告被貼回描述之後重跑
不會把標題累積起來。

認得的 SHALL 只有目前這一個標題。理由與已知代價見 design.md 決策二十四 —— 標題改版
後，既有描述裡若還留著舊的那一行，它會被當成描述的內容留下來。

出現在程式碼圍籬區塊內的標題 MUST NOT 被視為邊界。

理由：在那裡切下去會產出一份看起來正常、實際上被截斷的原始描述，而被截掉的內容在
報告中就真的不見了。

描述中沒有 AI 分析的標題時，整份描述 SHALL 視為原始描述。

理由：從未被本工具處理過的 Merge Request，描述就是純人寫的內容而沒有那個標題。若要求
一定要找到標題才取值，第一次執行的結果會是空的，而空描述在下游是合法值 —— 症狀會是
AI 拿到一份空白去分析，而不是一個錯誤訊息。

該 Merge Request 沒有填寫描述 SHALL 視為成功，MUST NOT 回報失敗。

指定的 Merge Request 不存在時，失敗訊息 SHALL 與專案不存在時不同，並 SHALL 指出編號
用的是畫面上的專案內編號而非全域 id。

#### Scenario: 取回實際的描述

- **WHEN** 指定一個確實存在的 Merge Request，而環境中的存取權杖有效
- **THEN** 取回的原始描述來自 GitLab 上該 Merge Request 的描述

#### Scenario: 描述中已有先前的 AI 分析

- **WHEN** 描述依序含有原始描述的標題與內容、以及 AI 分析的標題與內容
- **THEN** 這一步的產出只含原始描述那一段的內容
- **AND** 先前的 AI 分析不出現在產出中

#### Scenario: 描述中沒有任何標題

- **WHEN** 描述是一段沒有任何標題的純文字
- **THEN** 整份描述被視為原始描述

#### Scenario: 標題的階層或空白被改動

- **WHEN** 描述中 AI 分析的標題階層與常數不同，或大小寫不同，或詞間空白多寡不同
- **THEN** 該標題仍被認得，邊界正確

#### Scenario: 描述帶著報告寫出的標題

- **WHEN** 使用者把一份產出的報告貼回描述，其開頭是報告寫出的那個描述標題
- **THEN** 該行被認得並從原始描述中去除
- **AND** 重跑之後的報告中該標題只出現一次

#### Scenario: 圍籬區塊內的標題

- **WHEN** 原始描述的內容裡有一個程式碼圍籬區塊，區塊內出現 AI 分析的標題文字
- **THEN** 該處不被視為邊界
- **AND** 原始描述完整保留，包含那個圍籬區塊

#### Scenario: 沒有填寫描述

- **WHEN** 該 Merge Request 的描述為空
- **THEN** 這一步回報成功，原始描述為空
- **AND** 流程繼續執行後續步驟

#### Scenario: 指定的 Merge Request 不存在

- **WHEN** 專案存在但指定的編號在該專案中不存在
- **THEN** 這一步回報失敗
- **AND** 訊息與專案不存在時的訊息不同，並指出編號用的是專案內編號

### Requirement: device 的來源與解析

分析所使用的 device SHALL 由環境變數指定，腳本 MUST NOT 自其他來源取得它。

圖形介面呼叫端 SHALL 把設定中的 device 值注入為該環境變數；持續整合環境 SHALL 自行
設定同名的變數。

理由：腳本端因此只有一條取值路徑，兩個呼叫端對它而言完全相同 —— 與服務憑證的傳遞方式
一致。

device 名稱的比對 SHALL 不分大小寫。

值未設定或只有空白時 SHALL 使用預設 device。指定了一個沒有對應實作的名稱時 SHALL 失敗，
並在訊息中列出目前認得的所有 device 名稱。

理由：兩者的意思不同。沒指定代表「沒有特別需求」，使用通用邏輯是正確的；指定了一個不
存在的名稱代表打錯字或忘記部署，靜默改用通用邏輯會產出一份用錯邏輯、而每一個步驟都
回報成功的報告。

明確指定預設 device 的名稱 SHALL 為合法。

device 名稱 MUST NOT 被用來組成檔案路徑 —— 實作 SHALL 以名稱載入模組。

理由：既有設計明文禁止「腳本輸出的字串變成被執行的路徑」。以名稱載入完全不開那條路。

#### Scenario: 未指定 device

- **WHEN** 環境變數未設定，或其值只有空白
- **THEN** 分析使用預設 device 的實作
- **AND** 流程正常完成

#### Scenario: 指定存在的 device

- **WHEN** 環境變數的值對應到一個已存在的 device 實作
- **THEN** 分析使用該 device 的實作

#### Scenario: 指定不存在的 device

- **WHEN** 環境變數的值沒有對應的 device 實作
- **THEN** 該步驟回報失敗
- **AND** 訊息列出目前認得的所有 device 名稱

#### Scenario: 名稱大小寫不同

- **WHEN** 環境變數的值與 device 名稱僅大小寫不同
- **THEN** 仍解析到同一個 device

#### Scenario: 明確指定預設

- **WHEN** 環境變數的值就是預設 device 的名稱
- **THEN** 解析成功，行為與未指定時相同

### Requirement: device 的發現

目前有哪些 device SHALL 由掃描 device 實作所在的位置決定，MUST NOT 另外維護一份名單。

以底線開頭的目錄 MUST NOT 被視為 device。

理由：另外維護的名單會與實際的目錄漂移，而失敗訊息中那份清單一旦不準就比沒有更糟。
掃描也使「新增一個 device」不需要修改任何程式碼。底線開頭的慣例讓範本目錄不會被誤認
為 device。

#### Scenario: 新增一個 device

- **WHEN** 在 device 實作的位置新增一個目錄並放入鉤子
- **THEN** 該名稱即可被環境變數指定，不需要修改任何既有程式碼

#### Scenario: 範本目錄不是 device

- **WHEN** 列出目前認得的 device
- **THEN** 以底線開頭的目錄不出現在清單中

### Requirement: device 鉤子的範圍

流程中 SHALL 只有三個步驟因 device 而異：取得相關資訊（抽出 JIRA key 與種類）、AI 分析、
合併為 markdown。

取得 Merge Request 描述 MUST NOT 因 device 而異。

取得程式碼審閱報告的**運算與版面** MUST NOT 因 device 而異；device 僅得**宣告**來源文件中
總表那一節的標題。該步驟 MUST NOT 載入或執行任何 device 的實作。

理由：會因產品線而異的是別人的工具產出什麼格式，不是本工具的處理方式。以宣告而非鉤子承載
這件事，使擷取的演算法只有一份，而該步驟也不會出現「哪一個 device 的鉤子壞了」這類失敗。

鉤子 SHALL 分為兩類，其解析方式不同：

- **不因種類而異**：抽出 JIRA key、抽出種類。兩者在種類被決定之前執行（後者正是決定它的
  那一支），因此種類對它們沒有意義。
- **因種類而異**：AI 分析、合併為 markdown。

每一步的入口腳本 SHALL 保留共用的部分 —— 信封處理、憑證取得、對外服務的呼叫、產物落檔、
失敗訊息與進度回報 —— 並只將業務運算交給 device 的鉤子。

理由：若每個 device 各有一支完整的腳本，共用部分（服務錯誤的分類指引、程式碼區塊界線的
計算、diff 的長度上限）會在每個 device 中各出現一次並各自漂移。

#### Scenario: 只有三個步驟因 device 而異

- **WHEN** 以不同的 device 執行同一個 Merge Request 的分析
- **THEN** 取得描述的行為相同
- **AND** 取得程式碼審閱報告的擷取演算法與報告版面相同，只有總表那一節的標題可以不同
- **AND** 抽出 JIRA key、抽出種類、AI 分析與報告版面可以不同

#### Scenario: 取得程式碼審閱報告不載入 device 實作

- **WHEN** 某個 device 的鉤子檔案有語法錯誤
- **THEN** 取得程式碼審閱報告那一步不因此失敗

#### Scenario: 抽出用的鉤子不因種類而異

- **WHEN** 解析抽出 JIRA key 或抽出種類的鉤子
- **THEN** 只在該 device 與預設 device 之間尋找，不涉及任何種類

#### Scenario: 共用部分不因 device 重複

- **WHEN** 某個 device 的鉤子執行失敗
- **THEN** 失敗訊息的形式與其他 device 相同，因為它由入口腳本產生

### Requirement: 鉤子的逐項回退

device 的實作 SHALL 允許只提供部分鉤子。缺少的鉤子 SHALL 使用預設 device 的對應實作。

理由：只想改變報告版面的 device 不應被迫複製其他鉤子 —— 那份複本會與預設實作漸漸不同。

同一個原則 SHALL 適用於種類：種類目錄 SHALL 允許只提供部分鉤子，缺少的依「種類只在自身
device 之內解析」的順序回退。

此回退 SHALL 只適用於「device 存在但缺少某個鉤子」與「種類目錄存在但缺少某個鉤子」。
device 本身不存在時的行為見其對應需求（失敗）；種類不存在時的行為見「認不得的種類」。

#### Scenario: 只提供一個鉤子

- **WHEN** 某個 device 只提供報告版面的鉤子
- **THEN** 報告版面使用該 device 的實作
- **AND** 抽出 JIRA key 與 AI 分析使用預設 device 的實作

#### Scenario: 種類目錄只提供一個鉤子

- **WHEN** 某個種類目錄只提供 AI 分析的鉤子
- **THEN** AI 分析使用該種類的實作
- **AND** 報告版面回退到該 device 的通用實作

#### Scenario: 兩種缺失的區別

- **WHEN** device 存在但缺少某個鉤子
- **THEN** 使用預設的該鉤子，流程繼續
- **AND** 這與 device 本身不存在時的失敗是不同的行為

### Requirement: 鉤子的輸入與輸出邊界

鉤子收到的資料 SHALL 包含該步驟手上所有相關的輸入，即使目前的實作並未全部用到。

合併為 markdown 的鉤子 SHALL 只回傳「AI 分析那一段標題底下的內容」。該標題本身、原始
描述那一段、段落分隔線與末尾的出處 SHALL 由入口腳本寫出，device MUST NOT 能改變它們。

理由：AI 分析那一段的標題同時是下一次執行時切出原始描述的邊界。若 device 能改寫它，某個
device 把它寫成別的文字就會讓下一輪找不到邊界 —— 整份舊報告被當成原始描述，再接上新的
一段，於是不斷累積，而每一個步驟都回報成功。由入口腳本寫出那一行，此保證即為結構性的，
不依賴任何人記得。

輸入從寬的理由：日後補參數需要修改所有 device 的鉤子簽章，而多給參數的成本為零。

需要連線、憑證或錯誤分類才能取得的東西，SHALL 以**已經取得的內容**或**可呼叫的能力**
交給鉤子，MUST NOT 要求鉤子自行處理這些。同理，回報進度與寫出除錯檔 SHALL 以可呼叫的
形式提供，MUST NOT 要求鉤子匯入入口腳本的模組。

理由：鉤子是使用者寫的，而改 prompt 的人不該為了一句話去面對連線與憑證。交出一個「能
做某件事」的函式而不是整個模組，也使鉤子無法自行結束行程。

#### Scenario: 報告骨架不受 device 影響

- **WHEN** 以任何 device 產出報告
- **THEN** 原始描述那一段、AI 分析那一段的標題與末尾的出處都存在且形式相同
- **AND** 只有 AI 分析標題底下的內容因 device 而異

#### Scenario: 貼回描述後仍切得回來

- **WHEN** 使用者把任一 device 產出的報告貼回 Merge Request 的描述，之後再執行一次
- **THEN** 原始描述被正確切出
- **AND** 新報告中 AI 分析只有一段

#### Scenario: 鉤子不需處理連線

- **WHEN** device 的 AI 分析鉤子被呼叫
- **THEN** 程式碼差異已經是現成的內容
- **AND** 取得議題內容、回報進度與寫出除錯檔都以可呼叫的形式提供

### Requirement: 鉤子回傳的驗證與版本標記

AI 分析的鉤子 SHALL 只回傳分析內容，MUST NOT 自行填寫結構的版本號；版本號 SHALL 由入口
腳本標記。

入口腳本 SHALL 在收到鉤子的回傳時立即驗證其結構，且 SHALL 與渲染前的驗證使用同一份規則。

理由：讓鉤子自行填寫版本號，複製範本時忘記修改就會產出一個聲稱是某版、實際是另一種形狀
的檔案。立即驗證則使錯誤在**產生它的那一步**被指出 —— 否則根因在 AI 分析、症狀卻出現在
兩步之後的渲染，而訊息無法指出是哪個 device 的哪個檔案。

#### Scenario: 鉤子回傳的結構有誤

- **WHEN** 某個 device 的 AI 分析鉤子回傳的結構不符合契約
- **THEN** AI 分析那一步立即回報失敗
- **AND** 訊息指出是哪一個 device、哪一個欄位與讀到的型別

#### Scenario: 版本號由入口標記

- **WHEN** 鉤子回傳的內容中沒有版本號
- **THEN** 落檔的結構仍帶有正確的版本號

### Requirement: device 實作載入失敗的回報

device 的實作無法載入或執行時（語法錯誤、匯入失敗、執行期例外），失敗訊息 SHALL 指出是
哪一個 device 與哪一個鉤子，並 SHALL 包含足以定位問題的資訊。

理由：圖形介面的錯誤視窗只顯示結果訊息，不顯示診斷細節。而 device 腳本的開發者的迴路是
「修改腳本、按下按鈕、看結果」—— 若訊息中沒有檔案與位置，該迴路無法運作。

#### Scenario: device 腳本有語法錯誤

- **WHEN** 某個 device 的鉤子有語法錯誤
- **THEN** 該步驟回報失敗
- **AND** 訊息指出是哪一個 device 的哪一個鉤子

#### Scenario: device 腳本執行時拋出例外

- **WHEN** 某個 device 的鉤子在執行中拋出例外
- **THEN** 該步驟回報失敗
- **AND** 訊息指出是哪一個 device 的哪一個鉤子，並包含定位問題所需的資訊

### Requirement: device 實作的版本

每一個 device SHALL 宣告自己的版本。未宣告時 SHALL 視為錯誤。

理由：該版本會出現在報告的出處資訊中。若它可以是空的，那一行就無法說明報告是由哪一版
邏輯產生的 —— 而那正是它存在的理由。

版本之外的其他宣告 SHALL 為選填，且 SHALL 有明確的預設值。

理由：既有的 device 不應因為新增了一項宣告而失效。版本是例外，因為它沒有合理的預設。

#### Scenario: device 未宣告版本

- **WHEN** 被指定的 device 沒有宣告版本
- **THEN** 該步驟回報失敗，訊息指出是哪一個 device

#### Scenario: 未宣告選填項目

- **WHEN** 某個 device 只宣告了版本
- **THEN** 其餘宣告使用預設值，該 device 正常執行

### Requirement: device 實作的範本

專案 SHALL 提供 device 鉤子的範本，說明每一個鉤子收到什麼、必須回傳什麼，以及可供使用
的共用函式。

範本 SHALL 包含種類目錄的範本。

範本的宣告檔 SHALL 以註解列出所有可用的宣告項目及其預設值。

理由：這些名稱沒有別的地方會提示。要使用時得翻文件或讀載入器的原始碼，而那是一個每次
都要付、且容易讓人直接放棄的成本。

範本與其中的種類範本 MUST NOT 被視為可用的 device 或種類。

#### Scenario: 依範本新增 device

- **WHEN** 開發者複製範本並填入自己的邏輯
- **THEN** 該 device 可被環境變數指定並正常執行

#### Scenario: 宣告項目可被發現

- **WHEN** 開發者開啟範本的宣告檔
- **THEN** 所有可用的宣告項目及其預設值以註解列出

### Requirement: 取得相關資訊的 GitLab 連線

取得相關資訊那一步 SHALL 自行連線 GitLab 取得該 Merge Request，MUST NOT 依賴其他步驟
轉送這些資料。

理由：抽出 JIRA key 與種類的預設規則需要 Merge Request 的標題，而取得描述那一步的產物
只有描述本文。圖形介面也不可靠 —— 使用者手動輸入編號時畫面上沒有標題。自行取得使該步
可以單獨執行，且圖形介面與持續整合不需要多傳任何東西。

已知代價：同一個 Merge Request 在一次分析中被取得兩次。加入種類的抽出 MUST NOT 使這個
次數增加。

交給抽取鉤子的 SHALL 是整理過的欄位（至少包含標題、來源分支、目標分支、描述、專案與
編號），MUST NOT 是 GitLab 原樣的回應物件。抽出 JIRA key 與抽出種類的鉤子 SHALL 收到
相同的欄位。

理由：原樣傳遞會讓 GitLab 回應的所有欄位成為對 device 作者的契約，日後無法更換取得方式。

取得失敗時 SHALL 回報失敗並結束流程，且失敗訊息的分類 SHALL 與其他連線 GitLab 的腳本
一致（存取權杖、專案或 Merge Request 不存在、憑證驗證失敗各自不同且可行動）。

#### Scenario: 取得 Merge Request

- **WHEN** 該步驟執行且環境中的存取權杖有效
- **THEN** 它自行取得該 Merge Request 的資料
- **AND** 不需要其他步驟轉送標題或分支

#### Scenario: 鉤子收到整理過的欄位

- **WHEN** 抽取鉤子被呼叫
- **THEN** 它收到的是整理過的欄位，而非 GitLab 原樣的回應物件

#### Scenario: 兩個抽取鉤子共用同一次取得

- **WHEN** 該步驟同時抽出 JIRA key 與種類
- **THEN** 只向 GitLab 取得該 Merge Request 一次

#### Scenario: 取得失敗

- **WHEN** 無法取得該 Merge Request
- **THEN** 該步驟回報失敗，流程結束
- **AND** 訊息的分類與其他連線 GitLab 的腳本一致

### Requirement: AI 服務的呼叫

AI 分析 SHALL 經由一個共用模組向 AI 服務提問，各 device MUST NOT 各自實作連線、重試與
錯誤分類。

理由：每一個 device 都會遇到同一組問題（限流、逾時、回覆被包在圍籬裡），各寫一份的結果
是每一份都只解決了作者當時遇到的那幾種。

該模組 SHALL 只負責「問與等」。組 prompt SHALL 由 device 的鉤子負責，MUST NOT 收進共用
模組 —— 要問什麼正是各產品線要自己掌握的東西，收進共用模組等於把 device 機制的意義
抵消掉。

服務端點 SHALL 取自設定中該 AI 模式的端點欄位，且該欄位 SHALL 允許在位址尾端以冒號附加
一段識別碼。拆解 SHALL 只把**最後一個斜線之後**的冒號視為分隔符。

理由：位址本身至少含有一個冒號（通訊協定），也可能含有連接埠。以第一個或最後一個冒號
切都會在某些位址上把路徑的一部分當成識別碼送出，而伺服器只會回一個看不出原因的錯誤。

端點未附識別碼時 SHALL 立即失敗並指出正確的寫法，MUST NOT 送出一個沒有識別碼的請求。

設定中的模型名稱 MUST NOT 進入請求 —— 模型由識別碼那一端決定。它 SHALL 僅作為報告出處
的資訊，且 SHALL NOT 成為必填。

理由：收下一個送不出去的參數，會讓人以為換掉它就會換模型。而讓一個純顯示用的欄位擋住
整條流程，與它的作用不成比例。

#### Scenario: 端點含識別碼

- **WHEN** 設定的端點為 `https://主機:8443/路徑:識別碼`
- **THEN** 請求送往 `https://主機:8443/路徑`
- **AND** 識別碼為 `識別碼`，連接埠未被誤判為識別碼

#### Scenario: 端點未附識別碼

- **WHEN** 設定的端點沒有尾端的識別碼
- **THEN** 該步驟立即失敗，訊息指出端點缺少識別碼
- **AND** 沒有任何請求被送出

#### Scenario: 模型名稱未進入請求

- **WHEN** AI 分析送出請求
- **THEN** 請求內容不含設定中的模型名稱
- **AND** 模型名稱為空時流程仍可完成

### Requirement: AI 服務的回應

共用模組 SHALL 認得服務的回應信封，並 SHALL 在信封標示失敗時回報失敗，即使傳輸層回報
成功。

理由：把一個標示失敗的回應當成答案，取到的通常是錯誤說明本身，而它會被當成分析寫進
報告 —— 那份報告看起來是完整的。

失敗時的訊息 SHALL 帶上服務自己給的說明。

理由：只有狀態碼的訊息無法行動。

回覆內容 SHALL 同時接受字串與已解析的物件兩種形式，並 SHALL 一律以文字交給呼叫端。

理由：這一層對外的約定是「回一段文字」。在此分岔的話，每一個呼叫端都要先判斷這次拿到
的是哪一種。

取不到回覆內容時，訊息 SHALL 列出回應實際含有的欄位名。

理由：這個錯誤最常見的成因是回應形狀與預期不同，而該清單就是修正它所需的全部資訊。

#### Scenario: 信封標示失敗

- **WHEN** 傳輸層回報成功，但回應信封的狀態不是成功
- **THEN** 該步驟回報失敗
- **AND** 訊息含有服務給的說明，而非僅有狀態碼

#### Scenario: 回覆內容已被服務解析

- **WHEN** 回應中的回覆內容是一個物件而非字串
- **THEN** 呼叫端仍取得一段文字，解析路徑與字串時相同

#### Scenario: 回應形狀不符

- **WHEN** 回應中找不到回覆內容
- **THEN** 訊息列出該回應實際含有的頂層欄位名

### Requirement: AI 呼叫的重試界線

共用模組 SHALL 重試限流、伺服器端暫時狀況、逾時與連線中斷，且 MUST NOT 重試憑證驗證
失敗、認證失敗、端點不存在、請求過長與回應形狀不符。

理由：這幾種重試三次結果完全一樣，只是把一個註定的失敗等三倍，而使用者面對的是一個沒有
動靜的對話框。一張不被信任的憑證不會在兩秒後變得被信任。

是否值得重試 SHALL 由拋出錯誤的那一處決定，MUST NOT 由重試邏輯自狀態碼反推。

理由：有一整類錯誤沒有狀態碼卻要分在兩邊 —— 連線中斷該重試，回應的欄位與預期不符不該。

服務指定了等待秒數時 SHALL 依其指定等待；未指定時 SHALL 指數退避。指定的秒數超過上限時
SHALL 立即失敗並說明原因，MUST NOT 照其等待。

理由：限流時伺服器自己說的比猜的準。但一個卡上數分鐘、最後仍然失敗的對話框，比立刻說
明白糟得多。

逾時 SHALL 以分鐘為量級設定，MUST NOT 沿用其他 REST 呼叫的秒級預設。

理由：秒級的逾時會把正常的長回答判成失敗，然後重試 —— 結果是等更久，而且每一次都計費。

#### Scenario: 限流後重試成功

- **WHEN** 服務回報限流並指定等待秒數，其後回應成功
- **THEN** 該次呼叫依指定秒數等待後重試並成功

#### Scenario: 認證失敗不重試

- **WHEN** 服務回報認證失敗
- **THEN** 該次呼叫只嘗試一次即回報失敗

#### Scenario: 憑證驗證失敗不重試

- **WHEN** 連線因憑證驗證失敗而中斷
- **THEN** 該次呼叫只嘗試一次即回報失敗
- **AND** 訊息指出是憑證驗證失敗

#### Scenario: 指定的等待過長

- **WHEN** 服務要求的等待秒數超過上限
- **THEN** 該次呼叫立即失敗並說明要求的秒數與上限

### Requirement: AI 服務的憑證與傳輸

AI 服務的端點、金鑰與模型名稱 SHALL 經由步驟參數傳遞，MUST NOT 注入為環境變數。

理由：其餘服務的憑證走環境變數是為了讓持續整合與圖形介面共用同一條取值路徑；AI 的這
三項則隨使用者在畫面上選的模式而變，屬於該次執行的參數。兩者都不上命令列。

AI 服務的 TLS 憑證驗證 SHALL 預設關閉，並 SHALL 可經由環境變數開啟。

理由：與 GitLab 的同名設定同一個取捨。地端服務多半使用自簽或內部憑證，驗證失敗會使功能
完全無法使用。這是明著寫出來的選擇，不是疏忽。

#### Scenario: 金鑰不在命令列上

- **WHEN** AI 分析那一步被啟動
- **THEN** 該行程的命令列參數中不含金鑰

#### Scenario: 自簽憑證可連線

- **WHEN** AI 服務使用自簽憑證，且未設定開啟驗證的環境變數
- **THEN** 呼叫成功

#### Scenario: 明確開啟驗證

- **WHEN** 設定開啟驗證的環境變數，而服務使用自簽憑證
- **THEN** 該次呼叫立即失敗，訊息指出是憑證驗證失敗

### Requirement: AI 分析的素材備置

AI 分析那一步 SHALL 在呼叫鉤子**之前**取得該 Merge Request 的程式碼差異，並 SHALL 在
取得失敗時回報失敗並結束流程。

理由：沒有差異的「程式碼分析」只能靠描述推測，而它會回報成功。在呼叫鉤子之前取得，則
連線問題不會被包裝成「某個 device 的鉤子執行失敗」——那會把一個連線問題講成腳本寫壞了。

差異 SHALL 有大小上限，超過時 SHALL 截斷並留下可見的記號。

理由：靜默截斷會讓模型對著半份差異給出一份自信的分析，而讀報告的人看不出它只看到一半。

相關議題的內容 SHALL 在鉤子判定該識別碼有效**之後**才取得，MUST NOT 在此之前取得。

理由：識別碼是否有效屬於 device 的政策，入口不認得該政策。先取得的話，標題前綴那類
從方括號抽出來的字串每一次都會換回一個查無此項的結果。

取得議題內容的能力 SHALL 以可呼叫的形式交給鉤子，MUST NOT 要求鉤子自行處理連線與憑證。

理由：撰寫 prompt 的人不應為了改一句話而面對這些。

相關議題取得失敗 SHALL NOT 使流程失敗；prompt SHALL 省略該段落。

理由：議題內容在此是補充資料，查不到的原因多半無害。

議題描述 SHALL 有長度上限並在截斷時留下記號。

理由：該欄位沒有長度限制，實務上會出現整份規格書，原樣送出會把差異擠出可用的範圍。

#### Scenario: 差異在呼叫鉤子前取得

- **WHEN** AI 分析那一步執行
- **THEN** 程式碼差異在鉤子被呼叫之前已經取得
- **AND** 取得失敗時的訊息不指向任何 device 的鉤子

#### Scenario: 識別碼無效時不查詢

- **WHEN** 自標題抽出的識別碼被鉤子判定為無效
- **THEN** 該次執行未向議題系統發出任何查詢
- **AND** prompt 中沒有議題那一段

#### Scenario: 議題查無此項

- **WHEN** 識別碼有效但議題系統查不到該議題
- **THEN** 流程繼續，prompt 省略議題那一段

### Requirement: prompt 的組成

prompt 的內容 SHALL 由 device 的 AI 分析鉤子決定。

該鉤子 SHALL 把 prompt 的組成獨立成一支可單獨呼叫的函式，使其可在不呼叫 AI 的情況下
印出檢視。

理由：調整 prompt 是一件要反覆進行的事，每改一次就付一次費用與等待是不必要的。

樣板填值失敗時 SHALL 回報一個指出問題所在的訊息：認不得的佔位符 SHALL 指名該佔位符並
列出可用的佔位符；大括號不成對或為空 SHALL 說明如何跳脫。MUST NOT 直接拋出底層的例外。

理由：貼進 prompt 的內容常含有大括號（結構化範例、程式碼片段），而底層例外指名的往往
是剛貼進去的那段內容的一部分，完全看不出是跳脫的問題。

期望的回覆格式與解析回覆的實作 SHALL 在同一份 device 實作中，且 SHALL 互相標註。

理由：兩者是同一件事的兩面。改了一邊而未改另一邊，症狀是「回覆格式不符」，而該訊息
指不出真正的原因。

#### Scenario: 不呼叫 AI 也能檢視 prompt

- **WHEN** 開發者呼叫組成 prompt 的那支函式
- **THEN** 取得完整的 prompt 文字，且未發出任何請求

#### Scenario: 樣板含未跳脫的大括號

- **WHEN** 樣板中含有未跳脫的大括號
- **THEN** 訊息指名該處，並列出可用的佔位符與跳脫的寫法

### Requirement: AI 回覆不符預期時的重問

共用模組 SHALL 支援在回覆不符預期時，於 prompt 尾端追加一段要求後重新提問，次數 SHALL
由呼叫端決定。

回覆的解析與結構的檢查 SHALL 串成同一道轉換交給共用模組，MUST NOT 分成呼叫前後兩段。

理由：分兩段的話，第二段執行於重問機制之外，重問永遠不會觸發 —— 而「格式合法但結構
不符」正是模型最常見的失手方式。

重問用盡後仍不符時 SHALL 回報失敗，MUST NOT 以不完整的結構繼續。

理由：湊出來的報告看起來是完整的。

#### Scenario: 回覆前多了一句開場白

- **WHEN** AI 的回覆在結構化內容之前多了一段文字
- **THEN** 共用模組追加要求後重問一次
- **AND** 第二次的回覆符合格式時，該步驟成功

#### Scenario: 結構不符也會觸發重問

- **WHEN** AI 的回覆格式合法但缺少必要的結構
- **THEN** 共用模組同樣重問，而非直接失敗

### Requirement: 除錯輸出的內容

開啟除錯輸出時，AI 分析那一步 SHALL 將實際送出的 prompt 與**每一次**收到的原始回覆各自
寫成獨立的檔案。

理由：調整 prompt 時唯一真正需要看的就是這兩份，而它們都不適合寫進逐行的日誌 ——
prompt 含有原始碼，回覆的長度以萬字計。

每一次回覆 SHALL 寫在解析之前，且各自成檔。

理由：重問成功會覆蓋掉失敗的那一次，而失敗的那一次才是線索。

未開啟除錯輸出時 SHALL NOT 寫出任何檔案。

理由：prompt 含有原始碼，預設落到磁碟並非使用者要求的事。

流程步驟失敗時 SHALL 在除錯目錄留下該次失敗的訊息、代碼與細節；鉤子拋出例外時，細節
SHALL 包含完整的追蹤堆疊。

理由：只在成功時留下紀錄，等於最需要那份紀錄時剛好沒有。而鉤子的錯誤發生在某一行，
只有類別與訊息指不出位置。

鉤子回傳的結構未通過驗證時 SHALL 將該結構整份寫入除錯目錄。

理由：被告知某個欄位型別不對之後，仍然需要看到它實際的樣子才改得動。

#### Scenario: 調整 prompt 時取得所需的兩份資料

- **WHEN** 使用者開啟除錯輸出並執行一次分析
- **THEN** 除錯目錄中含有該次送出的 prompt 與收到的原始回覆

#### Scenario: 重問時兩次都留下

- **WHEN** 第一次回覆不符格式而觸發重問
- **THEN** 除錯目錄中同時存在兩次回覆的檔案

#### Scenario: 失敗也留下紀錄

- **WHEN** AI 分析那一步失敗
- **THEN** 除錯目錄的日誌中含有該次失敗的訊息與代碼

### Requirement: 程式碼審閱報告的來源與取得時機

取得程式碼審閱報告那一步 SHALL 自該次採用的 JIRA 議題的附件中取得報告，MUST NOT 自其他
來源取得。

該步驟 SHALL 收到上一步抽出的 JIRA key 與 AI 分析那一步判定的 key 狀態。只有狀態為有效時
SHALL 向議題系統發出請求；沒有 key 或狀態不是有效時 MUST NOT 發出任何請求，並 SHALL 回報
成功且不產生任何產物。

理由（為什麼在這一步而不是更早）：key 是否有效屬於 device 的政策，而判定發生在 AI 分析
那一步。在那之前取得附件，等於對每一筆標題前綴是 `[WIP]`、`[Draft]` 這類字串的 Merge
Request 都白打一趟議題系統，換回一個查無此項的結果 —— 與「相關議題的內容在判定有效之後
才取得」是同一條理由。

該步驟 MUST NOT 接受一個獨立的布林開關來表示「要不要取得」。理由：「要不要做」與「對誰
做」由同一個值承載（key 與其狀態），就不會出現「開關為真但沒有 key」這種自相矛盾的狀態。

議題系統的端點與存取權杖 SHALL 取自環境變數，與其他連線議題系統的步驟相同。

#### Scenario: 有有效的 key 時取得附件

- **WHEN** 上一步抽出的 JIRA key 被判定為有效，且議題系統可連線
- **THEN** 該步驟向該議題查詢附件清單
- **AND** 報告中出現程式碼審閱那一段

#### Scenario: 沒有 JIRA key

- **WHEN** Merge Request 的標題中抽不出 JIRA key
- **THEN** 該步驟不向議題系統發出任何請求
- **AND** 該步驟回報成功且不產生任何產物
- **AND** 報告中沒有程式碼審閱那一段

#### Scenario: key 被判定為無效

- **WHEN** 抽出的 key 不符合該 device 的樣式而被判定為無效
- **THEN** 該步驟不向議題系統發出任何請求
- **AND** 報告中沒有程式碼審閱那一段

### Requirement: 程式碼審閱報告附件的選取

附件 SHALL 以檔名篩選：以設定的關鍵字**開頭**，且副檔名為 `.md`。

比對 SHALL 區分大小寫。理由：關鍵字是部署者刻意填進設定檔的值，與使用者主動輸入的過濾
文字同一類，而非被動看到的結果。

比對 SHALL 為前綴比對，MUST NOT 為子字串比對。理由：子字串比對會讓 `Old_CodeReview_backup.md`
這類檔案參與競爭，而它多半正是不該被選中的那一份。

副檔名 MUST NOT 可由設定或宣告改變。理由：這一步的產出要直接接進報告的一個段落，「必須是
markdown」是它的契約而非使用者偏好。可配置的話，指向一份試算表或壓縮檔會讓二進位內容被貼
進報告，而每一個步驟都回報成功。

符合條件者有多筆時 SHALL 取上傳時間最新的一筆。上傳時間 SHALL 以解析後的時間值比較，
MUST NOT 以字串的字典序比較 —— 時間值帶有時區，字典序在跨時區時會排出錯誤的先後。上傳
時間相同時 SHALL 以議題系統給的識別碼較大者為新。

取得附件內容之前 SHALL 先以議題系統回報的大小拒絕超過上限者，MUST NOT 先下載再丟棄。

本地存檔的檔名 SHALL 由本工具決定，MUST NOT 取自附件本身的檔名。理由：附件檔名是上傳者
打的字，用它組成路徑與「device 名稱不得用來組成檔案路徑」是同一類風險。

附件內容 SHALL 以 UTF-8 解碼，並 SHALL 容許位元組順序記號。解碼失敗時 MUST NOT 改猜其他
編碼，也 MUST NOT 以替代字元忽略壞掉的位元組。理由：猜錯編碼會產出一份看起來正常的亂碼
報告，替代字元會產出一份少了幾個字卻回報成功的報告 —— 兩者都比一個明確的訊息糟。

該議題上沒有符合條件的附件 SHALL 視為成功，並 SHALL 不產生任何產物；報告中因此沒有程式碼
審閱那一段。

#### Scenario: 只收關鍵字開頭的檔名

- **WHEN** 議題上有一個檔名以關鍵字開頭的 markdown 附件，以及一個檔名中間才出現關鍵字的附件
- **THEN** 只有前者參與選取

#### Scenario: 大小寫不同的檔名不被選中

- **WHEN** 附件的檔名與關鍵字僅大小寫不同
- **THEN** 該附件不被選中
- **AND** 沒有其他符合條件的附件時，報告中沒有程式碼審閱那一段

#### Scenario: 多筆時取最新

- **WHEN** 議題上有三個符合條件的附件，上傳時間各不相同
- **THEN** 被取得的是上傳時間最新的那一個

#### Scenario: 上傳時間跨時區

- **WHEN** 兩個符合條件的附件的上傳時間帶有不同的時區，而字典序與實際先後相反
- **THEN** 被取得的是實際上較晚上傳的那一個

#### Scenario: 附件過大

- **WHEN** 最新的符合條件的附件，其議題系統回報的大小超過上限
- **THEN** 該附件的內容不被取得
- **AND** 報告中出現程式碼審閱那一段，內容說明該附件過大

#### Scenario: 解碼失敗

- **WHEN** 取得的附件不是合法的 UTF-8
- **THEN** 報告中出現程式碼審閱那一段，內容說明解碼失敗並指出應存為 UTF-8
- **AND** 流程繼續執行

#### Scenario: 議題上沒有符合的附件

- **WHEN** 該議題有附件，但沒有任何一個符合檔名條件
- **THEN** 該步驟回報成功且不產生任何產物
- **AND** 報告中沒有程式碼審閱那一段

### Requirement: 風險評估總表的擷取

取得程式碼審閱報告那一步 SHALL 自附件的內容中擷取風險評估總表，並 SHALL 只交出**表格
本身**，MUST NOT 自行冠上任何標題。理由與其他段落一致：標題由合併那一步寫出，產生內容的
步驟無從知道自己會被放在哪一層。

定位 SHALL 以總表那一節的標題為依據。標題的比對 SHALL 由標題常數導出，MUST NOT 另外手寫
一份字面文字，且 SHALL 容許標題階層與行首行尾空白的差異。

出現在程式碼圍籬區塊內的標題 MUST NOT 被視為該節的開始；圍籬區塊內的表格 MUST NOT 被
擷取。

擷取的搜尋範圍 SHALL 限定在該標題之後到**下一個標題或內容結尾**之間，MUST NOT 越過下一個
標題繼續搜尋。

理由：這是本需求最重要的一條。若不限定範圍而只是「往下找第一個表格」，當那一節恰好沒有
總表時會抓到**下一節的表格** —— 而那份報告會看起來完全正常，標題還寫著風險評估表。抓不到
必須是抓不到。

範圍內 SHALL 取第一個表格。表格的起點 SHALL 為第一個以表格分隔字元開頭的行，終點 SHALL
為其後第一個不以該字元開頭的行。

擷取到的區塊 SHALL 通過形狀檢查：至少含有一列表頭與一列分隔列。不通過時 SHALL 視同沒有
擷取到。理由：這道檢查不預設任何欄位名稱，卻擋掉「那一節只有散文」與「來源少了分隔列」
兩種情況 —— 後者原樣貼進報告不會被渲染成表格，給訊息比給一堆分隔字元好。

表格 SHALL 原樣傳遞：MUST NOT 對齊、排序、改變欄序或補齊欄位。理由：表格的欄位因 device
而異，任何正規化都可能弄壞某一個 device 的表格。

沒有前後分隔字元的表格寫法 MAY 不被支援。理由：改以「這一行含有分隔字元」偵測，會把散文
中任何一個分隔字元當成表格的開始。

#### Scenario: 擷取那一節底下的表格

- **WHEN** 附件中有總表那一節，其下有一個格式正確的表格
- **THEN** 該表格被擷取，內容與來源完全相同
- **AND** 擷取的內容不含任何標題行

#### Scenario: 標題階層不同

- **WHEN** 附件中總表那一節的標題階層與常數不同
- **THEN** 該標題仍被認得

#### Scenario: 找不到那一節

- **WHEN** 附件中沒有總表那一節的標題
- **THEN** 報告中出現程式碼審閱那一段，內容說明找不到那一節
- **AND** 流程繼續執行

#### Scenario: 不越過下一個標題

- **WHEN** 總表那一節底下沒有表格，而它的下一節有一個表格
- **THEN** 下一節的表格 MUST NOT 被擷取
- **AND** 報告中出現程式碼審閱那一段，內容說明那一節中沒有表格

#### Scenario: 圍籬區塊內的標題與表格

- **WHEN** 附件的程式碼圍籬區塊內出現總表那一節的標題文字與一個表格
- **THEN** 該處不被視為那一節的開始，區塊內的表格不被擷取

#### Scenario: 形狀不符

- **WHEN** 那一節底下的內容缺少分隔列
- **THEN** 視同沒有擷取到，報告中出現程式碼審閱那一段並說明原因

#### Scenario: 表格原樣呈現

- **WHEN** 來源的表格欄位未對齊、欄位名稱與其他 device 不同
- **THEN** 報告中呈現的表格與來源完全相同，未被重新對齊或改變欄序

#### Scenario: 同一節有多個表格

- **WHEN** 總表那一節底下有兩個表格
- **THEN** 被擷取的是第一個

### Requirement: 總表那一節的標題可由 device 宣告

來源文件中總表那一節的標題 SHALL 有一個預設值，並 SHALL 可由 device 在自己的宣告中覆寫。
未宣告時 SHALL 使用預設值。

該宣告 MUST NOT 為必填。

理由：會因產品線而異的是**別人的工具產出什麼格式**，不是本工具的處理方式。各條產品線的
code review 工具不保證把那一節叫同一個名字。

取得程式碼審閱報告那一步的**運算與版面** MUST NOT 因 device 而異 —— device 只宣告一個
字串，MUST NOT 在該步驟中執行任何程式碼。

理由：擷取的演算法只有一份，不會每個 device 各長一份而各自漂移；而且該步驟因此不會出現
「哪一個 device 的鉤子壞了」這類失敗。

報告中程式碼審閱那一段的標題、總表的小標題，以及日期／作者／連結三行的版面，MUST NOT 可
由 device 覆寫。

#### Scenario: 未宣告時用預設

- **WHEN** 被指定的 device 沒有宣告總表那一節的標題
- **THEN** 擷取以預設標題進行

#### Scenario: device 宣告了不同的標題

- **WHEN** 某個 device 宣告了與預設不同的標題，而附件中那一節正是該標題
- **THEN** 該節被正確定位並擷取到表格

#### Scenario: 版面不因 device 而異

- **WHEN** 以兩個不同的 device 各產出一份報告，兩份都取得了總表
- **THEN** 兩份報告中程式碼審閱那一段的標題、小標題與三行資訊的版面完全相同

### Requirement: 程式碼審閱取得失敗的分類

取得程式碼審閱報告那一步的失敗 SHALL 分為三類，行為各不相同：

| 類別 | 判定方式 | 行為 |
|---|---|---|
| 部署缺漏 | 不必發出任何請求即可判定 | 回報失敗，結束整條流程 |
| 外部服務的回答 | 發出請求之後才知道 | 回報成功，訊息寫入產物 |
| 別人文件的內容不合約定 | 取得內容之後才知道 | 回報成功，訊息寫入產物 |

**部署缺漏** SHALL 包含：總表附件的檔名關鍵字未設定、議題系統的端點或存取權杖未設定。
這一類的檢查 SHALL 在進入業務邏輯之前進行，且 SHALL 無條件執行 —— 不論該次是否真的需要
取得附件。

理由（為何無條件）：只在「真的要去抓」時才檢查，會讓一個設定錯誤只在剛好遇到有效 key 的
Merge Request 時才浮現。一個有時才出現的部署錯誤比每次都出現的難查得多。

失敗訊息 SHALL 同時點名該環境變數與設定檔中對應的鍵。理由：只說環境變數沒設，使用者會去
設系統環境變數，而真正該改的是執行檔旁那份設定檔。

**外部服務的回答** SHALL 包含：連線失敗、逾時、連線中斷、認證或授權被拒、指定的議題不
存在、附件下載失敗。

**別人文件的內容不合約定** SHALL 包含：找不到總表那一節、那一節中沒有表格、擷取到的區塊
形狀不符、附件解碼失敗、附件過大。

後兩類 MUST NOT 使整條流程失敗。

理由：這一步在 AI 分析之後執行，因此讓它結束流程會把一份**已經完成且已經付費**的 AI 分析
整份丟掉。而內容不合約定這一類，與「為了一個沒照約定的 Merge Request 標題讓整份分析做不
出來」是同一種代價 —— 那是別人打的字，不是本次部署的錯誤。

後兩類發生時，報告中程式碼審閱那一段 SHALL 仍然出現，且 SHALL 顯示說明原因的訊息。已經
取得的附件資訊（日期、作者、連結）SHALL 照常顯示。

理由：連結在這些情況下的價值最高 —— 讀者點進去就能自己看全文，而這正是這一段設計的目的。

訊息 SHALL 可與真正的審閱內容區分，MUST NOT 讓讀者把它當成審閱意見。

#### Scenario: 關鍵字未設定

- **WHEN** 總表附件的檔名關鍵字未設定
- **THEN** 該步驟回報失敗，整條流程結束並顯示錯誤訊息框
- **AND** 訊息同時點名該環境變數與設定檔中對應的鍵
- **AND** 沒有產出報告

#### Scenario: 沒有 JIRA key 時仍檢查部署缺漏

- **WHEN** 總表附件的檔名關鍵字未設定，而該 Merge Request 的標題中沒有 JIRA key
- **THEN** 該步驟仍回報失敗
- **AND** 失敗不因「這次本來就不需要取得附件」而被略過

#### Scenario: 議題系統的憑證未設定

- **WHEN** 議題系統的端點或存取權杖未設定
- **THEN** 該步驟回報失敗，整條流程結束

#### Scenario: 議題系統連線失敗

- **WHEN** 議題系統無法連線或請求逾時
- **THEN** 該步驟回報成功
- **AND** 報告中程式碼審閱那一段出現，內容說明無法取得的原因
- **AND** 後續步驟照常執行

#### Scenario: 存取權杖被拒

- **WHEN** 議題系統以認證或授權失敗拒絕該次請求
- **THEN** 該步驟回報成功，報告中那一段顯示該原因

#### Scenario: 指定的議題不存在

- **WHEN** JIRA key 的格式有效，但該議題在議題系統上不存在
- **THEN** 該步驟回報成功，報告中那一段說明找不到該議題

#### Scenario: 下載失敗時連結仍然可用

- **WHEN** 附件清單取得成功，但該附件的內容下載失敗
- **THEN** 報告中那一段仍顯示該附件的日期、作者與連結
- **AND** 另外顯示下載失敗的訊息

#### Scenario: 訊息不會被當成審閱內容

- **WHEN** 報告中程式碼審閱那一段顯示的是失敗訊息
- **THEN** 讀者可由該段內容辨識出這不是審閱意見

### Requirement: 程式碼審閱的產物結構

取得程式碼審閱報告那一步 SHALL 產出一份帶版本的**結構**，MUST NOT 產出已經排好版的
markdown。渲染 SHALL 由合併為 markdown 那一步負責。

該結構 SHALL 至少包含：附件的檔名、上傳時間、上傳者、可連回該附件的網址、擷取到的表格，
以及失敗訊息。

理由：報告要印出附件的日期、作者與連結，而那些值只有這一步拿得到；合併那一步收到的只有
一個檔案路徑。把它們寫進結構，兩步之間就不需要額外的轉送，而呼叫端也不必多傳參數。這與
AI 分析的產物是同一套作法 —— 結構是唯一的真相，markdown 是它的呈現。

版本 SHALL 由入口腳本標記，MUST NOT 由任何被呼叫的實作自行填寫。

渲染端 SHALL 依版本決定如何讀取；認不得的版本 SHALL 明確失敗，MUST NOT 自行猜測。版本的
比對 SHALL 容許數值與純數字字串的差異。

該步驟未產生任何產物時（沒有 key、key 無效、沒有符合的附件），合併那一步 SHALL 表現為
「沒有這一段」，而非一個空的段落。

#### Scenario: 結構含有渲染所需的全部欄位

- **WHEN** 該步驟成功取得並擷取到總表
- **THEN** 產物中含有檔名、上傳時間、上傳者、網址與表格內容

#### Scenario: 版本由入口標記

- **WHEN** 檢視該步驟落下的產物
- **THEN** 它帶有正確的版本號

#### Scenario: 認不得的版本

- **WHEN** 合併那一步讀到的程式碼審閱結構版本不是它認得的
- **THEN** 該步驟回報失敗，訊息指出讀到的版本與實作認得的版本

#### Scenario: 版本寫成字串

- **WHEN** 結構的版本欄位是與目前版本相同的純數字字串
- **THEN** 該結構被正常渲染

### Requirement: 報告中程式碼審閱那一段的版面

合併為 markdown 那一步 SHALL 依程式碼審閱的結構渲染出該段落，版面依序為：段落標題、
附件的日期／作者／連結三行、總表的小標題、表格本身。

段落標題 SHALL 與 AI 分析那一段**同層**，MUST NOT 低於它。

理由：AI 分析那一段的內容本身使用低一層的標題。程式碼審閱若採用同樣的層級，在畫面上會
與那些內容並列，讀起來就是 AI 分析的一部分 —— 而它在語意上與分析並列，不從屬於它。

日期 SHALL 取自附件的上傳時間，並 SHALL 以日期呈現。作者 SHALL 為上傳者的顯示名稱，
MUST NOT 使用電子郵件位址。連結的文字 SHALL 為附件的檔名，其位址 SHALL 連回該附件。

附件的檔名進入連結文字時 SHALL 被轉義。理由：檔名是上傳者打的字，其中的方括號或圓括號
會讓那一行的連結失效。

段落標題與總表的小標題 SHALL 由這一步寫出，產生內容的那一步 MUST NOT 自行寫出它們。

在來源文件中尋找總表那一節所用的標題，與寫進報告的小標題 SHALL 為**兩個各自獨立的常數**，
MUST NOT 合為一個。

理由：兩者的職責不同 —— 一個是在別人的文件裡搜尋的依據，一個是本工具報告的版面。改動任何
一邊都不該牽動另一邊。這與 AI 分析那一段的標題情況相反：那一個同時是寫出與切回的同一個
邊界，因此必須只有一份來源。

程式碼審閱那一段 MUST NOT 影響原始描述的切段：切出原始描述的邊界仍 SHALL 只有 AI 分析
那一段的標題。理由：程式碼審閱永遠位於 AI 分析之後，切段時連同它一併被切掉，因此把報告
貼回描述再重跑不會累積。

#### Scenario: 段落的版面與順序

- **WHEN** 成功取得並擷取到總表
- **THEN** 報告中依序出現段落標題、日期／作者／連結三行、總表的小標題與表格

#### Scenario: 段落標題與 AI 分析同層

- **WHEN** 報告同時含有 AI 分析與程式碼審閱兩段
- **THEN** 兩段的標題階層相同
- **AND** 程式碼審閱那一段不低於 AI 分析那一段的內容所用的階層

#### Scenario: 檔名含括號

- **WHEN** 附件的檔名中含有方括號或圓括號
- **THEN** 報告中那一行的連結仍然有效

#### Scenario: 貼回描述後重跑不累積

- **WHEN** 使用者把一份含有程式碼審閱那一段的報告貼回 Merge Request 的描述，之後再執行一次分析
- **THEN** 新報告中程式碼審閱只有一段
- **AND** 原始描述中不殘留上一輪的程式碼審閱內容

#### Scenario: 沒有這一段時不留空區塊

- **WHEN** 該次分析沒有取得程式碼審閱報告
- **THEN** 報告中不含程式碼審閱那一段的標題，也不含任何佔位文字

### Requirement: 分析流程的對外契約與 AI 端點缺失時的行為

分析流程五個步驟的腳本 SHALL 完整實作對外契約：標準輸出只有一個結果 JSON、診斷與進度
走錯誤輸出、結束碼、參數與設定鍵的宣告、必填檢查、設定模板傾印、以及標準輸入與檔案兩
種投遞方式。

五個步驟的外部依賴 SHALL 為：步驟 1 取得描述與步驟 2 取得相關資訊連線 GitLab；步驟 3
AI 分析連線 GitLab（取得差異）、議題系統（取得議題內容）與 AI 服務；步驟 4 取得程式碼
審閱報告連線議題系統（取得附件）；步驟 5 合併為 markdown 沒有任何外部依賴。

未設定 AI 端點時，AI 分析那一步 SHALL 產出替代內容而非失敗，且該內容 SHALL 於首行言明
未經過 AI。

理由：開發期常常還沒有可用的端點，而整條流程需要能跑完才驗得到。但一份看起來正常、
實際上沒問過 AI 的報告，比一個錯誤訊息糟得多。

本能力的每一支腳本 SHALL 自功能腳本範本複製後改寫。

#### Scenario: 契約可被獨立驗證

- **WHEN** 開發者對本能力的任一支腳本執行說明、傾印模板、檔案投遞與標準輸入投遞
- **THEN** 四種操作都成功
- **AND** 兩種投遞方式都回傳 `result` 為 `PASS` 的結果

#### Scenario: 未設定 AI 端點仍可跑完整條流程

- **WHEN** 使用者在未設定 AI 端點、但 GitLab 存取權杖有效的環境中執行一次分析
- **THEN** 五個步驟皆成功
- **AND** 報告中 AI 分析那一段的首行言明未經過 AI

#### Scenario: 腳本自範本複製

- **WHEN** 檢視任一支新增的腳本
- **THEN** 它保有範本的版本號常數
- **AND** 它保有範本中設定模組搜尋路徑的那一段，因此可在未設定任何模組搜尋路徑的情況下直接執行

### Requirement: Merge Request 種類的抽出

流程 SHALL 為每一次分析解析出該 Merge Request 的**種類**，並 SHALL 以 device 的鉤子
進行，使判斷規則可因產品線而異。

理由：各條產品線的標題約定各自演化 —— 一條看第二個方括號、另一條看第三個。把規則寫死在
共用的腳本裡，等於要求所有產品線先達成共識。

抽出 SHALL 與抽出 JIRA key 在**同一個步驟**進行，MUST NOT 為此新增流程步驟或新增一次
對 GitLab 的取得。

理由：兩者解的是同一份 Merge Request 的同一個標題。分成兩步會讓同一筆 MR 被取得三次。

鉤子 SHALL 收到與抽出 JIRA key 的鉤子相同的欄位。

抽出的結果 SHALL 一律轉為小寫後比對。

理由：目錄名一律小寫（見「種類的名稱規則」），而標題裡寫的是 `[NewTestCase]` 這種給人
看的形式。

鉤子 SHALL 得以把標題中的寫法映射為不同的名稱。

理由：標題可能寫 `[FW-Update]`，而目錄名必須是合法的識別字。映射由該 device 決定，標題
長什麼樣是各產品線自己的約定。

#### Scenario: 不同 device 有不同的抽出規則

- **WHEN** 兩個 device 分別宣告自標題第二與第三個方括號抽出種類
- **THEN** 同一份標題在兩個 device 下解析出不同的種類

#### Scenario: 與 JIRA key 同一次取得

- **WHEN** 一次分析執行完畢
- **THEN** 該 Merge Request 被取得的次數與未加入種類之前相同

#### Scenario: 大小寫

- **WHEN** 標題中的種類寫作 `NewTestCase`
- **THEN** 解析出的種類為 `newtestcase`

### Requirement: 種類的名稱規則

種類的名稱 SHALL 與 device 的名稱適用同一套規則：小寫英數與底線、不以數字開頭。

理由：種類對應到一個目錄，而該目錄會被當成模組匯入。

以底線開頭的目錄 MUST NOT 被視為種類。

抽出的字串不符合該規則時 SHALL 視同沒有抽出種類，MUST NOT 另外回報「名稱不合法」。

理由：那是 Merge Request 作者打的字，不是部署者的錯誤。兩者的後續處理相同（見「認不得的
種類」），分開回報只會多一種使用者無法行動的訊息。

#### Scenario: 不合法的字串

- **WHEN** 鉤子自標題抽出含有空白或非英數字元的字串
- **THEN** 該次分析視同沒有種類

#### Scenario: 底線開頭的目錄

- **WHEN** 列出某個 device 目前認得的種類
- **THEN** 以底線開頭的目錄不出現在清單中

### Requirement: 種類只在自身 device 之內解析

因種類而異的鉤子 SHALL 依序尋找：該 device 底下該種類的實作、該 device 底下的實作、
預設 device 的實作。

系統 MUST NOT 尋找「預設 device 底下該種類的實作」。

理由：各 device 的種類字彙互相獨立且各自演化，同一個名稱在兩個 device 下不保證是同一件
事。跨 device 尋找同名的種類，會在字彙撞名時套用另一條產品線的邏輯 —— 而每一個步驟都會
回報成功。這與「未知的 device 必須失敗」要避免的是同一種失敗。

附帶的結果是解析順序沒有任何模稜兩可之處：少了那一段，就不需要裁決「自身的通用實作」與
「預設的種類實作」孰先。

跨 device 的共用 SHALL 以明確的匯入達成，MUST NOT 由回退機制隱含提供。

理由：明確匯入時，是撰寫者自己決定要用哪一份。

#### Scenario: 種類有專屬實作

- **WHEN** 某 device 底下存在該種類的 AI 分析實作
- **THEN** 使用該實作

#### Scenario: 種類沒有專屬實作

- **WHEN** 某 device 底下存在該種類的目錄，但其中沒有報告版面的實作
- **THEN** 使用該 device 的報告版面實作；該 device 也沒有時使用預設 device 的

#### Scenario: 不跨 device 尋找種類

- **WHEN** 某 device 沒有某種類的實作，而預設 device 有同名種類的實作
- **THEN** 使用該 device 的通用實作或預設 device 的通用實作，MUST NOT 使用預設 device
  的該種類實作

### Requirement: 認不得的種類

抽不到種類、抽出的字串不合法、或該 device 底下沒有該種類的目錄時，系統 SHALL 使用該
device 的通用實作，MUST NOT 回報失敗 —— 除非該 device 宣告了嚴格模式。

理由：device 的名稱來自設定檔，打錯是操作者的責任，因此未知的 device 必須失敗。種類則
來自 Merge Request 的標題 —— 那是任何能開 MR 的人打的字。為了一個沒照約定的標題讓整份
分析做不出來，等於把工具的可用性綁在他人的打字習慣上。

device SHALL 得以宣告要求每一筆 Merge Request 都解析出認得的種類；未宣告時 SHALL 視為
不要求。

理由：「Merge Request 一定要標明種類」是一條團隊紀律，而紀律是各條產品線自己的事。全域
的開關會迫使字彙都不共用的兩條產品線在這件事上達成一致。定義字彙的人正是知道那些種類
該不該強制的人。

該宣告 MUST NOT 為必填。

理由：設為必填會讓每一個既有的 device 立刻失效，而預設值有一個明確且安全的選擇。

#### Scenario: 未宣告嚴格模式

- **WHEN** 標題中的種類在該 device 底下沒有對應的目錄，而該 device 未宣告嚴格模式
- **THEN** 分析以該 device 的通用實作完成

#### Scenario: 既有的 device 不受影響

- **WHEN** 某個 device 沒有任何種類目錄，也未宣告嚴格模式
- **THEN** 其行為與加入種類機制之前完全相同

### Requirement: 嚴格模式的範圍與時機

宣告了嚴格模式的 device SHALL 在解析不出認得的種類時回報失敗。

該檢查 SHALL 在抽出種類的那一步進行，MUST NOT 延後到後續步驟。

理由：在任何 AI 花費之前失敗。一個打錯的標題不該先付一次費用才被告知。

嚴格模式 SHALL 只針對「種類本身認不認得」，MUST NOT 要求種類目錄提供所有鉤子。

理由：否則新增一個種類就必須放齊所有鉤子，而逐項回退正是為了避免那種複製。

失敗訊息 SHALL 區分「沒有宣告種類」與「宣告了認不得的種類」，且後者 SHALL 列出該 device
目前認得哪些種類。

理由：兩者的下一步不同 —— 一個是去補標題，一個是去確認名稱或新增目錄。而由於沒有中央
的種類清單，錯誤發生的當下正是使用者需要那份清單的時刻。

#### Scenario: 沒有宣告種類

- **WHEN** 某 device 宣告嚴格模式，而某筆 Merge Request 解析不出種類
- **THEN** 該步驟回報失敗，訊息指出這筆 Merge Request 沒有宣告種類
- **AND** 失敗發生在任何 AI 呼叫之前

#### Scenario: 宣告了認不得的種類

- **WHEN** 某 device 宣告嚴格模式，而標題中的種類在該 device 底下沒有對應目錄
- **THEN** 該步驟回報失敗，訊息列出該 device 目前認得哪些種類

#### Scenario: 嚴格模式不要求放齊鉤子

- **WHEN** 某 device 宣告嚴格模式，而某個種類目錄中只有部分鉤子
- **THEN** 缺少的鉤子照常回退，分析完成

### Requirement: 種類隨分析結果傳遞

解析出的種類 SHALL 由抽出它的那一步產出，並 SHALL 由 AI 分析那一步寫入分析結構。

合併為 markdown 那一步 SHALL 自分析結構讀取種類以解析自己的鉤子，MUST NOT 另行取得。

理由：種類因此被記入產物，可用於報告的出處與其他消費者；而圖形介面只需要把它從一步轉送
到下一步一次。

種類 SHALL 由入口腳本寫入，鉤子 MUST NOT 自行填寫。

理由：與結構版本同一個理由 —— 讓鉤子填寫，複製範本時遲早有人忘記。

分析結構中沒有種類時 SHALL 視為沒有種類並使用通用實作，MUST NOT 回報失敗。

理由：與結構版本的寬鬆比對一致，使舊的產物仍可被渲染。

報告末尾的出處資訊 SHALL 包含種類。

#### Scenario: 種類進入分析結構

- **WHEN** 一次分析解析出種類
- **THEN** 分析結構中含有該種類

#### Scenario: 合併那一步自產物取得種類

- **WHEN** 合併為 markdown 那一步執行
- **THEN** 它使用分析結構中的種類解析自己的鉤子

#### Scenario: 舊的分析結構

- **WHEN** 合併為 markdown 那一步讀到不含種類的分析結構
- **THEN** 使用該 device 的通用版面，流程成功

### Requirement: 由 Merge Request 內容選擇實作的界線

系統 SHALL 允許由 Merge Request 的內容決定套用哪一個種類的實作，此為「執行哪一段運算不
取自回傳資料」的明確例外。

該例外 SHALL 受兩項限制：名稱必須通過名稱規則的檢查，且必須對應到一個**已經部署在該
device 底下**的目錄。

理由：Merge Request 的標題是任何能開 MR 的人打的字。上述兩項限制使它只能在既有的選項
之間挑選，MUST NOT 引入任何未部署的程式碼，也 MUST NOT 指向該 device 以外的位置。

#### Scenario: 名稱無法指向其他位置

- **WHEN** Merge Request 的標題中含有路徑分隔字元或上層目錄的寫法
- **THEN** 該字串不通過名稱規則，視同沒有種類

#### Scenario: 只能挑既有的選項

- **WHEN** Merge Request 的標題宣告了一個未部署的種類
- **THEN** 系統回退或失敗，MUST NOT 載入任何其他位置的實作
