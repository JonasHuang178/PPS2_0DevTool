## Why

外殼目前只能執行單一支腳本。要讓一個 button 依序跑多支腳本（跑 `a.py` 拿結果、由 Qt 依結果組出參數、再跑 `b.py`，最後一次更新介面），唯一的寫法是在前一支的 callback 裡啟動下一支。這條路走得通 —— `PythonRunner::finish()` 在呼叫 callback 之前就把 `m_state` 歸零，所以串接會成功 —— 但外殼的兩項資源被綁在「單次腳本執行」上，串接會直接壞掉：

- **處理中對話框每執行一支腳本就重建一次。** `pps2_0devtool.cpp:172-177` 每次 `runFunctionScript()` 都 `delete` 後 `new ProcessingDialog` 並 `show()`，`:195-199` 每次結束都 `hide()` 後 `deleteLater()`。跑 N 支腳本，使用者就看到處理中視窗出現、消失 N 次 —— 在 Windows 上 `hide()` 會立即走 `ShowWindow(SW_HIDE)`，是真正的視窗閃爍、焦點重奪與工作列跳動，不是理論風險。
- **耗時計時器每執行一支腳本就重跑一次。** `m_runTimer.start()` 在 `pps2_0devtool.cpp:153`。整條流程跑三分鐘，`showResultDialog()` 拿到的 `elapsedMs` 只有最後一支腳本的時間。

另有一個誤用陷阱：在同一個 slot 裡連續呼叫 `runFunctionScript()` 兩次，第二次會因 `PythonRunner::start()` 的忙碌守衛（`PythonRunner.cpp:58`）回傳 false，而依 `script-execution` 的「一次只執行一支腳本」需求，這種情況**刻意不顯示訊息框**。結果是第二支腳本靜默地沒有執行，畫面看起來完全正常。這條「安靜」的設計建立在「一個 button 只跑一支腳本」的前提上，前提一旦被打破，防呆就變成陷阱。

腳本合併不是解法：本專案的腳本要能各自獨立被其他功能與命令列使用，刻意不綁在一起。因此流程編排放在 Qt 端。

## What Changes

**新增流程執行介面**

- 外殼新增多步驟流程的執行介面。功能提供一個「決定下一步」的函式，外殼負責依序執行並維護流程狀態。
- 流程長度不固定，步驟也不預先列出：每執行完一步，外殼把**目前為止所有已完成步驟的結果**交給功能，由功能回答「執行某一步」或「流程結束」。功能因此可以依前一步的結果組裝下一步的參數、跳過某一步、或改走別的分支。
- 外殼 MUST NOT 依成敗自行決定是否繼續 —— 某步失敗時同樣詢問功能，由功能決定要結束還是執行補救步驟。這讓外殼在支援分支流程的同時，自身仍不含任何判斷邏輯。

**資源所有權從「單次執行」搬到「整條流程」**

- 處理中對話框改為整條流程共用一個：流程開始時建立、流程結束時銷毀，步驟之間只更新文字，MUST NOT 重建。
- 對話框顯示兩層文字：功能提供的步驟名稱，以及腳本經 stderr 回報的階段文字。
- 耗時改為自流程開始計到流程結束。
- 現有的 `runFunctionScript()` 成為「只有一步的流程」，讓對話框、計時器、取消三者只有一份實作。

**明確化 Qt 與 Python 的分工邊界**

- 既有分工（`README.md:19` 的職責表）已把「組裝參數」列為 Qt 的職責，「不該做的事」列的是解析檔案格式、呼叫外部 API、產生報表、做 AI 分析。本次把流程編排明確歸入 Qt 端職責，並同時把界線寫成需求：**單一步驟的業務運算仍 MUST 在腳本內完成**。
- 這是澄清邊界，不是推翻原則。外殼本身仍不含業務邏輯 —— 決策函式由功能提供，不在外殼裡。

**已知的代價（明列，不隱藏）**

- 流程的分支判斷寫在 C++，因此**整條流程無法從命令列重現**，只能開 GUI 驗證。個別腳本仍可獨立以 `--request-stdin` 執行。
- 取消或失敗時介面完全不變（沿用既有保證），但**已完成步驟造成的外部副作用不會還原**。這一點會寫成需求並要求腳本可重入，避免使用者把「取消」理解為「什麼都沒發生」。

## Capabilities

### New Capabilities

（無）

### Modified Capabilities

- `script-execution`: 新增多步驟流程的執行、決策、對話框、耗時、分工邊界與副作用語意等需求；並修訂「一次只執行一支腳本」、「執行期間顯示可取消的處理中對話框」、「取消」、「介面僅在成功後變更」四條，使其在多步驟流程下語意明確

## Impact

- **修改檔案**：`pps2_0devtool.h` / `pps2_0devtool.cpp`（新增流程介面、對話框與計時器所有權搬移、`runFunctionScript()` 改走流程路徑）、`ProcessingDialog.h` / `ProcessingDialog.cpp`（步驟名稱與階段文字兩層顯示）、`README.md`（職責表與流程章節）
- **不修改**：`PythonRunner.h` / `PythonRunner.cpp` —— 單步執行、取消、輸出解析的行為完全不變，流程狀態機建在它之上而非改寫它
- **不修改**：`json.cpp` —— 步驟若需覆寫 `Program`（例如兩步跑在不同的 Python 環境），由功能自己從自己的設定區塊取值後填入步驟，外殼不解讀 `Function` 底下的任何鍵
- **不修改**：`scripts/` 下的任何腳本與信封協定 —— 流程的每一步都是一次符合現有協定的普通執行
- **相依**：不新增。流程狀態機以現有的 `PythonRunner` 與 Qt 訊號機制實作
- **建置**：不新增檔案，`.pro` 的 `SOURCES` / `HEADERS` 不需異動

## Non-goals

- 不做並行執行 —— 「一次只執行一支腳本」維持不變，流程內的步驟一律依序
- 不做步驟層級的取消（取消一律終止整條流程）
- 不做副作用回捲或補償機制 —— 補救步驟若有需要，由功能自行編排
- 不改變腳本的信封協定，也不放寬 stdout 的整段解析規則
- 不把流程定義搬進設定檔 —— 流程寫在功能的程式碼裡，不做設定驅動的流程引擎
