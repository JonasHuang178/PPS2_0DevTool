## Context

動機見 `proposal.md`「Why」；需求見 `specs/script-execution/spec.md`。這裡只記錄實作上的取捨。

塑造這份設計的三項既有事實：

1. **`PythonRunner` 的單步語意是所有既有保證的來源。** 它以單一狀態（Idle / Running / Cancelling）管理一次執行，取消時不呼叫 callback —— 這是「取消後畫面完全不動」的物理保證。這個保證不依賴功能作者正確地寫出取消分支，改寫它風險最高、收益最低。
2. **`PythonRunner::finish()` 的呼叫順序已經支援串接。** `m_state` 在 `emit runFinished()` 與 `callback()` 之前就歸零，所以在 step callback 裡啟動下一步會成功。但 `runFinished` 排在 callback **之前**，代表外殼在收到 `runFinished` 的當下還不知道流程是否要繼續 —— 這是本設計必須繞開的核心時序問題。
3. **目前沒有任何功能存在。** `setupToolService()` 是空的（`pps2_0devtool.cpp:50`）。`runFunctionScript()` 沒有任何呼叫端，因此改動它的內部實作不會破壞任何既有程式碼。

## Goals / Non-Goals

**Goals:**

- 流程狀態機建在 `PythonRunner` 之上，`PythonRunner.h` / `PythonRunner.cpp` 一行都不改
- 對話框、耗時、取消三者只有一份實作，單步與多步共用
- 外殼不含任何流程判斷，判斷全部由功能提供的決策函式承擔

**Non-Goals:**

- 不改變單步執行的任何外部行為（信封、環境變數、輸出解析、取消時序）
- 不在外殼引入「總步數」的概念 —— 流程長度不定，外殼無從得知
- 不做設定驅動的流程引擎（見 `proposal.md`「Non-goals」）

## Decisions

### D1：以「決策函式」而非「步驟清單」表達流程

**選擇**：功能提供一個 `std::function`，外殼每完成一步就呼叫它一次，帶入依序排列的所有已完成結果，由它回答「執行某一步」或「流程結束」。

**替代方案（已否決）**：啟動時傳入 `QList<FlowStep>` 靜態清單，每個 step 各帶一個組裝參數的 builder。

**理由**：需求方明確表示流程長度不固定，且下一步要**依前一步結果做判斷**（可能跳過某步、可能改走別的分支）。靜態清單只能表達「參數依賴」，無法表達「路徑依賴」；要補上就得額外加入 skip 條件、跳轉目標等欄位，等於在資料結構裡重新發明控制流。決策函式是一個 callback，控制流就用 C++ 的控制流寫，反而更小。

**代價**：外殼不知道總步數，因此無法顯示「2/5」。改由功能自己把序號寫進步驟名稱（例如 `"步驟 2/2：產生報表"`）。外殼原樣顯示，不解讀。

### D2：外殼不判斷成敗，失敗也交給決策函式

**選擇**：步驟回傳失敗結果時，外殼照樣呼叫決策函式，由功能決定結束或執行補救步驟。

**替代方案（已否決）**：外殼實作 fail-fast，遇到失敗自動終止流程。

**理由**：fail-fast 看似安全，但它是一項業務決策 —— 「這一步失敗了要不要繼續」只有功能知道。把它放進外殼，外殼就有了判斷邏輯，且第一個需要「失敗後補救」的功能就會被迫繞過整套機制。讓外殼一律轉交，外殼的職責退化為純粹的排程器。

**例外**：步驟**啟動前**的失敗（腳本不存在、找不到 Python）不轉交，直接顯示錯誤訊息框並結束流程。理由記於 spec —— 這類失敗是部署問題，補救步驟解決不了，轉交只會讓每個功能重寫一次相同的處理。

### D3：對話框的關閉時機 —— 繞開 `runFinished` 的時序問題

`PythonRunner::finish()` 先 `emit runFinished()` 再 `callback()`，所以外殼在 `runFinished` 的當下無法得知流程是否結束。

**選擇**：外殼維護流程狀態（是否有流程進行中、是否已被取消），並拆開兩條路徑：

```
  正常結束路徑（有結果）
  ------------------------------------------------------------
  PythonRunner::finish()
      emit runFinished()  --> 外殼：流程進行中且未取消 -> 什麼都不做
      callback(result)    --> 流程狀態機：
                                 累積結果
                                 呼叫決策函式
                                 +-- 回答「執行下一步」-> 啟動下一步（對話框不動）
                                 +-- 回答「流程結束」  -> 收對話框、呼叫流程 callback

  取消路徑（無結果）
  ------------------------------------------------------------
  使用者按取消 -> 外殼標記「流程已取消」-> PythonRunner::cancel()
  PythonRunner::finish()
      emit runFinished()  --> 外殼：流程已取消 -> 收對話框、不呼叫流程 callback
      （callback 不被呼叫，決策函式因此永遠不會被問到）
```

**替代方案（已否決）**：修改 `PythonRunner::finish()`，把 `emit runFinished()` 移到 `callback()` 之後。這樣外殼在 `runFinished` 時就知道結果了。否決理由：`runFinished` 的契約是「不論成敗或取消都要通知外殼收掉對話框」，把它移到 callback 之後會讓取消路徑與正常路徑的時序不再一致，且要動到本設計刻意不碰的檔案。

**替代方案（已否決）**：在 `runFinished` 裡不關對話框，改由一個 0ms 的延遲判斷。否決理由：延遲判斷會讓事件迴圈跑一輪，在步驟交界處製造出沒有互斥遮罩的空窗 —— 那正是本次要修掉的問題之一。

**下一步採同步啟動**：決策函式回答「執行下一步」後，在同一個呼叫堆疊裡直接啟動。此時 `PythonRunner` 的 `m_state` 已是 Idle、`m_process` 已置空（`teardownProcess()` 先於 `emit`），啟動安全。同步啟動意味著步驟之間事件迴圈不跑，對話框自然不會有任何閃動 —— 這也是本設計不需要中間重繪的原因：中間結果本來就不上畫面。

### D4：單步執行實作為「只有一步的流程」

**選擇**：`runFunctionScript()` 保留現有簽章，內部改為建立一條只有一步的流程。

**替代方案（已否決）**：保留兩條獨立的程式路徑。

**理由**：對話框所有權、耗時起訖、取消語意這三件事若有兩份實作，一定會漂移 —— 修了流程路徑的 bug，單步路徑上還在。目前 `runFunctionScript()` 沒有任何呼叫端，是做這個統一的最低成本時機。

**相容性**：外部簽章不變，之後新增的功能可以繼續只用單步介面，不必認識流程概念。

### D5：兩層文字用「標題列 + 標籤」承載，不動對話框版面

`QProgressDialog` 只有一個 `labelText`。

**選擇**：步驟名稱寫進對話框標題列（目前放的是功能名稱），腳本回報的階段文字仍寫進 `labelText`。只有一步的流程，標題就是功能名稱 —— 與現況完全相同。

**替代方案（已否決）**：把兩層文字合成多行字串塞進 `labelText`。否決理由：`QProgressDialog` 會隨標籤內容重新計算大小，多行字串在步驟切換時造成視窗尺寸跳動，換掉一種閃爍又換來另一種。

**替代方案（已否決）**：在對話框裡加自訂 widget 承載步驟名稱。否決理由：`ProcessingDialog` 目前刻意只做三件事（禁 Escape、立即顯示、取消後不關閉），加版面會擴大它的職責，而標題列已經是現成且不佔版面的第二層。

**附帶**：切換步驟時 `labelText` 重設為初始文字，避免新步驟的對話框上還留著上一步最後回報的階段文字。

### D6：耗時計時器改由流程持有

`m_runTimer.start()` 從 `runFunctionScript()`（`pps2_0devtool.cpp:153`）移到流程啟動處，`elapsed()` 於流程結束時讀取一次並放進流程結果。步驟切換時不觸碰計時器。

功能不再需要自己記錄時間，`showResultDialog()` 的 `elapsedMs` 直接用流程結果帶回來的值。

### D7：步驟的直譯器覆寫由功能填入，外殼不讀設定鍵

若兩步需要跑在不同的 Python 環境，步驟結構帶一個可選的直譯器欄位；留空則沿用該功能設定區塊的既有欄位。

**理由**：外殼一旦去讀 `Step_A_Program` 之類的鍵，就違反了「`Function` 物件 MUST NOT 被逐欄位解析」（`app-shell` 既有需求）。讓功能自己從自己的設定區塊取值再填進步驟，`json.cpp` 完全不用改，設定檔的形狀也繼續由功能自己決定。

## Risks / Trade-offs

- **流程的分支判斷寫在 C++，整條流程無法從命令列重現** → 個別步驟仍可獨立以 `--request-stdin` 執行，因此「單步做錯了什麼」仍可在命令列查。無法命令列驗證的只剩「步驟之間的接線」。緩解：把接線壓到最薄 —— 決策函式只做挑欄位、改名、讀 UI 值與分支判斷，任何計算、過濾、聚合一律推進腳本（已寫成 spec 需求）。

- **前一步的資料要繞經 Qt 再序列化進下一步的 stdin** → 資料量大時（數萬筆）會有可觀的序列化成本與記憶體佔用。緩解：資料量大的情境，讓上游步驟把結果寫成檔案、只在 `data` 裡回傳路徑，下一步以路徑取用。這是腳本設計層的作法，外殼不需要知道。

- **同步啟動下一步 = 步驟之間事件迴圈不跑** → 若日後有人在決策函式裡呼叫任何會轉動事件迴圈的東西（`QMessageBox::exec()`、`QFileDialog`、`processEvents()`），主視窗會在該期間被那個巢狀迴圈接管。緩解：對話框此時仍然存在且仍是 application-modal（不像改動前會被關掉），互斥遮罩不會消失；但決策函式內不應該有使用者互動 —— 這一點寫進實作註解與 README。

- **取消時已完成步驟的副作用不還原** → 已寫成 spec 需求，並要求參與流程的腳本可重入。這是架構解不掉的問題（Python 端串一樣如此），只能靠明說與腳本設計，避免使用者把「取消」理解為「什麼都沒發生」。

- **決策函式的生命週期** → 它捕捉功能物件的指標，而流程是非同步的。若功能在流程進行中被銷毀，回呼會落到已釋放的物件上。緩解：流程期間主視窗被互斥遮罩鎖定，使用者無法觸發 tab 移除或功能銷毀；`removeTabByTitle()` 只在 `UI_Init()` 啟動階段呼叫。實作時仍以功能物件為 parent 建立流程狀態，讓銷毀時能一併中止。

## Migration Plan

不涉及資料或設定格式，也沒有既有呼叫端需要遷移：

1. 先做 `ProcessingDialog` 的標題／標籤兩層文字，單獨可驗證（現有單步行為不變）
2. 再把對話框與計時器的所有權搬到流程狀態機，`runFunctionScript()` 改走流程路徑
3. 最後開放流程介面

回退策略：三步都在同一份程式碼內，任一步出問題可直接 revert 該次提交；`PythonRunner` 未被修改，單步執行的既有保證不受影響。
