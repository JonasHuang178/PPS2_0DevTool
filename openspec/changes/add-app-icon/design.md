## Context

見 [proposal.md](proposal.md) 的 Why。此處只記錄影響技術取捨的現況與限制。

**現況**：`main.cpp` 未呼叫 `setWindowIcon()`；`PPS2_0DevTool.pro` 沒有 `RESOURCES` 也沒有 `RC_ICONS`；`pps2_0devtool.cpp:94` 的系統匣圖示寫成「`windowIcon()` 為空就退回 `SP_ComputerIcon`」，因此目前恆走 fallback。

**來源圖檔**：256x256、8-bit RGBA、非交錯 PNG。經逐像素檢查，**alpha 通道全為 255**，四角為 `(253,254,254)` 至 `(254,254,254)`，也就是圖案被畫在一塊接近純白的不透明方形上。圖案本身包含**白色的閃光符號與墨鏡反光**，這一點決定了去背方法（見 D3）。原圖已隨本 change 一起提交於 `assets/app_icon_original.png`。

**技術限制**：Qt5 + qmake，Windows 端 Qt Creator + MinGW；macOS 僅用於確認編得過。Windows 專屬的建置設定不能讓 macOS 端編不過。

**使用者已確認的決定**：

1. 背景去除為透明。
2. 圖示套用範圍包含 Windows 執行檔本身。
3. 程式碼改用**執行期載入**，讓日後換圖不必重新建置。
4. exe 本身的圖示採內嵌（連結期）方式 —— 這一項技術上無法執行期載入，見 D10。
5. 外部圖檔缺失時回退到內嵌的預設圖。

## Goals / Non-Goals

**Goals:**

- 換掉視窗與系統匣的圖示只需要放檔案並重啟，不需要重新建置
- 圖檔不見時程式仍有圖示可顯示 —— 外部圖檔是「覆寫」而不是「必需品」
- 三處（視窗／對話框、系統匣、執行檔）預設用的是同一組圖示，換內嵌預設時只需重跑一次產生腳本
- 不新增建置期相依：Windows 端拿到 repo 用 Qt Creator 開啟即可建置，不需要安裝 Python 影像套件

**Non-Goals:**

- 不重繪圖案、不調整構圖與配色
- 不做熱重載 —— 換檔後需重啟程式
- 不提供改寫已編譯執行檔 PE 圖示資源的機制
- 不做 macOS bundle 的 `.icns`（macOS 非支援平台）

## Decisions

### 一、資產產生

**D1 去背後產生多尺寸點陣圖，不使用單張大圖縮放。**

Qt 在只有一個尺寸可用時會即時縮放，256 直接縮到 16x16 會讓貓臉的條紋與墨鏡糊成一團。改為在產生階段以高品質重採樣（Lanczos）產出 16 / 24 / 32 / 48 / 64 / 128 / 256 七個尺寸，各自存成獨立 PNG。

此規則約束的是**內嵌預設**。使用者放進外部資料夾的圖示接受單一尺寸 —— 那是他自己的取捨（見 D6）。

*替代方案*：改用 SVG 向量圖示。不採用 —— 手上只有點陣原圖，重新描邊等於重繪；且 Qt 的 SVG 支援需要額外模組，違反「不新增相依」。

**D2 資產是提交進 repo 的產物，不在建置期產生。**

產生腳本 `tools/make_app_icon.py` 需要 Pillow。若放進建置流程，Windows 端建置就必須先裝 Python 影像套件 —— 本專案的執行期已經要求使用者機器有 Python 3，建置期再加一層相依只會讓「開啟 .pro 就能建置」不再成立。

*作法*：腳本手動執行，產物（PNG 與 `.ico`）提交進 repo。腳本存在的意義是「換內嵌預設或 exe 圖示時可重現」，不是建置步驟。

**D3 去背用四邊 flood fill，不用全域「白色即透明」。**

圖案內含白色的閃光符號與墨鏡反光。若以「亮度高於門檻就設為透明」的全域規則處理，這些白色區域會被打成透明破洞，在深色背景下直接漏底。

*作法*：從影像四邊的邊界像素開始，對「與背景色差異在容差內」的像素做連通區域填充，只有**與邊界連通**的白色才會被去掉；被圖案包圍的白色閃光因為不連通而完整保留。

*邊緣處理*：原圖的圖案外緣是抗鋸齒像素（介於橘色與白色之間）。硬性二值化會留下一圈白邊，在深色背景上非常明顯。因此對邊界區域依「與背景色的接近程度」換算出部分 alpha，讓縮小後的邊緣仍然乾淨。

*驗收方式*：把產出的 16x16 與 32x32 分別疊在純黑與純白背景上目視檢查 —— 白邊與破洞在這兩個背景上一眼可見。

**D4 `.ico` 的內部格式：小尺寸用 BMP、256 用 PNG 壓縮。**

這是 Windows Vista 之後的標準作法，也是 Pillow 儲存 ICO 時的預設行為。256x256 若以未壓縮 BMP 存放，單一項目就要 256KB。

*取捨*：PNG 壓縮的項目在 Windows XP 上不顯示。XP 不在支援範圍，接受。

### 二、執行期載入

**D5 外部圖檔優先，內嵌預設回退。**

使用者要的是「不重建就能換圖」。作法是啟動時掃描外部資料夾，有就用、沒有就用內嵌的。

*為什麼保留內嵌*：純外部檔案會讓圖示變成第三個「掉了就壞掉」的部署項目 —— 本工具已經有設定檔與 `scripts/` 兩個。設定檔掉了程式會直接結束（那是刻意的），但圖示掉了不該有任何後果。內嵌一份的成本是幾十 KB，換到的是「圖檔是覆寫而非必需品」。

*代價*：執行檔略大，且換內嵌預設仍需重建。可接受 —— 換內嵌預設是罕見動作，日常換圖走外部資料夾。

**D6 外部圖示以「全有全無」取代內嵌，不混用。**

這是本次最容易做錯的一條。若把外部找到的檔案「補進」內嵌的 `QIcon`，使用者只丟一張 256 進去時，`QIcon` 在 16x16 仍會選中內嵌的舊圖 —— 結果是標題列顯示新貓、系統匣顯示舊貓，而且看起來像 bug 而非設定問題。

*作法*：外部資料夾中找到**至少一個**可用圖檔時，整個 `QIcon` 只由外部檔案組成；一個都沒有才用內嵌那組。

*代價*：使用者只放 256 時，系統匣的 16x16 由 Qt 即時縮放，比內嵌那組糊。這是他自己選的取捨，而且是可預期的；混用造成的新舊圖並存則不可預期。README 中說明「想要小尺寸銳利就多放幾個尺寸」。

**D7 搜尋位置為 `<執行檔目錄>/icons/`，樣式為 `app_icon*.png`。**

放在執行檔旁的子資料夾，與既有的 `scripts/` 同一個層級和心智模型 —— 使用者已經知道「東西放執行檔旁邊」。

*為什麼用萬用字元而不是固定檔名*：使用者放一張 `app_icon.png` 可以動，想要多尺寸時放 `app_icon_16.png`…`app_icon_256.png` 也可以動，不需要記住特定檔名規則。`QIcon::addFile()` 讀的是檔案的實際像素尺寸，檔名裡的數字只是給人看的，因此掃描順序不影響結果。

*為什麼限定 PNG*：PNG 的讀取內建於 QtGui。若允許 `.ico`，Qt 需要 `qico` 影像格式外掛，部署時得一併帶上 `imageformats/qico.dll` —— 又多一個掉了就壞掉的項目。

*為什麼要前綴*：直接掃 `*.png` 會把使用者順手丟進去的其他圖也當成圖示。

**D8 設定圖示的時機：`main.cpp` 中緊接 `setApplicationVersion()` 之後。**

`main.cpp` 在建立主視窗之前就可能顯示三個 `QMessageBox`（重複啟動、設定檔錯誤、找不到 Python 3）。圖示若晚於這些設定，這些訊息框會頂著預設圖示出現 —— 而它們正是使用者最可能第一次看到本程式的時機。

*與 `Debug::init()` 的時序衝突*：`Debug::init()` 必須等讀完設定檔才知道 `Debug_Mode`，因此排在圖示設定之後。圖示載入時 console 尚未開啟。

*為什麼仍然照記*：`Debug::write()` 一律先寫入 300 行環形緩衝，只有 console 輸出受 `Debug_Mode` 控制（見 `debug.cpp` 的 `appendToRing` 與 `printToConsole`）。因此圖示來源的診斷訊息不會遺失 —— 它會進緩衝，並在 SIGSEGV 時出現在 `crash.log` 中。console 上看不到這一則是已知且可接受的。

**D9 系統匣不改任何程式碼。**

`QWidget::windowIcon()` 在 widget 本身未設定圖示時回傳應用程式圖示。因此 D8 完成後，`setupTrayIcon()` 中 `windowIcon().isNull()` 自然為假，直接走正式分支。

*fallback 保留*：`SP_ComputerIcon` 那一支留著。它現在是死路，但成本為零。

*驗證重點*：這一條是「不改程式碼卻預期行為改變」的推論，必須在 Windows 上實際看過系統匣圖示才算數 —— 本專案先前正是在系統匣這裡吃過一次「以為會動、其實靜默失效」的虧（見 `archive/2026-09-07-bootstrap-devtool-shell` 的 7.6），而 offscreen 平台的 `isSystemTrayAvailable()` 回 false，自動測試碰不到這段。

### 三、Windows 執行檔

**D10 exe 的檔案圖示只能內嵌，這是平台限制而非設計選擇。**

`PPS2_0DevTool.exe` 在檔案總管、捷徑、開始功能表與釘選狀態下顯示的圖示，來自 PE 檔案的資源區段，由 windres 在連結期寫入。執行中的程式無法改變自己在磁碟上的圖示資源。因此**這一項不受外部圖檔影響**，換圖需重新建置。

執行中的工作列按鈕、Alt-Tab 切換器與標題列則來自視窗圖示，屬 D5 的範圍，換外部檔案即可改變。這個分界必須寫進 README，否則使用者換了外部圖檔卻發現檔案總管沒變，會以為功能壞了。

**D11 用 qmake 的 `RC_ICONS`，不手寫 `.rc`。**

`RC_ICONS = resources/icons/PPS2_0DevTool.ico` 一行即可，qmake 會產生資源檔並交給 windres 嵌入。手寫 `.rc` 得自己管理資源 ID 與編碼，沒有好處。

*非 Windows 平台*：qmake 在非 Windows 平台忽略 `RC_ICONS`，因此**不需要條件式包裝**，macOS 端照樣編得過。

**D12 一併補上 `VERSION` 與 `QMAKE_TARGET_*`。**

一旦設定 `RC_ICONS`，qmake 產生的資源檔會同時帶入 VERSIONINFO 區塊。不設定的話版本會是 qmake 的預設值，與 `version.h` 的 `v2.0.0` 對不上 —— 使用者在檔案內容頁看到的版本會和 About 對話框顯示的不同。因此設定 `VERSION = 2.0.0`、`QMAKE_TARGET_PRODUCT`、`QMAKE_TARGET_DESCRIPTION`、`QMAKE_TARGET_COMPANY`，與 `version.h` 的 `TOOL_NAME` / `TOOL_VERSION` 保持一致。

*注意*：`VERSION` 只在函式庫專案影響輸出檔名；本專案 `TEMPLATE = app`，`TARGET` 不受影響。

### 四、檔案配置

repo 中：

```
IconLoader.{h,cpp}                    執行期圖示載入（外部優先、內嵌回退）
resources.qrc                         Qt 資源清單（前綴 :/icons）
resources/icons/
├── src/app_icon_original.png         使用者提供的原圖（含白底，保留供重新產生）
├── app_icon_{16,24,32,48,64,128,256}.png   去背後的多尺寸圖（進 .qrc）
└── PPS2_0DevTool.ico                 多尺寸 ICO（給 RC_ICONS，不進 .qrc）
tools/make_app_icon.py                資產產生腳本（非建置步驟）
```

部署後：

```
<執行檔目錄>/
├── PPS2_0DevTool.exe
├── PPS2_0DevTool.json     ← 缺少會跳訊息框後結束（既有行為）
├── scripts/               ← 既有行為
└── icons/                 ← 選用；缺少時回退內嵌預設
    └── app_icon*.png
```

`.ico` 不放進 `.qrc`：Qt 讀 ICO 要靠 `qico` 影像格式外掛，PNG 則內建於 QtGui。Qt 端一律吃 PNG，`.ico` 只給 windres 用。

`IconLoader` 獨立成一個檔案而不是塞進 `main.cpp`：它有可測試的邏輯（掃描、篩選、全有全無的取捨），而 `main.cpp` 目前是一連串啟動檢查，混進去會讓兩邊都難讀。

## Risks / Trade-offs

- **去背容差抓錯會留白邊或咬掉圖案外緣**（D3）→ 以「與邊界連通」為條件而非全域門檻，並在 16x16 與 32x32 上分別疊黑底與白底目視檢查。這是本次唯一需要人眼判斷的環節。
- **使用者換了外部圖檔，卻發現檔案總管中的 exe 沒變**（D10）→ 這是平台限制，不是缺陷。緩解方式是文件：README 用表格明確列出哪些位置換檔即改、哪些需要重建。
- **使用者只放單一尺寸，系統匣圖示偏糊**（D6）→ 可預期且由使用者自己決定；README 說明多放幾個尺寸即可。比起混用造成的新舊圖並存，這是較輕的代價。
- **Windows 圖示快取導致更新後仍顯示舊的 exe 圖示** → 已知的系統行為，非程式缺陷。驗證時若遇到，複製執行檔到新路徑再看。此點寫進任務的驗證註記，避免被誤判為實作失敗。
- **D9 推論「不改程式碼即生效」** → 若 Qt 版本行為與預期不符，退路是在 `setupTrayIcon()` 明確設定圖示。實際驗證前不預先加，避免看不出是哪一條在生效。
- **圖示來源的診斷訊息在 console 上看不到**（D8）→ 訊息仍進環形緩衝並會出現在 crash.log。若日後需要在 console 看到，可在 `Debug::init()` 之後補印一次來源摘要。
- **`.ico` 的 256 項目在 Windows XP 不顯示**（D4）→ XP 非支援平台，接受。

## Migration Plan

無資料遷移。使用者重新取得建置後的執行檔即生效。

既有部署目錄不需要調整 —— `icons/` 是選用項目，不放也能正常執行。

Windows 端首次建置後若檔案總管仍顯示舊圖示，屬圖示快取，非需要處理的缺陷。

無。背景處理方式、套用範圍、載入方式與回退行為皆已由使用者確認。
