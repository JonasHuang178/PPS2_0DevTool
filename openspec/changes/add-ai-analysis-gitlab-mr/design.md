## Context

AI Analysis GitLab MR 是本工具的第二個功能，也是第一個需要對外部服務認證、第一個畫面上有表格、第一個真正用到多步驟流程機制的功能。前一個 change 建立的流程機制（`runFunctionFlow` 與決策函式）到目前為止只被「只有一步的流程」走過，這次是它第一次承載五個步驟。

功能的形狀大致沿用使用者在既有工具中已經寫過的一份實作（同步、以命令列參數呼叫 Python、以檔案路徑在步驟之間傳遞資料）。本設計的主要工作，是把那份實作對齊本專案既有的契約：非同步流程、信封走 stdin、通道分離、Qt 不含業務邏輯。

本 change 交付**完整的 Qt 側與腳本的完整契約**。取得 Merge Request 清單那一支腳本為真實實作（真的連線至 GitLab）；分析流程五步的業務內臟以 stub 實作（回傳寫死的假資料）。

## Goals / Non-Goals

**Goals:**

- 使用者能在工具中選定一個 GitLab repo 與一個 Merge Request，對它執行一條五步的 AI 分析流程，並在結果視窗看到產出的 markdown
- 跨功能共用的服務端點與憑證在設定檔中只有一份來源
- 同一批腳本能被 Qt 與 CI/CD 的 bash 以相同方式呼叫，且編排邏輯不重複實作
- 憑證不出現在行程的命令列上
- 完整走通流程機制的多步路徑：步驟切換、兩層文字的進度、取消、失敗即停

**Non-Goals:**

- **分析流程五步實際連線到 GitLab / AI 供應商 / JIRA**。這五支本次為 stub，回傳符合契約的假資料，真實實作留給後續 change。取得 Merge Request 清單那一支**不在此列**，它本次即為真實實作
- `handler` 的實際 dispatch 內容（步驟 3 / 5 內部要如何依 `handler` 選擇處理方式）
- 批次分析（一次多個 repo 或多個 MR）
- mockup 中另外三個分頁（`Log Info`、`AI Analysis Code`、`Generate CSV`）
- Source Path 列上那顆額外的圖示鈕

## Decisions

### 一、設定檔新增工具層級 Service 區塊

**決定**：外殼認得的工具層級欄位由三個增為四個，新增 `Service` 存放跨功能共用的服務端點與憑證。`Service` 與 `Function` 一樣整包保留、不做任何解析。

**理由**：GitLab 與 JIRA 會被日後多個分頁共用。若每個功能區塊各抄一份 token，使用者換 token 時漏改一處的症狀是 401 —— 而 401 的第一直覺是「token 過期了」，於是去重發一把新的，找錯方向。這與 `script_io` 註解記載過的舊坑同類。

**替代方案**：

- 每個功能區塊各自抄一份：即上述漂移問題
- 功能區塊寫引用（`${Service.Gitlab_Access_Token}` 這類語法）：要求外殼讀值、認語法、做代換，直接違反「外殼不解析 `Function` 底下任何鍵」

### 二、Service 以「併進 config」的方式送達腳本，合併點在 getFunctionConfig()

**決定**：`Config::getFunctionConfig()` 回傳「`Service` 併上該功能區塊」的結果，同名鍵以功能區塊為準。信封的 `config` 因此自動變成合併後的物件。

**理由**：腳本端與信封格式完全不用改 —— `script_io.py`、`--dump-config` 的模板、既有的四支 Single Building 腳本都不需要修改。而且 Qt 側也需要讀 `Service`（`AI_Mode_List` 在那裡，下拉選單要用），合併在查詢介面裡一次解決兩個需求，`pps2_0devtool.cpp` 的組信封程式碼一行都不用動。

功能區塊優先的理由是讓個別功能能指向不同的伺服器。

**替代方案**：信封多一個 `service` 欄位 —— 協定是加法式的所以可行，但要動到 `script_io.parse_request()` 這個所有腳本共用的地基，風險最高，收益只是語意上更分明。

### 三、isFunctionVisible() 仍讀原始的功能區塊

**決定**：只有 `getFunctionConfig()` 回傳合併結果；`isFunctionVisible()` 讀 `Function` 底下的原始區塊。

**理由**：否則哪天有人在 `Service` 放了 `Visible`，所有「沒設 `Visible`」的功能會從「預設隱藏並記警告」變成「全部顯示」。那條預設隱藏的規則存在的目的，正是讓漏設定的功能不要靜默跑出來。

### 四、json.h 的硬性規則改寫，但牙齒保留

**決定**：原文「新增一個功能不得修改這個檔案」改為「新增一個功能不得修改這個檔案，新增一個共用服務的鍵也不得修改這個檔案；只有在新增一整個工具層級區塊時才需要改它」。

**理由**：那條規則防的是「把每個功能的每個欄位寫死在這裡解析」—— 舊版就是那樣爛掉的。加一個整包不解析的 `Service` 區塊，性質與現行對 `Function` 的處理完全相同。改完之後，新增第三、第四個功能依然不需要碰 `json.cpp`。

### 五、憑證：值留在 JSON，由功能注入環境變數，腳本只讀環境變數

**決定**：

- `Gitlab_Server_URL` / `Gitlab_Access_Token` / `Jira_Server_URL` / `Jira_Access_Token` 的**值**放在 `Service`
- 功能在組每一個 `FlowStep` 時，把這四項注入為環境變數（鍵名全大寫：`GITLAB_ACCESS_TOKEN` 等）
- 腳本**只從環境變數讀**，不從 `config` 讀
- CI/CD 自行設定同名的環境變數

**理由**：腳本端只有一條讀取路徑，Qt 與 bash 對它來說長得一模一樣。這正是「同一批腳本服務兩個呼叫端」最省的做法。機制也已經存在 —— `PythonRunner::start()` 收 `envVars`、`FlowStep` 有 `envVars` 欄位、規格寫著「功能 SHALL 可再疊加自己的環境變數」，因此外殼零改動。

鍵名到變數名的對應採機械化的「全大寫」規則，不另外維護一張對照表。

**已知的不一致**：AI 的 `Api_URL` / `Api_Key` / `Model` 改走 `params` 而非環境變數（使用者的選擇）。兩者都不上命令列，但 CI 端要記得兩種都設。

**替代方案**：設定檔只存環境變數的名字 —— Qt 完全碰不到憑證，更安全；但使用者要在 JSON 與系統環境兩個地方維護，且 Windows 上改環境變數需重開工具才生效。使用者選擇把值留在 JSON。

**這是有意識的取捨**：憑證因此會經過 C++ 的變數，也仍會出現在信封的 `config` 裡（外殼不解讀也就無從剔除）。連帶的紀律是腳本**不得整包 log 出 `config`**。

### 六、設定檔移出 git 追蹤

**決定**：`PPS2_0DevTool.json` 停止追蹤並加入 `.gitignore`；新增追蹤的 `PPS2_0DevTool.example.json`；建置的複製規則改為「執行檔旁已有設定檔就完全不動它，沒有才從範本生成一份」。

**理由**：現行規則每次建置無條件覆蓋執行檔旁那份。加入憑證之後，使用者只剩兩個選擇：填在執行檔旁（下次建置被蓋掉），或填在專案那份（`git status` 永遠顯示被改過，遲早 commit 上去）。

選擇「不存在才從範本生成」而非「完全不複製」，是因為它讓全新 clone 的第一次失敗從「程式直接結束、訊息是找不到檔案」變成「程式跑起來、腳本明確指出缺哪一把 token」—— 後者自己會教人下一步做什麼。

**已知代價**：新增的設定鍵不會傳播到既有部署。症狀由腳本層的必填檢查回報（指名道姓），可接受，但要寫進 README。另：Windows 的 shadow build 有 debug 與 release 兩個目的地，token 要填兩次。

此檔案自第一次 commit 起從未裝過任何憑證，因此不需要改寫 git 歷史。

### 七、主視窗 1200x830 改為 1280x830

**決定**：寬度加 80，高度不變，維持固定尺寸。

**理由**：MR 表格的欄位預算。固定欄（MR 60 / Author 110 / Created 90 / State 70）合計 330，加捲軸與框線約 20；左欄由 `Save Analysis file Path` 那一列決定，約 460。1200 之下 Title 只剩約 324px，中文標題看得到約 22 字；1280 之下是 404px、約 28 字。標題是使用者唯一用來認出「是哪一筆 MR」的欄位，被截掉的話這張表就退化成一行字的清單。

不再往上加是因為 1366x768 的筆電 —— 寬度塞得下，但高度 830 在那種螢幕上本來就超出可用高度，那是另一個更該先處理的問題。

### 八、清單選取樣式進外殼共用服務

**決定**：清單項目的選取樣式由外殼統一提供，且選取態**不因視窗焦點離開而變色**（同時指定 `:selected` 與 `:selected:!active`）。色值：底色 `#CCE8FF`、文字 `#042C53`、hover `#E5F3FF`。

**理由**：Windows 上焦點離開清單後，預設的選取高亮會退成很淡的灰色。本功能的操作順序每次都會踩到它 —— 選 repository、按重新整理、到表格挑 MR，三步之後使用者已經看不清楚自己選的是哪個 repo，而按下 AI Analysis 時真正生效的正是那一個。

色值選 Windows 檔案總管的選取藍：使用者每天在看不用學；黑字對比約 15:1；藍色系對紅綠色盲最安全，日後要加紅色狀態不會撞色。

放進外殼而非只套用於本功能，是因為問題不是本功能特有 —— 任何「有清單又有其他控件」的分頁都會遇到。副作用是 Single Building 的兩個清單外觀會改變（行為不變）。

### 九、分析單位是「一個 repo 的一個 MR」

**決定**：Repository 清單與 MR 表格皆為單選。

**理由**：畫面上「手動輸入 MR 編號」那條路徑本來就只能一筆，兩條路徑產出同一種輸入，後面的流程只需要處理一種情況。也讓 MR 表格不需要 Repository 欄，640px 的欄位預算才夠用。

日後若要批次，放寬 selectionMode 並加勾選欄是加法式的改動。

### 十、進入功能不執行任何腳本

**決定**：Repository 清單來自設定檔，於功能建立時填入；MR 清單一律由使用者按重新整理才取得。

**理由**：與 Single Building 的「進入即載入」相反。這裡每次載入都是一次網路請求，若照做，每次切到這個分頁都會彈出 application-modal 的處理中對話框並等待 GitLab 回應。畫面上那兩顆 refresh 鈕本來就暗示「手動才抓」。

### 十一、切換 repository 即清空 MR 清單

**決定**：切換 repository（或改動查詢條件）時清空 MR 表格並停用 AI Analysis，使用者必須重新取得。

**理由**：否則畫面上顯示的是 repo A 的 MR、選定的 repo 卻是 B，按下去就是拿 B 配 A 的編號。與 Single Building 的「來源路徑變更後重新開始」是同一類問題、同一種解法。

**替代方案**：清單記住自己屬於哪個 repo，不一致時只停用按鈕 —— 友善一些，但要多維護一個狀態。選擇簡單的那個。

### 十二、AI Analysis 停用時不解釋原因

**決定**：條件不足時按鈕停用，不加 tooltip、不加狀態文字。與 `SingleBuilding::updateButtonStates()` 的既有作法一致。

**已知代價**：`Save_Analysis_File_Dir` 若在設定檔中留空且 `Add Debug Analysis file` 為勾選，使用者第一次開啟會看到一顆灰按鈕且無從得知原因。緩解方式是在 `PPS2_0DevTool.example.json` 給一個有意義的預設值。

### 十三、五步流程固定執行，分支壓成參數

**決定**：流程固定五步，每一步都執行。「要不要真的做事」由腳本自己看參數決定（例如步驟 4 收到 `fetch_code_review=false` 時回一份空報告並回報成功）。

**理由**：這是「同一批腳本服務 CI」這個目標最重要的一個設計約束。規格已經承認「流程的分支判斷寫在 Qt 端，因此整條流程無法從命令列重現」。在只有 Qt 呼叫時那是可接受的代價；一旦 CI 也要跑同一條流程，那條 bash 就成為**第二份編排實作**，兩份必然漂移，症狀是「工具裡跑對、CI 跑出不一樣的報告」。

把判斷壓進腳本之後，Qt 的決策函式退化成「上一步失敗就結束，否則依已完成步驟數決定下一步」，CI 的 bash 就是照順序跑六行。判斷邏輯只有一份。

### 十四、步驟 3 / 5 的腳本路徑固定，handler 由 Python 內部 dispatch

**決定**：`script_info` 中的 `handler` / `source` / `path` 原樣往下傳給步驟 3 與 5 的 `params`，由腳本自己解讀。Qt 不依它決定要執行哪一支腳本。

**理由**：使用者原本的實作是「設定給了就用設定的路徑，設定留空才用 `script_info` 的路徑」—— 動態路徑只是後備。既然本專案把腳本路徑寫死在 C++（腳本是程式的一部分，不是使用者該調的東西），該後備永遠不會被觸發。

更關鍵的是，那兩行後備邏輯在既有實作中**已經寫錯過一次**：merge 步驟的判斷條件用了 summary 的路徑變數（複製上一個函式未改），四種組合中有兩種會選錯來源，而且錯的時候症狀是「找不到腳本」，直覺會去查設定檔。同樣的邏輯還要在 CI 的 bash 裡再寫一次。

把 dispatch 放進 Python，Qt 這側就沒有任何條件判斷可以寫錯。

**替代方案**：動態腳本路徑 —— 外殼支援（`FlowStep.scriptPath` 本來就每步由功能填），但要 CI 複製同一段邏輯，且會開出「腳本輸出的字串變成被執行的路徑」這條風險。若日後仍需要，收斂做法是「回名字不回路徑」，由 Qt 組成固定目錄下的檔名並驗證只含英數與底線。

### 十五、腳本的輸出入契約：data 必有、檔案選配、輸入內容優先

**決定**：

- **輸出**：結果一律放進 `data`；`params` 給了輸出路徑時**額外**落檔
- **輸入**：`params` 裡有內容就用內容；沒有內容但有路徑時讀該路徑

**理由**：bash 的原生貨幣是檔案，走 `data` 要靠 `jq` 拼 JSON 並處理引號逃脫；Qt 則希望完全不碰檔案系統。兩個呼叫端各走各的路，腳本只多一個判斷。這是規格中「協定 SHALL 為加法式」的直接應用。

**與既有規格的張力**：`script-envelope` 寫著「結果資料 SHALL 直接放在 `data` 中，MUST NOT 改為寫檔後回傳路徑」。本決定不違反它 —— `data` 依然一定有完整結果，檔案是額外的產物，而不是取代 `data` 的傳遞媒介。

**已知代價**：每支腳本多一條輸入路徑就是多一組要測的組合。付在腳本裡（有 `--request FILE` 可單獨測）比付在兩個呼叫端裡便宜。

### 十六、debug 目錄由 Qt 建立並傳入每一支腳本

**決定**：勾選 `Add Debug Analysis file` 時，Qt 在流程啟動前建立 `<Save_Analysis_File_Dir>/gitlab_mr_result_<repo>_<mr>_<時間戳>/`，並把絕對路徑放進每一步的 `params`；未勾選時傳空字串，腳本據此不寫任何檔案。

**理由**（使用者的選擇，與 Single Building「檔案一律由腳本存取」的先例不同，刻意記錄於此以免日後被「順手修正」）：

- 一個參數同時承載「在哪裡」與「要不要」，不會有「布林為真但路徑為空」的矛盾狀態
- 目錄建立失敗發生在任何工作開始之前 —— 路徑打錯或沒有寫入權限，在按下按鈕的當下就爆出來，不會等到跑完前三步、付完 AI 的錢才在第四步發現寫不進去
- 時間戳只產生一次，五個步驟因此寫進同一個目錄。若交給步驟 1 產生則需多一次資料傳遞；若各步驟自行產生，跨秒時會冒出兩個目錄，且是偶發的

路徑以 `QDir::absoluteFilePath()` 組合，不以字串串接分隔符號。目錄以 `mkpath()` 建立（`mkdir()` 只建一層）。

**已知代價**：流程被取消時會留下一個只有半截內容的目錄，外殼不清理。這符合規格明文的「流程不保證外部副作用的原子性」。

### 十七、未勾選 debug 時完全不寫檔，報告內容走 data

**決定**：最終 markdown 的內容一律放進步驟 5 的 `data`；勾選時**額外**寫一份檔案。結果視窗的內容一律取自 `data`。

**理由**：Qt 因此從不開檔，既有實作中的 `QFile` / `setCodec("UTF-8")` /「檔案不存在」三段處理全部消失。也讓那個 checkbox 真的有意義 —— 不勾就是整條流程零檔案。

### 十八、中間產物以序號前綴平鋪命名

**決定**：`01_description.md`、`02_script_info.json`、`03_summary.json`、`04_code_review.md`、`05_report.md`，全部直接放在 debug 目錄下，不再分子目錄。

**理由**：CI 撈 artifact 時檔名可預期；目錄列表的順序就是流程順序，出問題時一眼看出停在哪一步。既有實作在 summary 步驟另外建了一層 `summary/` 子目錄，平鋪之後不需要，Qt 也就只建最上層那一個。

### 十九、失敗即停，保留取消鈕

**決定**：任一步回報失敗即結束流程，由流程 callback 統一顯示一個錯誤視窗（內容用該步腳本寫的 `message`，位置用 `failedStepIndex`）。取消鈕維持現狀。

**理由（取消）**：使用者曾提出拿掉取消功能。保留的理由是代價不對稱 —— 拿掉之後，AI 那步若無回應，application-modal 的對話框永遠不關、主視窗永遠鎖著，而規格明文「MUST NOT 設執行逾時」，使用者唯一的出路是工作管理員。保留的代價只是「取消時已送出的 AI 請求可能照樣計費，而畫面完全不動」。保留同時是零改動。

若要緩解計費的疑慮，可在該步的步驟標籤寫明（標籤是功能自己填的字串，外殼不解讀）。

### 二十、取得 MR 清單為真實實作，流程五步為 stub

**決定**：

| 腳本 | 本次 |
|---|---|
| 取得 Merge Request 清單（重新整理鈕） | **真實實作** —— 真的連線至 GitLab |
| 流程五步 | stub —— 回傳寫死的假資料 |

六支的契約層面一律為真：stdout 只有結果 JSON、進度走 stderr、exit code、必填檢查、參數宣告、`--dump-config`、兩種投遞方式。

**理由**：stub 的那五支讓信封契約、流程編排、對話框、取消、失敗路徑能被端到端驗證，而不需要 AI 供應商的金鑰或費用。而取得 MR 清單那一支做成真的，是因為它一次驗證掉四件否則要等到下一個 change 才會知道對不對的事：

- `Repo_List` 採 `namespace/project` 字串是否足以識別專案（URL-encode 之後）
- 憑證經環境變數傳遞的整條路徑是否真的接通
- `script_utils/gitlab_utils/` 這個分組第一次有內容時的形狀
- 畫面上的查詢條件如何對應到 GitLab 的查詢參數

它同時是風險最低的一支：唯讀、單一端點、失敗了只是表格空著。

**理由（分界）**：界線畫在**契約 vs 業務運算**，剛好與本專案自己的分工邊界重合。Qt 這一側整個是真的；Python 那一側，契約是真的，流程五步的內臟是假的。

每支腳本一律從 `scripts/_function_template.py` 複製後改寫（既有規則，本次在 `tasks.md` 中逐支列為可勾選項目）。複製時不得刪除設定模組搜尋路徑的那一行，且須保留 `TEMPLATE_VERSION`。

### 二十一、GitLab 的 HTTP 呼叫以標準函式庫實作

**決定**：`script_utils/gitlab_utils/` 中的 REST 呼叫使用 Python 標準函式庫（`urllib.request`），不引入第三方套件。

**理由**：本專案目前沒有任何 Python 相依清單，`.pro` 的註解也寫明 Windows 端拿到專案用 Qt Creator 開啟即可建置、不需要安裝套件。引入 `requests` 會讓「安裝相依」變成部署與 CI 的新步驟，而這支腳本的需求只是一個帶標頭的 GET。

共用模組的既有四條規則同樣適用：不印 stdout、不結束行程、不自行讀環境變數或設定檔、回傳資料結構。權杖由入口腳本自環境變數取出後明著傳入。

### 二十二、取回筆數以固定上限 100 收斂

**決定**：取得 Merge Request 清單時以單次請求取回最多 100 筆，不跟著分頁連結往下翻。

**理由**：畫面上的表格是單選的 —— 使用者要從中挑出**一筆**。取回上千筆不會讓那個動作更容易，只會讓等待變長、讓表格更難掃。查詢條件（只取未關閉的、只取 N 天內建立的）本來就是為了把範圍縮到人看得完的大小；若 100 筆還不夠，正確的操作是調緊條件，而不是往下翻頁。

100 也剛好是 GitLab `per_page` 參數的上限，因此是一次請求就能拿到的最大值，不需要任何翻頁邏輯。

**已知代價**：條件寬鬆的大型 repo 會被截斷，而使用者看不出「這是全部」還是「被截斷了」。緩解方式是在取回筆數達到上限時，於清單旁或訊息中說明可能未完整。

### 二十三、TLS 驗證預設關閉

**決定**：GitLab 的 HTTPS 連線**預設不驗證伺服器憑證**。`Service` 提供 `Gitlab_Verify_SSL` 開關（字串 `"true"` / `"false"`，未設定時視為 `"false"`），由功能與既有四項一併注入為環境變數 `GITLAB_VERIFY_SSL`。

這是使用者明確的決定，理由是目標環境是否使用自簽憑證尚不確定，而驗證失敗會讓功能完全無法使用。

**已知代價，必須明白記錄**：關閉驗證時暴露的是**存取權杖本身**。任何能插入連線中間的人出示一張假憑證，腳本就會把權杖送過去，而 GitLab 的 personal access token 通常帶 API 寫入權限。在公司內網這個風險較低，但不是零；而且關閉狀態下，被攔截時沒有任何徵兆。

**保留開關而非寫死的理由**：一，行為看得見 ——「我們沒有驗證憑證」寫在設定檔裡，而不是藏在程式碼中讓所有人被迫接受且無人察覺。二，可逐台機器、逐環境調整，日後確認目標環境其實有正規憑證時，把它改成 `"true"` 即可，不需要重新建置。

**日後要改回驗證時**：多數自簽情境不需要關閉驗證 —— Python 的 `urllib` 遵守 `SSL_CERT_FILE` 環境變數，把公司的 CA 憑證指過去就能正常驗證。屆時把開關設為 `"true"`、設定該環境變數即可，程式碼不需要改。

**範圍**：本次只加 GitLab 的開關。JIRA 尚未有真實連線，依本專案「宣告了卻永遠不會觸發的東西是陷阱」的原則，等它真的要連線時再加對應的鍵。

## Risks / Trade-offs

| 風險 | 緩解 |
|---|---|
| 憑證仍在信封的 `config` 裡，腳本若整包 log 出來會寫進 debug console | 範本與 README 明列「不得 log 整包 `config`」；腳本只從環境變數讀憑證 |
| 既有部署的設定檔不會長出新鍵，使用者看到「缺少必填項目」 | 訊息本身指名道姓；README 說明升級後對照 `PPS2_0DevTool.example.json` 補鍵 |
| Windows shadow build 有 debug / release 兩個目的地，token 要填兩次 | 無解，寫進 README |
| `Save_Analysis_File_Dir` 留空導致按鈕開箱即灰且不解釋 | `PPS2_0DevTool.example.json` 給有意義的預設值 |
| 取消或失敗時留下半完成的 debug 目錄 | 規格已明文流程不保證外部副作用原子性；目錄名含時間戳，不會互相覆蓋 |
| 五步流程的編排在 CI 需要一份 bash，兩份可能漂移 | 決策十三把所有分支壓進參數，使兩邊都是固定六步的線性呼叫 |
| Single Building 的外觀因視窗變寬與選取樣式而改變 | 行為不變；納入本 change 的驗收項目 |
| 改了環境變數後 Windows 不會推送給執行中的行程 | 本次憑證由 Qt 自 JSON 注入，不受此影響；僅 CI 端需注意 |
