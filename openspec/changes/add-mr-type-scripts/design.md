## Context

`add-device-specific-scripts` 已經讓每條產品線可以替換三個鉤子（`jira_key`、`summary`、
`merge_to_md`），由環境變數 `PPS_DEVICE` 選擇，缺的鉤子逐項回退到 `default`。

這一輪要加的是**第二個軸**：同一個 device 底下，不同種類的 MR 要走不同的 `summary` 與
`merge_to_md`。兩個軸的性質不同：

```
            誰決定        來源              變動頻率     信任程度
  device    操作者 / CI   設定檔 / 環境變數   幾乎不變     操作者自己填的
  type      MR 的作者     MR 的標題等         每一筆都不同  任何能開 MR 的人打的字
```

「信任程度」那一欄是本設計最多決定的來源。現有規格有一條明文：**腳本路徑固定寫死在
C++，不取自任何步驟的回傳資料；哪一段運算因 device 而異由環境變數決定，同樣不取自回傳
資料。** 種類打破了後半句 —— 它來自 MR 標題，而它要決定載入哪一個模組。

## Goals / Non-Goals

**Goals:**

- 同一個 device 底下，可依 MR 的種類替換 `summary` 與 `merge_to_md`
- 判斷種類的規則本身可因 device 而異
- 各 device 的種類字彙互相獨立，不需要任何跨產品線的共識
- 不新增流程步驟，不增加 GitLab 的取得次數
- 沒有種類子目錄的既有 device 行為完全不變

**Non-Goals:**

- 加寬交給鉤子的 MR 欄位（目前只看標題就夠，未來需要 label 再議）
- 跨 device 的種類共用（要共用就明著 import，見決策六）
- 讓 `jira_key` 或步驟 4 因種類而異
- 全域強制宣告種類的開關（見決策八）

## Decisions

### 一、種類是 device 的第四個鉤子，不是第六個流程步驟

判斷種類的規則因 device 而異 —— SSD 讀標題第二個方括號、SD 讀第三個。這正是 device 鉤子
存在的形狀，與 `jira_key.py` 完全對稱：兩者解的是同一個標題、由同一次 GitLab 取得餵進去、
在同一步執行。

替代方案是新增一支 `mr_type.py` 作為第六個流程步驟。否決理由：

| | 新增步驟 | 併入步驟 2 |
|---|---|---|
| GitLab 取得次數 | 再多一次（已經有兩次，規格列為已知代價） | 不變 |
| Qt | 新常數、新產物名、步驟數、新 case、兩處參數轉送 | 一行 |
| 規格 | 「固定五步」要改 | 不動 |

「每個 device 有自己取種類的 .py」這個需求，由 `device/<name>/mr_type.py` 滿足，不需要
它同時是一個流程步驟。

### 二、種類只在自己的 device 之內解析（三段回退）

```
  summary / merge_to_md 的解析：

    <device>/<type>/   ->   <device>/   ->   default/
    這個種類的專屬版           我的通用版         最後的後備
```

**刻意不放 `default/<type>/` 這一段。** 各 device 的字彙獨立演化，SSD 的 `bug` 與 SD 的
`bug` 不保證是同一件事；跨 device 去找同名的種類，等於在兩套字彙撞名時安靜地套用另一條
產品線的邏輯 —— 而每一步都會回報成功。這正是「未知的 device 要報錯」當初要避免的失敗
形狀。

副作用是好的：少了那一段，**就沒有優先序需要裁決**。四段回退必須回答「我的通用版與別人
的種類版誰優先」，而兩種答案都講得通 —— 講得通的兩種優先序，就是之後每個人都會搞錯的
地方。

### 三、`jira_key` 與 `mr_type` 兩個鉤子不因種類而異

它們在種類被決定**之前**執行（`mr_type` 就是決定它的那一支），所以種類這一層對它們沒有
意義。兩者維持現有的兩段解析：`<device>/` → `default/`。

結論是鉤子分成兩類，規格與範本都要講明白：

```
  不因種類而異    jira_key.py   mr_type.py        <device>/ -> default/
  因種類而異      summary.py    merge_to_md.py    <device>/<type>/ -> <device>/ -> default/
```

### 四、認不得的種類預設回退，但由 device 自己決定

device 與 type 在這件事上**相反**：

```
  未知的 device  ->  錯誤。名字來自設定檔，打錯是操作者的責任，而靜默改用通用邏輯
                     會產出一份用錯邏輯、每一步卻都回報成功的報告。

  未知的 type    ->  回退。名字來自別人寫的 MR 標題。為了一個沒照約定的標題讓整份
                     分析做不出來，是把工具的可用性綁在別人的打字習慣上。
```

但「MR 一定要標種類」是一條**團隊紀律**，而紀律是各條產品線自己的事。因此開關掛在
device 上，而不是全域：

```python
# device/ssd/__init__.py
VERSION = "1.2"
STRICT_TYPE = True      # 抽不到或認不得就失敗
```

未宣告視為 `False`。與 `VERSION` 不同，它**不是必填** —— 設成必填會讓每一個既有的 device
立刻壞掉，而預設值有一個明確且安全的選擇。

定義字彙的人正是知道那些種類該不該強制的人，這也是它掛在 device 上而不是設定檔的理由。

### 五、嚴格檢查在步驟 2，且只管種類本身

檢查放在步驟 2 抽出種類的當下，不是步驟 3 解析鉤子的時候 —— **在任何 AI 花費之前失敗**。
標題打錯不該先付一次錢才被告知。

嚴格只管「抽出來的種類認不認得」，**不管鉤子缺檔**。`ssd/bug/` 底下只有 `summary.py`
時，`merge_to_md` 照常回退到通用版，即使 `STRICT_TYPE = True`。否則開一個種類目錄就得
放齊所有鉤子，而逐項回退正是為了避免那種複製。

兩種失敗訊息分開寫，因為使用者的下一步不同：

```
  抽不到      「這筆 MR 沒有宣告 type，而 device ssd 要求宣告」
  認不得      「device ssd 認不得 type 'refactor'，目前認得的是：bug、newtestcase」
```

### 六、跨 device 的共用要明著 import

per-device 字彙的代價是可能重複：兩條產品線的 Bug prompt 若有八成相同，兩份會各自漂移。

解法是讓共用成為一個**明確的動作**，而不是回退鏈偷偷幫忙接上：

```python
# device/ssd/bug/summary.py
from ai_analysis_gitlab_mr.device.default.bug import summary as base
```

明著寫的話，是作者自己決定「我要用那一份」；靠回退接上的話，撞名就會安靜地跑錯。日後
共用真的變常見，再開一個 `device/_shared/`（底線開頭不算 device，與 `_template` 同一個
規則）。

### 七、種類隨分析結構傳遞，步驟 5 不經 Qt 取得

```
  02_mr_info.json   { "jira_key": ..., "mr_type": "bug" }
        |
        |  Qt 轉送（新增的那一行）
        v
  03_summary.json   { "schema_version": 4, "analysis": { "mr_type": "bug", ... } }
                                                              |
                                                              |  步驟 5 讀這份檔案
                                                              v
                                                        解析 merge_to_md
```

步驟 5 從產物讀而不是由 Qt 再轉送一次，有兩個好處：Qt 只需要改一行；種類被記進產物，
因此可以印在報告的出處，也留給其他消費者。

由**入口腳本蓋章**而不是鉤子自己填，與 `schema_version` 同一個理由：讓鉤子填，複製範本
時遲早有人忘記。

版本自 3 提升為 4。步驟 5 讀到沒有 `mr_type` 的舊結構時視為沒有種類、走通用版 —— 與
版本比對的寬鬆原則一致。

### 八、不加全域強制種類的環境變數

`STRICT_TYPE` 已經覆蓋「這條產品線要求宣告種類」。再加一個環境變數讓 CI 全域強制，會出現
兩個機制與它們的交互（全域開、device 關，聽誰的？）。目前沒有已知的需求，等真的出現再議。

### 九、種類的名稱規則沿用 device 的

小寫英數與底線、不以數字開頭（`^[a-z_][a-z0-9_]*$`），因為目錄名會被當成模組名 import。
抽出來的字一律轉小寫比對，`[NewTestCase]` 對到 `newtestcase/`。底線開頭的目錄不算種類，
與 `_template` 一致。

鉤子因此也負責**映射**：標題寫 `[FW-Update]`、鉤子回 `fw_update`。目錄名維持合法識別字，
標題長什麼樣是各產品線自己的約定。

不合法的字串（`[緊急]`、`[bug fix]`）視同抽不到，走決策四 —— 不另外報「名稱不合法」，
因為那是 MR 作者的打字，不是部署者的錯誤。

### 十、範本的 `__init__.py` 以註解列出所有可宣告的項目

```python
VERSION = "1.0"          # 必填

# 底下都是選填，拿掉註解才生效。

# STRICT_TYPE = False    # True = 抽不到 type 或認不得時直接失敗
```

理由：這些名稱沒有別的地方會提示。要用的時候得去翻文件或讀載入器的原始碼，而那是一個
每次都要付、且很容易讓人直接放棄的成本。

## Risks / Trade-offs

**[MR 標題影響載入哪一個模組]** 現有規格明文「不取自回傳資料」，而種類打破了這一點。
→ 風險有界：名稱必須通過 `^[a-z_][a-z0-9_]*$`（擋掉路徑穿越），且必須對應到一個**已經
部署在該 device 底下**的目錄，否則回退或失敗。也就是說，MR 標題只能在既有的選項之間挑，
不能引入任何新的程式碼。這一點要寫進規格，作為對原本那條規則的明確例外，而不是默默做。

**[多一個鉤子就多一個漏寫的機會]** SD 寫了 `mr_type.py`（第 3 個方括號）卻忘了寫
`jira_key.py`，就會沿用 `default` 的第 1 個方括號規則，安靜地抽到錯的 key。
→ 症狀看得見（報告印 `JIRA: Alpha (invalid)`），但要看報告才看得見。逐鉤子回退本來就有
這個性質，不是新問題；緩解是在範本與文件明講「標題格式與 default 不同的 device，兩個
鉤子通常要一起寫」。

**[種類目錄增加會讓重複悄悄長出來]** 五個種類各一份 `summary.py`，共同的部分會被複製
五次。
→ 決策六給了明確的共用方式；而在真的長出來之前不預先抽象。

**[字彙沒有中央清單]** 沒有任何一個地方寫著「系統認得哪些種類」。
→ 這是刻意的（決策二），代價是要知道有哪些種類只能去看目錄。錯誤訊息會列出該 device
目前認得哪些，那是使用者真正需要的時刻。

## Migration Plan

沒有破壞性變更，不需要遷移步驟。

- 既有 device 沒有種類子目錄 → 解析鏈第一段直接跳過，行為與現在完全相同
- 既有 device 沒有 `mr_type.py` → 回退到 `default/mr_type.py`
- 既有 device 沒有宣告 `STRICT_TYPE` → 視為回退，與現在的行為相同
- 既有的 `03_summary.json`（版本 3）→ 步驟 5 視為沒有種類

Qt 需要重新建置（一行參數轉送）。在重新建置之前，腳本更新後步驟 3 收不到 `mr_type`，
於是一律走通用版 —— 降級而不是失敗。

## Open Questions

- 交給鉤子的 MR 欄位是否要加寬（`labels` 最可能需要）。本輪確認暫時不需要，等實際的
  判斷規則定下來再議。
- 五個種類以上時，共同的 prompt 片段要不要有 `device/_shared/`。等真的出現再開。
