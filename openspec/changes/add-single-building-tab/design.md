## Context

見 `proposal.md` — Why。此處只記錄影響實作取捨的既有條件。

外殼與腳本執行管線已完成，本次是第一個真實走過它的功能。管線上有幾項硬性條件：

| 條件 | 來源 | 影響 |
|---|---|---|
| `PythonRunner` 一次只執行一支腳本（Idle / Running / Cancelling 單一狀態） | `PythonRunner.h` | 需要接續執行的動作必須串接，不能並行 |
| 每次執行都彈出 modal 的 `ProcessingDialog` 並鎖住主視窗 | `ProcessingDialog.h` | 載入不是背景動作，是會打斷使用者的事件 |
| 取消時功能的 callback 不會被呼叫 | `PythonRunner.h` | 「取消後畫面完全不動」是免費的，但串接時要自行中止後續 |
| 結果信封的 `data` 是 JSON 物件，不是陣列 | `PythonRunner::PythonRunnerResult` | 清單必須包在一個鍵底下回傳 |
| 信封的 `source_path` 由外殼自動填入 | `pps2_0devtool.cpp` `runFunctionScript()` | 腳本不需要、也不應該由 params 另外接收來源路徑 |
| 來源路徑由 `QFileDialog::getExistingDirectory` 選取 | `pps2_0devtool.cpp` `onBrowseSourcePath()` | 它是目錄，不是檔案 |
| `sourcePathChanged` 由 `editingFinished()` 觸發並與前值比對去重 | `pps2_0devtool.cpp` `onSourcePathEdited()` | 不會逐字元發訊號，自動載入不至於連續彈出對話框 |

## Goals / Non-Goals

**Goals:**

- 讓外殼具備「每個功能各自的來源路徑」這項能力，一次做進框架，後續功能直接受惠
- 功能端不需要知道路徑保管機制的存在
- 四支腳本都由 `scripts/_function_template.py` 複製而來，業務邏輯集中在 `script_utils/`
- Qt 端完全不碰檔案系統：目錄掃描與設定檔讀寫全在 Python

**Non-Goals:**

- 不做未儲存變更的保護（提示、暫存草稿）。切換功能時覆蓋結果清單是 spec 明確定義的行為
- 不做背景（非 modal）執行。維持既有管線的行為
- 不處理設定檔的並行存取。單一實例鎖已保證同時只有一個程式在跑
- 不驗證設定檔中的路徑是否仍然存在

## Decisions

### 決策一：來源路徑由外殼保管，鍵為功能名稱

外殼維護 `QMap<QString, QString>`，鍵為功能名稱（即 tab 標題），值為該功能的來源路徑。切換 tab 時把對應的值寫回共用的文字框。

**替代方案：各功能自己保存。** 需要一個功能的共同基底類別，好讓外殼在切換時向當前功能索取路徑 —— 而目前功能只是各自獨立的 `QObject` 子類，沒有共同基底。為了保管一個字串而引入繼承階層，代價高於收益，也違背「功能之間互相獨立」的設計。

外殼保管的另一個好處是後續功能免費取得這個行為，不需要各自重寫一遍。

### 決策二：切換 tab 還原路徑時，同步更新去重用的前值，不發訊號

`onSourcePathEdited()` 目前以 `m_lastSourcePath` 與新值比對來去重。切換 tab 時直接 `setText()` 並同步更新 `m_lastSourcePath`，訊號自然不會發出。

**替代方案：新增 `sourcePathRestored` 訊號。** 語意上更清楚，但功能端要多接一條訊號，而它的正確處理方式是「什麼都不做」—— 為一個空的 slot 增加介面表面積不划算。

**實作時的修正**：`m_lastSourcePath` 最後是被整個移除，而不是「同步更新」。既然每個功能的路徑已經存在 `m_functionSourcePaths` 裡，去重的比對基準直接用 map 中的值即可 —— 切換 tab 時把文字框還原成 map 中的值，之後的 `editingFinished` 比對相同就不會發訊號。少一個成員、少一份需要人工維持同步的狀態，原本「兩種語意容易誤改」的風險也一併消失。

### 決策三：來源路徑變更訊號附帶功能名稱

Qt 的訊號會送達所有已連接的 slot，「只有該功能反應」無法靠不廣播達成。訊號因此改為附帶路徑所屬的功能名稱，功能端比對自己的名稱後決定是否處理。

```
sourcePathChanged(const QString &sourceFilePath, const QString &functionName)
```

**替代方案：訊號簽章不變，改由功能查詢外殼「我是不是當前功能」。** 需要外殼多開一個查詢介面，而且把「這是誰的路徑」這件事變成隱含狀態；附帶在訊號上更直接，也更難用錯。

目前 `Function` 區塊是空的，沒有任何功能連接此訊號，改簽章的實際成本為零。

### 決策四：清單顯示檔名，項目另外保有絕對路徑

清單項目的顯示文字為檔名，絕對路徑存在項目的附加資料中。

**替代方案一：清單直接顯示絕對路徑。** 型態一致最單純，但前綴完全相同的長路徑會撐爆清單寬度並需要橫向捲軸；過濾時使用者輸入的字也會命中路徑中的目錄名，造成整批誤中。

**替代方案二：Qt 端以來源路徑組出絕對路徑。** 那是 Qt 在做路徑處理，與「Qt 只負責 GUI」相牴觸，而且組出來的路徑分隔符與腳本寫入的可能不一致。

因此改由腳本同時回傳兩者，Qt 只做搬運：

```json
{ "data": { "files": [
    {"name": "a.cpp", "path": "C:\\proj\\src\\a.cpp"}
]}}
```

取得來源清單與讀取設定 SHALL 使用同一種形狀，Qt 端得以共用同一段解析。

### 決策五：過濾與排序以模型層處理，且兩者的大小寫規則各自獨立

清單以「模型 + 排序過濾代理」的方式呈現，而非逐項設定隱藏。逐項隱藏的作法容易讓「被藏起來但仍處於選取」的項目在送出時混進去 —— 那正是 spec 要求避免的行為。

過濾**區分**大小寫、排序**不區分**大小寫。兩者是不同的關切：過濾是使用者主動輸入，區不區分由他自己掌握；排序是被動看到的結果，若把所有大寫排在所有小寫之前，使用者會覺得清單根本沒排序。代理層剛好把這兩個規則分成獨立的設定。

自然排序（`a2.cpp` 在 `a10.cpp` 之前）需要自訂比較，不能用預設的字串比較。

**不使用 `QCollator::setNumericMode(true)`。** 實測發現 Qt 在沒有 ICU 的建置上會走後備的比較實作，而那條路徑**靜默忽略** `numericMode`：`numericMode()` 照樣回報 `true`，`compare("a2", "a10")` 卻回傳正數。規格要求的排序行為不能取決於目標平台的 Qt 是怎麼編的，因此改為自己寫比較函式 —— 數字段落跳過前導零後先比位數再逐位比較（避免超長編號轉整數時溢位），其餘字元以 `toCaseFolded()` 不分大小寫比較，完全相同時退回區分大小寫的比較以保證次序穩定。

### 決策六：四支腳本，不是一支多動作

`script_io.parse_request()` 會以信封中的 `action` 覆蓋腳本自身的常數，因此一支腳本內部分派多個動作技術上可行。但範本的 `--help` 與 `--dump-config` 是繞著單一 `ACTION` 建立的：一支多動作會讓自我描述機制只認得其中一個，另外幾個的參數不會出現在模板裡。設定鍵的 `required=True` 也無法按動作分別標記。

專案明確支援「命令列與 CI 直接執行腳本」，這套自我描述機制不能壞。四支入口腳本各自很薄，業務邏輯集中在 `script_utils/` 共用，重複的部分有限。

### 決策七：暫存設定檔的位置由 `script_utils` 的單一函式決定

三支腳本（讀取、寫入、清空）必須指向同一個檔案，指不一致的症狀是「寫進去讀不出來」，而且很難查。位置與檔名因此由 `script_utils` 中的單一函式決定，三支共用。

目錄取 `tempfile.gettempdir()` —— 它在 Windows 解析為 `%TEMP%`，在 Linux/macOS 為 `/tmp`，是使用者要的「類似 /tmp」的直接對應，且各使用者互相隔離。

**不放進設定檔。** 多一個設定鍵就多一個使用者可以填錯的地方，而這個路徑沒有需要因環境調整的理由。

### 決策八：來源路徑變更時重用「清空設定」的腳本

「重新開始」需要清空暫存設定檔再重新載入來源清單。清空的動作與 Recovery Setting 完全相同，直接重用同一支腳本即可，不需要第五支。

確認對話框在 Qt 端，只掛在 Recovery Setting 上；路徑變更走的是同一支腳本但不經過確認框。

### 決策九：串接以「前一支的 callback 中啟動下一支」實作

管線一次只跑一支腳本，需要接續的動作因此串接。取消時 callback 不會被呼叫，所以「取消即中止整串」是這個結構的自然結果 —— 不需要額外的旗標。

需要串接的情境：

```
進入功能（來源路徑非空）   取得來源清單 -> 讀取設定
進入功能（來源路徑為空）   讀取設定
來源路徑變更              清空設定 -> 取得來源清單
Modify Setting            寫入設定
Recovery Setting          確認框 -> 清空設定
```

### 決策十：初次載入不依賴分頁切換事件

tab 寫在 `.ui` 中時，分頁索引在 `setupUi()` 期間就從 -1 變成 0，那時訊號尚未連接。只依賴切換事件的話，應用程式啟動後使用者第一眼看到的會是空白畫面，而且必須切走再切回才會載入。

因此初始化流程中需要一次明確的載入呼叫，與切換事件走同一段程式碼。

### 決策十一：`sort()` 必須在接上來源模型之後呼叫

排序代理的 `sort(0)` 寫在建構子裡是無效的 —— 那時還沒有來源模型，`sort()` 是空操作，`sortColumn()` 會留在 `-1`，而 `setDynamicSortFilter(true)` 只會重新套用「既有的」排序欄，救不回來。症狀是清單完全沒有排序，但程式碼看起來每一行都對。

因此改為覆寫 `setSourceModel()`，在呼叫基底類別之後才 `sort(0)`，把這個順序要求封在類別內部，而不是留給每個使用者自己記得。

## Risks / Trade-offs

**每次進入功能都執行兩支腳本，連續彈出兩次 modal 對話框** → 使用者頻繁切換分頁時體感很吵。目前接受：兩支腳本都是本機檔案操作，執行時間應在毫秒級。若實測下來惱人，後續可考慮合併為單一腳本回傳兩份資料，或在來源路徑未變時略過重新掃描。

**未寫入的結果清單變更會在切換分頁時遺失** → spec 明確定義為預期行為並寫進場景，不是隱藏的副作用。使用者若在意，正確做法是先按 Modify Setting。

**暫存設定檔可能被作業系統清理而消失** → Windows 的磁碟清理與儲存空間感知會清 `%TEMP%`。使用者已確認這是預期行為（重開機讓它消失即可）。若日後需要跨重啟保留，正確位置是 `%LOCALAPPDATA%`，屆時只需改動 `script_utils` 中那一個函式。

**設定檔中的路徑可能指向已不存在的檔案** → 使用者在未變更來源路徑的情況下自行刪除 `.cpp` 檔案時會發生。本次不驗證：來源路徑變更已經會清空設定，涵蓋了絕大多數失效情境。剩餘情形下結果清單會顯示來源清單中沒有的項目。

**`m_lastSourcePath` 的語意改變** → 從「上一次的路徑」變成「當前功能的路徑」。誤解會導致切換分頁時誤觸重新載入，而症狀（設定莫名被清空）與成因距離很遠。需要在程式碼中明確註記。

**外殼的來源路徑列對不需要它的功能仍然顯示** → 切換到那樣的功能時欄位會是空白，看起來像壞掉。本次不處理（目前只有一個功能），但這是外殼下一次需要面對的問題。

## Migration Plan

不需要資料遷移。`Function` 區塊目前為空，沒有既有功能連接 `sourcePathChanged`，改變訊號簽章不影響任何現有程式碼。

回退方式是移除功能 tab 並還原外殼的三處改動（路徑保管、切換時還原、訊號簽章）。設定檔中的 `Single Building` 區塊留著也無害 —— 外殼不解析功能區塊的內容。
