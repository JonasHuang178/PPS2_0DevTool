# Design

## Context

動機與範圍見 proposal.md。這裡記下探索過程中被否決的替代方案與理由 —— 其中有幾個看起來明顯
更好，而否決它們的原因都不在「不好做」。

既有的畫面已經有一個 `Merge Request Parameter` 群組，裡面兩個條件都是**送給 GitLab 的查詢參數**，
而既有規格明文規定「改動任何一項查詢條件 SHALL 清空表格」。這次新增的兩個過濾器作用於**已經
取回的資料**，行為相反。這個對立是整份設計的起點。

另一個既有事實決定了這次改動的規模：取得清單那一步的回傳資料**早就包含 `author` 與 `web_url`**，
Qt 端只讀了其中五個欄位。四項需求所需的資料全部已經在手上，所以這是一個 Qt-only 的改動。

## Goals / Non-Goals

**Goals:**

- 讓「送出去的查詢」與「取回之後的顯示」這條分界在畫面上看得見，而不必靠試誤學會
- 讓「畫面上的比實際的少」這件事在任何時刻都看得見

**Non-Goals:**

- 不追求過濾的表達力。字面文字的三種比對就是上限，不做萬用字元、不做正規表示法
- 不追求記住使用者的偏好。設定檔只給預設值
- 不改變單次取回 100 筆、不翻頁的既有行為

## Decisions

**一、作者過濾在本機進行，不送 GitLab。**

GitLab 的查詢參數支援依作者篩選，送出去取回的是「某人的前 100 筆」，比在本機過濾精確。但查詢
參數吃的是 username，而表格顯示的是顯示名稱 —— 使用者看著「黃小明」把它打進去，換回一片空白，
而「打錯 username」與「這個人真的沒有 MR」在畫面上**完全一樣**。

改成從取回的資料推導候選之後，使用者只能挑**存在的人**，那種失敗不會發生。候選上同時標出筆數，
按下去會剩幾筆也就不必猜。

代價是 100 筆上限換了個形狀：某人的 MR 全部落在被截掉的部分時，他**連候選都不會出現**。這個
代價以「達到上限的提示持續顯示」承擔（見決策七），而不是靠使用者記得。

被否決的第三個選項是在設定檔維護一份作者清單（比照 `Repo_List`）。它同樣避開 username 陷阱，
但換成部署負擔：換人要改設定檔，而忘記改的症狀是「某個人就是篩不出來」。

**二、標題排除用三個欄位，不用符號語法。**

把比對方式塞進單一輸入欄只有符號語法一條路，三種寫法都被否決：

| 寫法 | 否決理由 |
|---|---|
| `^WIP` / `Draft$` | **它看起來就是正規表示法。** 使用者接著會試 `.*`、`[0-9]+` 然後困惑，而我們只支援兩個錨點 |
| `WIP*` / `*Draft` | 與既有規格「`*`、`?` 視為一般字元」**語意相反**。同一支程式兩個輸入框對同一個字元的解讀不同 |
| `start:WIP` | 不像正規表示法了，但關鍵字本身若要以 `start:` 開頭就撞了，加跳脫規則等於把複雜度繞回來 |

這些標題裡本來就有 `[`、`(`（`[WIP]`、`(DNM)`），在任何語法方案裡都會讓人**以為自己在寫正規
表示法**。三個有標籤的欄位沒有要教的東西，也沒有會被誤解的符號。

同時被否決的是「可勾選清單 + 模式下拉 + 新增／刪除」。它多一個能力：暫時關掉其中一條規則而不必
刪掉再打回來。但那個能力的常見替代是「清除全部」，而本設計已經有一鍵清除；為了它換來一整套
可編輯的清單介面，以及「使用者新增的規則重開就消失」這個預期落差（因為不持久化），不划算。

**三、承載過濾器的群組可摺疊，不用對話框。**

對話框能把主畫面佔用壓到最低，但它多出一層狀態：未套用的修改要暫存，`Cancel` 要丟棄。摺疊的
省空間效果幾乎相同（收合後只剩標題列），而且沒有那一層。

常駐群組（不可摺疊）也被否決：它固定吃掉約 120px，而視窗是固定尺寸，那是表格四到五列。過濾
不是每次都要調的東西。

摺疊的代價是**表格高度會在展開／收合時跳動**。在固定尺寸的視窗裡這很明顯，但它跳動的方向是
對的：需要調過濾時表格變矮，調完變回來。

**四、排除條件於輸入結束時套用，不逐字元套用，也不加 `Apply` 按鈕。**

逐字元套用會讓表格在輸入「skip」的過程中隨 `s`、`sk`、`ski` 連續重算。加一個 `Apply` 按鈕可以
解，但那是新的互動概念。

既有的來源路徑輸入框用的正是「輸入結束才處理」（`editingFinished`），所以這不是新發明，而是
沿用。作者候選維持即時生效 —— 勾選是離散動作，沒有這個問題。

**五、標題欄的可點擊外觀用資料角色，不用內嵌 widget。**

Qt 可以在每一格放一個真正的超連結元件（`setIndexWidget` + rich text），那樣單擊、手形游標、
hover 變色全部免費。否決它的理由很具體：**這次同時加入兩個動態過濾器**。內嵌元件與動態過濾
相衝 —— 每次過濾或排序使列的位置變動，所有內嵌元件都要重設；一次取回 100 筆就是 100 個元件。

改用資料角色（前景色與字型）之後，那一格仍然是純文字：排序、過濾、截斷與提示文字全部照常，
而「看起來可點」這件事只是兩個屬性。游標形狀由視圖的滑過事件依欄位決定，不需要自訂繪製。

連帶的設計結論：**可點擊的外觀只加在標題欄，所以只有標題欄會開頁面**是自洽的。原本考慮「整列
任一欄連按兩下都開」，理由是避免「點了沒反應」；外觀把範圍講清楚之後，那個理由就消失了。

**六、設定檔用三個鍵，與三個欄位一對一。**

曾考慮一個物件陣列 `[{Text, Match}]`（與既有的 `AI_Mode_List` 形狀一致），但那需要 Qt 端分組，
而且 `Match` 的值是一個可以拼錯的字串（`startswith` 對 `StartsWith`），拼錯的症狀是「那一條
規則沒作用」。

也考慮過單一逗號字串（`"Skip_Title": "skip,test"`），它與輸入框完全一對一，但在 JSON 裡用字串
編碼一個清單，與既有的命名風格（清單一律 JSON array）不符。

三個鍵的形狀是：JSON 裡寫什麼，欄位就長什麼樣，中間沒有任何轉換，也沒有可以拼錯的值。

**七、達到上限的提示改為持續顯示，取代原本的一次性訊息框。**

既有規格只要求「取回筆數達到上限時 SHALL 讓使用者知道結果可能未完整」，沒有規定呈現方式。原本
的實作是取得清單後跳一個訊息框。

那個訊息框按掉就沒了，而使用者**正是在按掉之後**才開始在候選清單裡找人 —— 也就是最需要那個
提示的時刻，它剛好不在。改成與過濾統計同一行持續顯示，順帶少一次點擊。

**八、兩個過濾器共用一層過濾，兩者為 AND。**

作者與標題排除寫在同一個過濾判定裡（先看作者是否在選取集合中，再看標題是否命中任何排除規則），
不疊兩層。疊兩層的話，「篩掉幾筆」這個統計要分別從兩層取，而兩層的順序會影響數字。

多筆關鍵字之間為 OR（命中任一即藏），三種比對之間也是 OR。這是「排除」的自然語意：使用者列出
的是「這些我都不想看」。

**九`AI Analysis` 的啟用條件不需要修改。**

既有需求是「選了 repository、指定了 MR…才啟用」。而本設計規定「改動任一過濾器 SHALL 清空表格
選取」，選取一空，「指定了 MR」就不成立，按鈕自動停用。不需要為「選取的那一筆被藏起來」另立
規則 —— 那個狀態被設計成不可能發生，而不是被偵測出來。

## Risks / Trade-offs

**全域樣式表可能蓋掉標題欄的前景色。** → 外殼設有 `QTableView::item:selected { color: ... }`。
Qt 在樣式表指定了 `color` 之後是否仍採用模型的前景色，是一個版本與平台相關的灰色地帶。症狀是
「選中的那一列，標題不再是連結色」。這一項列為 Windows 實機的驗證項目；若被蓋掉，在樣式表中為
標題欄補一條規則即可，不影響其餘設計。

**作者候選仍受單次上限影響。** → 某人的 MR 全部落在被截掉的部分時，他不會出現在候選中。以持續
顯示的上限提示承擔（決策七）。這比「指定了某人卻一片空白」好：使用者只能挑存在的人，所以不會
對著一個空結果追問原因。

**無法暫時關掉單一關鍵字。** → 要手動從欄位中刪掉再打回來。常見的替代動作是「我想看全部」，而
一鍵清除涵蓋它。真正需要「只放行其中一條」的情況應該很少；若日後證明不是，再加可勾選清單時，
三個設定鍵的形狀不必改變。

**摺疊使表格高度跳動。** → 在固定尺寸的視窗裡明顯，但方向是對的（需要過濾時才付出高度）。預設
收合使多數時候維持現有高度。

**關鍵字不能含逗號。** → 分隔符的固有限制。標題中含逗號而需要以它排除的情況應該極少；若發生，
改以不含逗號的片段排除即可。

## Migration Plan

無需遷移。三個設定鍵皆為選填，既有部署的設定檔不新增鍵時排除過濾為空，行為與現狀相同；作者
過濾預設全不選，等同不過濾。信封、腳本與產物結構皆不變動。
