# Tasks

這一輪完全落在腳本側，而且是純運算 —— 涵蓋範圍的計算只看兩樣現成的東西（差異的文字與
鉤子回傳的結構），不需要 GitLab、AI 端點或 Windows 實機。所以 1–4 節都在命令列上驗，
只有第 5 節需要實機。

      回傳差異文字、完整收進該文字的檔案路徑（依序）、該 Merge Request 的檔案總數、

## 4. 命令列上的核對

4.1–4.8、4.10 以一支 39 項檢查的腳本一次跑完（截斷的切點以真實的 `_render_file_diff`
算出來，不是估的）；4.9 另外一支，把入口腳本的 `main()` 接上假的 GitLab 與一支會謊報
「涵蓋全部」的鉤子跑完整一步，再讀落檔的產物。三份產物（有缺口、沒缺口、版本 4）另外
實跑了步驟 5，確認報告的版面。


- [x] 4.1 截斷：餵一份超過上限的差異，確認未送出的檔案被算進缺口，被切一半的那個檔案
      算在未送出那一類
- [x] 4.2 AI 少回報：差異完整、回報只涵蓋一部分，確認未回報的檔案被列出，且該步驟成功
- [x] 4.3 空的差異內容：確認那些檔案單獨成一類，不被算成「AI 未回報」
- [x] 4.4 回報了但差異中找不到：確認單獨成一類，且不讓其他三類的數字對不起來
- [x] 4.5 路徑寫法：回報的路徑帶 `a/`、`b/` 前綴或只有檔名時，仍算成有回報
- [x] 4.6 沒有缺口：確認報告中沒有涵蓋範圍那一段，而出處仍有涵蓋標示
- [x] 4.7 舊版本產物（版本 3、4）：確認仍能單獨重跑渲染，沒有那一段也沒有涵蓋標示

- [x] 4.9 鉤子自行填寫涵蓋範圍：確認落檔的是入口算出來的值
