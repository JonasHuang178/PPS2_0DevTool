# Design

## Context

三個查證到的事實決定了做法（來源：GitLab 官方文件與其 issue tracker）：

1. 單一 patch 到門檻的 10%（預設約 20 KB）就被收合，API 的 `diff` 欄位回空字串。
2. `/diffs` 只接受 `page` / `per_page` / `unidiff`，**沒有**繞過收合的參數。
3. `/diffs` 的 `per_page > 30` 在多個版本回 500。

## Decisions

**一、只在出現空內容時才重取，不改成一律走舊端點。**

`/changes` 已標記為 deprecated（API v5 移除），而且 `access_raw_diffs` 是直接向 Gitaly 取，
較慢也較耗資源。正常的 Merge Request 不該為了這個例外多付一趟。

**二、重取之後「內容較多的那一份勝出」，不無條件採用。**

`access_raw_diffs` 本身有已知問題，在某些版本上它自己也回空的（gitlab-org/gitlab#300385）。
比較「有內容的檔案數」再決定，所以重取失敗時至少不會比原本更糟 —— 而這正是不能無條件相信
一條「文件說可以」的路徑的理由。

**三、重取失敗不讓整件事失敗。**

端點不在、權限不足都可能發生。原本那一份仍然可用，而呼叫端會從空的檔案數看見問題。

**四、一行內容都沒有時讓步驟 3 失敗。**

這是這次改動裡**唯一會讓原本「成功」的執行變成失敗**的一條，而它是重點：對著幾行檔名做出的
分析看起來很正常，但它沒有看過任何程式碼。讓它成功交出去，比失敗糟得多 —— 使用者不會知道
要懷疑它。

判斷用「整份差異裡有沒有任何一個 `@@`」，而不是「有幾個檔案是空的」：後者在一支同時含有
二進位檔與正常檔案的 MR 上會誤判。沒有變更的 MR 則不在這一條的範圍內。

訊息要說出成因**與該找誰改**：這是伺服器端的設定，使用者自己改不動。

**五、每頁筆數降到 30。**

不是效能調整，是避開一個會回 500 的已知版本問題。而那個 500 不會觸發既有的 `/changes` 退回
（退回只在 404 時發生），所以它會變成一個指不出原因的失敗。

## Risks / Trade-offs

**只改了模式變更或只有二進位檔的 Merge Request 現在會失敗。** 那種 MR 本來就沒有程式碼可以
分析，而訊息會說清楚取回的差異只有檔名。接受。

**重取會多一趟較慢的 API。** 只發生在本來就取不到內容的時候，而那時的替代方案是拿不到差異。

**本容器沒有 GitLab，所以重取的行為是對著假的回應驗的。** 真實伺服器上 `access_raw_diffs`
到底拿不拿得到，只有實機能證實 —— 而程式對「拿不到」這條路徑也已經有明確的失敗訊息。
