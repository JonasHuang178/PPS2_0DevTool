# Design

## Decisions

**一、逐行呈現用清單，而不是四行連著的文字。**

段落內的換行在 markdown 是軟換行，轉譯後變成一個空白 —— 四行會擠成一行。這個專案上一輪
才為了同一件事修過兩處（審閱的三行、出處的兩行）。清單是結構上就分開的元素，在任何轉譯器
下都成立。

**二、`<sub>` 放在每一個項目裡，不是包住整個清單。**

`<sub>` 是 inline 標籤，包不住清單這種 block 元素。實測過：外層包法產生的是

    <p><sub></p> … <ul>…</ul> … <p></sub></p>

清單根本不在 `<sub>` 裡面，而 sanitizer 多半會把那兩個孤兒標籤丟掉 —— 結果是「字沒有變小，
但你以為有」。

**三、四行的分法不是隨意切的。**

每一行回答一個問題：

    Device    用哪一套邏輯（含種類）
    腳本      哪一版骨架
    AI        哪個模型
    產生方式  誰在哪裡產生的

**腳本那一行永遠都在** —— 它是這整段存在的理由；其餘三行在沒有內容時整行不出現。

**四、模式與模型兩個都印。**

模式是「使用者選了哪一組設定」，模型是「實際跑的是誰」。在 CI 上沒有人選模式，只有後者有
意義；在工具上兩者都看得到才說得清楚。只有其中一個時不印斜線。

**五、兩個版號並列，程式不比對。**

`Device` 那一行是擴充層的版號，`腳本` 那一行是通用層的。第一碼一致代表同一代 —— 不一致時
讀的人自己對照得出來，程式不擋也不加標記（見「腳本的版號」規則的取捨）。

## Risks / Trade-offs

**移除 JIRA 之後，CI 上抽錯的 key 沒有任何地方看得見。** 見 proposal 的說明 —— 這是明知的
決定，而不是疏忽。補回來的最小做法是「只在 invalid 時顯示」。

**`<sub>` 在結果視窗會原樣顯示。** 那個視窗是純文字、不轉譯 markdown，所以會看到字面的標籤。
已確認可接受：報告的最終去處是 Merge Request 頁面。
