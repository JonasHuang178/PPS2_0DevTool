# Design

## Context

markdown 的段落內換行是**軟換行**：轉譯後變成一個空白。要讓兩行真的分開，只有三種寫法 ——
行尾兩個空白（硬換行）、中間空一行（兩個段落），或讓它們成為結構上分開的元素（例如清單項目）。

GitLab 的轉譯器對軟換行的處理與嚴格的 CommonMark 不同，所以同一份文字在不同地方看起來
可能不一樣。這次選的兩種寫法**在哪一種轉譯器下都成立** —— 清單就是清單，段落就是段落，
不依賴任何一家的軟換行行為。

## Decisions

**一、審閱的三行改成清單，出處的兩行改成空一行。兩處用不同寫法是刻意的。**

那三行是一組**欄位**（日期、作者、連結），清單本來就是它的形狀；轉成三個段落則會多出
與「一組註記」不相稱的間距。

出處那兩行各自是一句完整的敘述（這份報告由誰產生、在哪裡產生），不是欄位，所以是兩個段落。

**二、不用行尾兩個空白。**

它能動，但它是看不見的。這一段的正確性會變成「取決於沒有人把行尾空白清掉」—— 而清掉行尾
空白是編輯器的預設行為、是 linter 的規則、也是這個專案別處已經明講過的事（縮排那一支就
特地不在空行補空白）。一個看不見又隨時會被清掉的正確性，等於沒有。

**三、驗證用真的轉譯器，不靠讀規格。**

這個 bug 本來就是「看起來應該會換行」造成的。所以核對的方式是把報告丟進轉譯器，掃出所有
「段落內還留著換行」的地方 —— 那正是被併掉的那些。

## Risks / Trade-offs

**審閱那三行前面會多出項目符號。** 版面上比原本多一點裝飾。相較於三行擠成一行，這是划算的；
而它在不轉譯 markdown 的結果視窗裡也仍然讀得出是三個欄位。
