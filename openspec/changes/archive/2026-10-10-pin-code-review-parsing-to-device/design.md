# Design

## 背景

五支鉤子分成兩組，分組寫在 `device/__init__.py`，差別是解析幾段：

```
UNTYPED_HOOKS  兩段：<device>/ -> default/
TYPED_HOOKS    三段：<device>/<type>/ -> <device>/ -> default/
```

分組本身是對的。壞掉的是**為什麼**。

## 決策

### D1：兩個理由分開寫，不要共用一句話

`UNTYPED_HOOKS` 裡的三支，進來的理由有兩種：

| 鉤子 | 執行時機 | 看得到種類嗎 | 為什麼兩段解析 |
|---|---|---|---|
| `jira_key` | 步驟 2 | 否 | 種類那時候**還不存在** |
| `mr_type` | 步驟 2 | 否（它就是產生種類的那一支） | 同上 |
| `parse_code_review` | 步驟 4 | **是** | 種類對它**沒有意義**（見 D2） |

原本的註解只寫了第一種，於是第三支看起來像是被順手塞進來的。**讀的人會把它當成疏漏，
而那正是實際發生的事。**

所以兩個理由都要寫，而且要寫明第三支「看得到種類但刻意不用」。只寫「它們都不依種類
解析」是不夠的 —— 那是結論，不是理由，擋不住下一個覺得這是疏漏的人。

### D2：審閱報告的格式是 device 的屬性

使用者確認：**一個 device 底下只有一種審閱報告格式。** 種類不會改變那份報告長什麼樣。

所以「依種類載入不同的 parser」解決的是一個不存在的問題。加了之後：

- 載入器多一層，而每個讀它的人都要先理解一次才能確定自己不需要
- 種類目錄多一個合法但永遠不該用的檔名
- 步驟 4 多一個參數，Qt 與 CI 各多一處轉送

需要多種審閱報告格式時，正確的做法是**另開一個 device** —— 那正是 device 這一軸存在
的意義。

### D3：spec 從「陳述」升級成「禁止」，並補 scenario

原本的 spec 只是把它列在「不因種類而異」那一類。那是一句**陳述**，而陳述擋不住改動。

改成兩條正面的禁令（SHALL NOT 依種類解析、MUST NOT 收到種類），並補兩個 scenario：

- 種類目錄裡放了一份解析鉤子 → **不會**被載入
- 那一步接受的參數裡 → **沒有**種類

這是防飄移第 ④ 條的直接應用：**刻意的缺席要寫成可以被驗證的條文，否則它看起來只像是
漏掉的。** 這一次就是漏掉的那個結果 —— 沒有任何 scenario 說「種類目錄裡的解析鉤子不
會被載入」，所以把它做成會被載入時，沒有一條驗證會失敗。

### D4：MUST NOT 收到種類，而不只是「不使用」

把參數擋在門外，而不是收下來但不用。

收得到的話，總有人會拿它分支 —— 而那條分支依據的是一個與這支鉤子無關的軸。擋在參數
層面，想分支的人會先撞到「它根本拿不到那個值」，於是回頭問為什麼，而答案就在註解裡。

## Risks / Trade-offs

- **有一天真的需要依種類解析時，要改的地方比較多** → 那時該改的本來就是 spec 與這些
  scenario，而不是悄悄加一層。多出來的成本正是這個設計要的：讓那個決定被看見。
