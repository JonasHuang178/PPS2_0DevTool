## MODIFIED Requirements

### Requirement: device 鉤子的範圍

流程中 SHALL 只有四個步驟因 device 而異：取得相關資訊（抽出 JIRA key 與種類）、AI 分析、
取得程式碼審閱報告（解析與判定）、合併為 markdown。

取得 Merge Request 描述 MUST NOT 因 device 而異。

程式碼審閱報告的**取得** MUST NOT 因 device 而異（查詢附件、選取、大小上限、下載、解碼
皆由入口腳本負責）；其**解析與結論判定** SHALL 由該 device 的鉤子負責。報告中那一段的
版面 MUST NOT 因 device 而異。

理由：取得需要議題系統的存取權杖與統一的選取政策，而權杖 MUST NOT 交給 device 的實作，
選取規則也不該每個 device 重寫一次。但「那份文件長什麼樣、怎麼算通過」取決於該產品線用
哪一套 code review 工具，那正是 device 存在的理由。

鉤子 SHALL 分為兩類，其解析方式不同：

- **不因種類而異**：抽出 JIRA key、抽出種類、解析程式碼審閱報告。
- **因種類而異**：AI 分析、合併為 markdown。

這一類的三支**不是同一個理由**，兩個理由都 SHALL 被記錄：

抽出 JIRA key 與抽出種類在種類被決定**之前**執行（後者正是決定它的那一支），所以種類那
一層對它們不只是沒有用，而是還不存在。

解析程式碼審閱報告在種類被決定**之後**執行，看得到種類，但 SHALL NOT 依種類解析。理由：
那份審閱報告的格式是 **device 的屬性** —— 一個 device 底下只有一種審閱報告格式，不會因為
這一筆 Merge Request 是哪一種而不同。做成依種類而異，等於替一個不存在的需求多加一層解析，
而那一層之後每個讀載入器的人都要先理解一次，才能確定自己不需要它。

解析程式碼審閱報告的鉤子 MUST NOT 收到該次解出的種類。理由：收得到就會有人用它分支，而
那條分支依據的是一個與該鉤子無關的軸。要處理「不同的審閱報告格式」SHALL 另開一個 device。

每一步的入口腳本 SHALL 保留共用的部分 —— 信封處理、憑證取得、對外服務的呼叫、產物落檔、
失敗訊息與進度回報 —— 並只將業務運算交給 device 的鉤子。

理由：若每個 device 各有一支完整的腳本，共用部分（服務錯誤的分類指引、程式碼區塊界線的
計算、diff 的長度上限）會在每個 device 中各出現一次並各自漂移。

#### Scenario: 只有四個步驟因 device 而異

- **WHEN** 以不同的 device 執行同一個 Merge Request 的分析
- **THEN** 取得描述的行為相同
- **AND** 程式碼審閱報告的取得方式與報告版面相同
- **AND** 抽出 JIRA key、抽出種類、AI 分析、程式碼審閱的解析與判定、報告版面可以不同

#### Scenario: 不因種類而異的鉤子

- **WHEN** 解析抽出 JIRA key、抽出種類、或解析程式碼審閱報告的鉤子
- **THEN** 只在該 device 與預設 device 之間尋找，不涉及任何種類

#### Scenario: 種類目錄中的解析鉤子不被載入

- **WHEN** 某 device 的種類目錄中放了一份解析程式碼審閱報告的鉤子
- **AND** 該次解出的種類正是那個目錄
- **THEN** 載入的仍然是該 device 自己的那一份，種類目錄中的那一份**不被載入**

#### Scenario: 取得程式碼審閱報告那一步不收種類

- **WHEN** 檢視取得程式碼審閱報告那一步接受的參數
- **THEN** 其中沒有種類
- **AND** 該步驟也不向 GitLab 取得該 Merge Request 以自行解析種類

#### Scenario: 共用部分不因 device 重複

- **WHEN** 某個 device 的鉤子執行失敗
- **THEN** 失敗訊息的形式與其他 device 相同，因為它由入口腳本產生
