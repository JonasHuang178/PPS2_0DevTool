# Design

## Context

動機見 proposal.md。這裡記下讓這條規則不會誤傷的幾個判斷。

版面屬於步驟 5（既有需求「最終報告的組成」），所以斷行寫在渲染端，而不是在步驟 3 把
`overview` 改掉。放進契約（`__init__.py`）而不是直接寫在預設 device 的鉤子裡，是讓其他
device 也用得到 —— 與 `hunk_of()`、`fence_for()` 同一個位置。

## Goals / Non-Goals

**Goals:**

- 一段式的總覽變成逐行可掃讀，兩個呈現面（結果視窗的純文字、GitLab 的 markdown）都成立
- 模型自己給的結構（有序編號、自帶換行）被保留，不被覆寫
- 既有產物重跑步驟 5 就能受益

**Non-Goals:**

- 不追求「切得像人」。這是啟發式，目標是比一整段好讀，不是斷句正確率
- 不改 prompt，不改產物

## Decisions

**一、判斷順序是：已有換行 → 有序編號 → 句末標點。**

三條互斥，先到先用。已有換行排第一，因為那代表來源已經做過版面決定（模型自己分行，或某個
device 自己排好 —— 例如沒有 AI 端點時的替代內容本來就是三行）。覆寫別人已經做好的版面是
這條規則唯一真正會造成損失的方式。

**二、只認全形 `。！？`，半形 `.`、`!`、`?` 一律不算。**

全形是這個方案成立的關鍵：

- 半形 `.` 出現在 `v1.0`、`0.5`、`e.g.`，認它就會把版本號切成兩半
- 半形 `!` 出現在 `!7` 這種 Merge Request 編號
- 半形 `?` 出現在查詢字串 `?foo=bar`

中文全形句號幾乎不可能出現在數字或識別碼裡，所以誤切的機會接近零。半形那三個則幾乎都是
誤切。被否決的替代方案是「半形也認但加上前後文判斷」——規則會長到沒人敢改。

**三、句末標點後面緊跟的收尾符號要一起留在前一句。**

`他說「要改」。`、`（見下）。`、`真的嗎？」` —— 把 `」` `）` 留給下一句，下一行就會以一個
孤立的右括號開頭。

**四、有序編號保留原本的數字，但正規化成 `N. `。**

模型可能寫 `1、`、`1)`、`(1)`。這三種**都不是 markdown 清單語法**，貼到 GitLab 不會變成
清單。換成 `N. ` 則資訊沒丟（數字還在、順序還在）而 GitLab 渲染得出來。

編號改成 `-` 也可以，但那會把「這是有順序的」這個資訊丟掉 —— 模型用編號通常是有意的
（步驟、優先序）。

**五、有序編號必須「從 1 開始、連續遞增、至少兩個」才算。**

這一條是整份規則最重要的保護。文字裡偶然出現的數字加標點不會剛好構成 1,2,3 的遞增序列：

- `升級到 v1.0` —— 編號後面緊跟數字，直接排除（見下一條）
- `版本 1.0 與 2.0 都要測` —— 兩個數字是 1 和 2，看似遞增，但同樣被「後面不可是數字」排除
- `見第 3 點` —— 單獨一個，不足兩個

只認單一個 `1.` 的話，`v1. 0 之後` 這類寫法就會被切壞。

**六、編號後面不可以緊跟數字。**

`1.0` 的 `1.` 後面是 `0`，排除。這一條與上一條一起，把版本號這個最可能的誤判來源消掉。

**七、編號前面必須是字串開頭、空白，或句末標點。**

`v1.` 的 `1.` 前面是 `v`，排除。而 `1.調高。2.改逾時。` 的 `2.` 前面是 `。`，要收 —— 模型
不加空白是常態。

**八、只切出一點時原樣輸出，不做成清單。**

單項清單在視覺上是噪音，而「這份摘要只有一句話」本身就是看得出來的。

**九、不設點數上限。**

prompt 要的是三到五句，不會爆成二十點。設了上限反而會出現「有時是清單、有時是一整段」的
不一致，那比二十個條目更難解釋。

## Risks / Trade-offs

**斷句是啟發式，一定有切不漂亮的時候。** 例如「這個問題在 A 模組。B 模組沒事。」切成兩點是
對的；但「因為 A 所以 B。」這種單句被判定成一點、原樣輸出，讀起來與改動前相同。接受 ——
這條規則的目標是消掉文字牆，不是重寫摘要。

**模型若回半形句點結尾的中文**（`此問題OO. XXXX.`），這條規則完全不會啟動，結果與現在相同。
不為它破例，因為半形句點的誤切成本遠高於這種情況的收益。真的遇到了，該改的是 prompt。
