# Design

## Decisions

**一、兩層分開設定，不合成一個「重試次數」。**

兩者在語意上是不同的東西：

    Retry_Count   連線層 —— 服務沒有回應（逾時、斷線、429、5xx）
    Reask_Count   內容層 —— 服務回了，但回來的東西解析不開

合成一個數字的話，一個把它設成 0 的人會同時失去「模型偶爾在答案前面多一句話就重問一次」
這個很划算的補救 —— 那一次重問不是在等一個忙碌的伺服器，而是在修一個幾乎必然成功的小錯。
分開設，使用者才能只關掉他真正想關掉的那一層。

**二、`0` 是合法值，與逾時不同。**

逾時 0 秒沒有意義（那不是「不要等」，是「立刻失敗」），但重試 0 次正是「服務很忙時不要再
等」的那個值。所以讀取與驗證那一支用一個 `allow_zero` 分開兩種，而不是兩套程式碼。

**三、三個值共用同一支讀取與驗證。**

三者的規則幾乎相同（數字與純數字字串都收、布林值擋掉、不合法就明確失敗而不退回預設），
差別只有「允不允許 0」與「允不允許小數」。各寫一份的結果是三份會慢慢漂移，而漂移的症狀是
「同樣打錯，有的欄位會報錯、有的安靜地用預設」。

**四、把三個值與算出來的最壞情況記進診斷輸出。**

事後最常問的問題是「為什麼這次等了十六分鐘」。那一行就是答案，而且它在**開始等之前**就印
出來了 —— 等到事後再推算，使用者手上通常已經沒有當時的設定。

## Risks / Trade-offs

**把兩者都設成 0 會讓偶發的失敗直接變成整次失敗。** 那正是使用者要的（早點知道這次不行），
但他得知道自己在換什麼。README 把三個值與最壞情況的關係列成表，而診斷輸出也印出來。

**最壞情況是乘出來的，不是設出來的。** 使用者要的是「最多等 N 秒」，而他能設的是三個因子。
沒有再加一個「總上限」設定，是因為兩套規則必然互相矛盾，而使用者無從得知哪一套生效 ——
寧可把乘法講清楚。
