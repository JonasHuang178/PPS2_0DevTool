# Design

## Context

專案裡已經有一個叫「版本」的東西：`TEMPLATE_VERSION`。先分清楚兩者，否則這條規則會把它弄壞。

| | 回答什麼 | 範圍 | 什麼時候動 |
|---|---|---|---|
| `TEMPLATE_VERSION` | 請求與回應的信封長什麼樣 | **全專案**（所有功能同一個值） | 信封格式本身改了 |
| 功能的腳本版號 | 這個功能的腳本是哪一版 | 單一功能 | 該功能每次修改 |

兩者放在一起看才看得出為什麼不能共用一個常數：把 `TEMPLATE_VERSION` 拿來當某個功能的版號，
它就會一直往上跳，而另一個功能的停著不動 —— 兩個本該代表同一份信封格式的數字於是分岔，
而它還會被 `--dump-config` 印出去給持續整合系統看。

## Decisions

**一、兩碼，不是三碼。**

```
          2  .  0
          │     │
          │     └── 第二碼：任何修改都 +1（含只改註解）
          └──────── 第一碼：重大修改才動，第二碼歸零
```

三碼（major.minor.patch）的中間那一碼需要判斷「這算 minor 還是 patch」，而需要判斷的規則
就是會被漏掉的規則。兩碼沒有判斷餘地：不是重大修改，就是 +1。

**二、同一個功能的所有入口腳本共用一份版號，宣告在該功能的套件裡。**

各支腳本各自宣告的話，五支腳本就有五個數字要維護，而它們是同一次 commit 一起出去的 ——
五個版號能回答的問題，一個已經回答了。

**三、由功能擴充的實作另外宣告，第一碼應與通用版號一致。**

`AI Analysis GitLab MR` 的 device 機制是目前唯一的例子：那一層的程式碼由各產品線自己寫、
自己改，與通用層的步調不同，所以它需要自己的版號。第一碼一致則讓人一眼看出「這份擴充是
照哪一代的契約寫的」。

**四、不檢查、不強制。**

兩件事都不做：

- 不檢查「第一碼是否一致」—— 第一碼升級是工具維護者做的事，擴充可能由別的團隊維護，
  因為維護者升級就讓人家的環境跑不起來，代價與收益不成比例。兩個版號都印在報告上，
  讀的人自己對照得出來。
- 不檢查「改了但忘了更新版號」—— 真要有牙齒得靠提交前檢查或持續整合，而這個專案目前
  兩者都沒有。加一個沒人跑的檢查等於沒加。

這一條是明知的取捨，寫進規格裡講明白，比假裝它不存在好。

**五、沒有產物的功能也要宣告版號。**

`Single Building` 不產出會脫離環境的報告，所以它的版號沒有地方可以印。即便如此仍然宣告，
並記進診斷輸出 —— 支援時問一句「console 第一行是什麼」就知道版本，成本接近零。

## Risks / Trade-offs

**版號會跑得很快。** 每次修改都 +1，所以 `2.0` → `2.40` 是常態。接受：它是**修改計數器**，
不是語意化版本 —— 它告訴你「有東西變了」，不告訴你「變了什麼、相不相容」。需要知道相不相容
的是 `TEMPLATE_VERSION`，那個才是契約。

**沒有強制就會有人忘記。** 已知並接受（見決策四）。規格明文要求每次修改都更新，其餘靠程式碼
審查。
