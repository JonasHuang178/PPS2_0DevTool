# Design

## Context

動機見 [`proposal.md`](proposal.md) 的 Why。這裡只記下形塑做法的既有狀態與約束。

**步驟 4 目前的樣子。** `ai_analysis_gitlab_mr_code_review.py` 的對外契約（信封、必填檢查、
模板傾印、兩種投遞）已完整，業務運算是一段寫死的假報告。它收一個 `fetch_code_review` 布林，
Qt 固定送 `false`，所以那一步實際上一直回傳空結果。

**「沒有這一段」已經有一套機制，不需要新造。** 步驟 4 不呼叫 `write_artifact()` 時
`04_code_review.md` 不存在 → Qt 的 `insertArtifactPath()` 檔案不存在就不放那個鍵 → 步驟 5
的 `_is_given()` 把 null／省略／空字串都當「沒給」→ 整段不出現。三層一致，而且刻意不用
哨兵值：`merge_to_md.py` 的註解寫著「路徑給了就必須存在」，因為指名一個不存在的檔案代表
上一步沒寫成功。

**`jira_state` 的判定位置。** key 的有效性由 device 的鉤子在**步驟 3** 判定
（`device/default/summary.py` 的 `_jira_state()`），並寫進 `03_summary.json`。步驟 4 在
步驟 3 之後，因此拿得到它。

**共用能力已經齊了。** `jira_utils.get_issue_attachments()` 回 JIRA 原樣的附件物件
（`filename` / `created` / `author` / `size` / `content`），沒有附件回空清單而不是錯誤；
`download_issue_attachment()` 串流寫入、覆蓋同名、收到 HTML 明確報錯（防被導去登入頁存成
附件）。`ai_analysis_gitlab_mr.jira_credentials()` 步驟 3 已經在用。不需要新的第三方套件。

**環境變數的注入是機械規則。** `serviceEnvVars()` 對 `kServiceKey[]` 的每個鍵做
`env.insert(key.toUpper(), cfg.value(key).toString())`，而 `cfg` 是 `getFunctionConfig()`
的結果 —— 已經是 `Service` 併上 `Function` 區塊，所以鍵放在哪一邊都撈得到。`PPS_Device`
就是這樣的先例。

**工作目錄與除錯目錄在勾選時是同一個。** `AIAnalysisGitLabMR.cpp:700-701` 同時把它們設為
使用者指定的目錄；未勾選時工作目錄是暫存目錄，流程結束後整個移除，而除錯目錄是空字串。

## Goals / Non-Goals

**Goals:**

- 擷取失敗時絕不產出一份「看起來完整」的報告 —— 要嘛是真的表格，要嘛是說得清楚的訊息。
- 步驟 4 仍可單獨以命令列執行，不依賴圖形介面轉送任何東西。
- 新增的 device 彈性收在一個字串宣告內，不讓步驟 4 開始執行 device 的程式碼。

**Non-Goals:**

- 不改變步驟 1 的切段機制。
- 不在 Qt 端新增任何判斷 —— case 3 只多兩行轉送。
- 不為「總表」以外的段落（明細、逐檔案發現）預留擷取能力。

## Decisions

### 一、取得附件放在步驟 4，不放步驟 2

**被否決的替代方案：步驟 2 取得。** 步驟 2 已經連 GitLab 取一次 MR，看起來順手。但 key 的
有效性要到步驟 3 才由 device 判定，所以步驟 2 無從知道那個 key 值不值得查。`default` 的
`jira_key.py` 無條件取標題第一個方括號，`[WIP]`、`[Draft]` 這類前綴非常常見 —— 放在步驟 2
等於每一筆這種 MR 都白打一趟議題系統換回 404。規格對同一件事已有明文（「相關議題的內容
SHALL 在鉤子判定該識別碼有效之後才取得」），這裡沿用同一條理由。

**被否決的替代方案：步驟 2 下載、步驟 4 擷取。** 動機是「I/O 與運算分開」，但代價是一個
關切橫跨兩步、多一個要靠路徑傳遞的中間檔、多一條 Qt 轉送，而且仍然踩上面那個順序問題。
CI 也變成要串兩支腳本才拿得到一段 markdown。

### 二、步驟 4 的產物是結構，渲染在步驟 5

報告要印出附件的日期、作者與連結，而那三個值只有步驟 4 拿得到 —— 步驟 5 對 code review
只收到一個檔案路徑。

**被否決的替代方案：步驟 4 直接寫出排好版的 markdown。** 那就等於讓步驟 4 自己寫段落標題，
而規格明文「每一段的標題都由合併那一步寫出，產生內容的步驟 MUST NOT 自行寫出它的標題」——
它無從知道自己會被放在哪一層。

**被否決的替代方案：Qt 從步驟 4 的 data 轉送 metadata 給步驟 5。** 可行，但那些值就有兩個
來源（產物與參數），而它們可以不一致；Qt 也多四行。

採用的做法與步驟 3 完全同一套（`03_summary.json` 是結構、步驟 5 渲染），理由也同一個：
結構是唯一的真相，markdown 是它的呈現。

**意外的好處**：下載失敗時 `error` 有值而表格為空，但日期／作者／**連結**三行照樣印得出來，
讀者點連結就能自己看全文 —— 而那正是這一段設計的目的（報告只放總表，全文靠連結）。若步驟 4
交出去的是一段錯誤訊息文字，就只剩「取不到」三個字。

### 三、關鍵字走 `Function` 設定鍵 + 環境變數

設定鍵取名 `PPS_Scripts_CodeReview_File_StartsWith`，`toUpper()` 後正好是
`PPS_SCRIPTS_CODEREVIEW_FILE_STARTSWITH`（已驗證）。`StartsWith` 這個字尾把「前綴而非
子字串」寫進鍵名本身，看設定檔的人不必翻文件。

**放 `Function` 而不是 `Service`**：`Service` 的定義是「跨功能共用的服務端點與憑證」，
而附件命名慣例只屬於這個功能。注入機制讀的是合併後的 config，所以放哪一邊都可行 ——
語意決定位置。

**走環境變數而不是 `params`**：專案的分界是「跨執行不變的東西走環境變數（讓 CI 與圖形
介面共用一條取值路徑），隨這次執行而變的走 params」。附件關鍵字屬於前者，與 `PPS_DEVICE`
同一類。

### 四、未設定即失敗，檢查只在腳本且無條件

**被否決的替代方案：給它一個預設值 `CodeReview_`。** 那會讓設定鍵變成裝飾 —— 使用者漏設
時靜默套用一個他沒選的前綴，而症狀是「明明有附件卻沒有那一段」。與 device 的 `VERSION`
同一個判斷：沒有合理預設值的項目就該必填。

**被否決的替代方案：Qt 在按下按鈕時也檢查一次。** 提前到流程啟動前可以避免白付一次 AI
費用（與「工作目錄於流程啟動前建立」同一條理由）。使用者選擇只留腳本那一道，理由是一個
地方一個真相、不會漂移。**明確接受的代價**：設定檔少那個鍵時，使用者是付完 AI 費用、等完
那兩分鐘之後才看到錯誤訊息，而且那一次沒有報告。這是每個部署只會撞一次的成本。

**無條件執行**：不論這一筆有沒有 JIRA key 都檢查。只在「真的要去抓」時才檢查的話，一個
設定錯誤只會在剛好遇到有效 key 的 MR 時浮現 —— 一個有時才出現的部署錯誤比每次都出現的
難查得多。

失敗訊息同時點名環境變數與設定檔中的鍵。只說環境變數沒設，使用者會去設系統環境變數，而
真正該改的是執行檔旁那份 JSON。

### 五、失敗分成三類，只有一類會結束流程

| 類別 | 判定方式 | 行為 |
|---|---|---|
| 部署缺漏 | 不必發出請求 | FAIL，結束流程 |
| 外部服務的回答 | 發出請求之後 | PASS，訊息寫進結構 |
| 別人文件的內容不合約定 | 取得內容之後 | PASS，訊息寫進結構 |

**為什麼 401 不算部署缺漏。** 權杖無效看起來也是設定錯誤，但步驟 4 從自己的位置分不出
「權杖過期」「權杖被撤銷」「伺服器設錯」—— 它只知道請求被拒。真正的分界是**能不能在本機
判定**：缺關鍵字、缺端點、缺權杖不必發任何請求就知道，而且訊息完全可行動。這條線的附帶
好處是步驟 4 的 FAIL 只有一種語意（部署沒做完），所以看到它失敗，下一步永遠是去看設定檔。

**為什麼內容不合約定不 FAIL。** 這一步在 AI 分析之後，讓它結束流程會把一份**已經完成、
已經付費**的分析整份丟掉。而「別人的文件沒照約定」與規格對 MR 標題種類的既有立場是同一種
代價：「那是任何能開 MR 的人打的字，為了一個沒照約定的標題讓整份分析做不出來，等於把工具
的可用性綁在別人的打字習慣上。」

### 六、議題系統憑證未設定即失敗，與步驟 3 刻意不同

步驟 3 的 `_fetch_jira()` 缺憑證時只記警告、prompt 少一段，因為 issue 內容在那裡是**補充
資料**。步驟 4 缺憑證是 FAIL，因為 code review 是報告的**一整節**，而且關鍵字已經是必填 ——
語意上這個部署宣告了「我們一定有 JIRA code review」。

兩支腳本對同一組環境變數有不同的嚴格度，這件事必須寫下來，否則下一個人會以為其中一邊是
漏寫的。

### 七、附件的選取規則

- **前綴、區分大小寫。** 區分大小寫沿用專案既有的取捨：「過濾區分大小寫、排序不分大小寫 ——
  過濾是使用者主動輸入，排序是被動看到的結果」。關鍵字是部署者刻意填的值，屬於前者。前綴
  而非子字串，是為了不讓 `Old_CodeReview_backup.md` 這類檔案參與競爭。
- **副檔名固定在腳本。** 可配置的話有人會指到 `.docx` 或 `.zip`，於是二進位內容被貼進報告，
  而每一步都回報成功。
- **最新一筆以解析後的時間值比較。** `created` 是 `2026-09-10T09:29:00.000+0800` 這種帶
  時區的字串，字典序在跨時區時會排錯。同時間以 `id` 較大者為新（否則順序取決於 JIRA 回傳
  的順序，那沒有保證）。

**被否決的替代方案：以表頭欄位名稱驗證抓到的是不是總表。** 一度採納，後來前提消失 ——
各 device 的報告連欄位名稱都不保證相同，因此沒有可用的預設值。

### 八、擷取的搜尋範圍限定在那一節之內

這是整個擷取規則裡最重要的一條。

```
範圍 = 標題行之後  →  下一個 ATX 標題（^#{1,6}）或內容結尾
範圍內取第一個表格
```

**被否決的替代方案：從標題往下找第一個表格。** 當那一節恰好沒有總表時，它會抓到**下一節
的表格** —— 於是一張看起來完全合理的錯誤表格被貼進報告，標題還寫著「風險評估表」。限定
範圍之後，抓不到就是抓不到，走訊息那條路。

只把 ATX 標題（`#`）當邊界，所以來源結尾那條 `---` 不會被誤判成 setext 標題。表格的分隔列
`|---|---|` 以分隔字元開頭，因此不會被當成表格的結束。

標題的比對沿用既有的 `_heading_pattern()`（由常數導出、不手抄字面文字、階層與行首尾空白
寬鬆），圍籬追蹤沿用 `_heading_positions()` 的作法，並**同時套用到表格的掃描** —— AI code
review 報告裡出現程式碼區塊的機率很高，區塊裡若有一個假表格，不追蹤圍籬就會抓錯。

### 九、形狀檢查取代欄位檢查

欄位**名稱**因 device 而異，但「是不是一張 markdown 表格」不會。所以只要求：至少一列表頭
加一列分隔列。這不預設任何欄位名稱，卻擋掉「那一節只有散文」與「來源少了分隔列」兩種情況 ——
後者原樣貼進報告不會被渲染成表格，給訊息比給一堆分隔字元好。

### 十、表格原樣傳遞

不對齊、不排序、不改欄序、不補齊欄位。欄位因 device 而異，任何正規化都可能弄壞某一個
device 的表格。這條要寫進規格，否則日後有人「順手美化」對齊就會踩到。

### 十一、總表標題以 device 宣告承載，不開第五個鉤子

**被否決的替代方案：第五個鉤子 `code_review.py`。** 全面的彈性，但那會真的推翻「步驟 4 不
因 device 而異」，而且違反專案既有的做法（「在真的長出來之前不預先抽象」）。開了鉤子之後，
擷取的演算法就會每個 device 各長一份並各自漂移，而步驟 4 也會開始出現「哪一個 device 的
鉤子壞了」這類失敗。

採用的做法與 `STRICT_TYPE` 完全同一個形狀：`device/<name>/__init__.py` 裡一個選填的宣告，
未宣告落到預設值。device 在步驟 4 中不執行任何程式碼。既有規格那一行因此是**精確化**而非
推翻：「運算與版面不因 device 而異；device 僅得宣告來源文件中總表那一節的標題」。

### 十二、兩個標題常數各自獨立

| 常數 | 用途 | device 可覆寫 |
|---|---|---|
| `CODE_REVIEW_SOURCE_HEADING` | 在**別人的文件**裡找那一節 | ✅ |
| `CODE_REVIEW_HEADING` | 寫進**我們的報告**的段落標題 | ❌ |
| `CODE_REVIEW_TABLE_HEADING` | 寫進**我們的報告**的總表小標題 | ❌ |

`SOURCE_` 這個前綴把「這個字串屬於別人的文件」寫進名字裡，兩組常數就不會互相誤用。

**這與 `AI_HEADING` 的情況剛好相反。** 那一個同時是「寫出去」與「切回來」的同一個邊界，
所以**必須**只有一份來源、比對式必須由它導出。這裡的兩個沒有那種關係：改我們報告的小標題
不該影響去別人文件裡搜尋什麼，反之亦然。合成一個反而會製造一條不存在的耦合。

### 十三、報告中那一段是 H1，與 AI 分析同層

`AI_HEADING` 是 `#`，而 AI 分析那一段的內容本身用 `##`（`## Summary`、`## Code Changes`）。
程式碼審閱若用 `##`，在畫面上就與那些內容並列，讀起來是 AI 分析的一部分 —— 而既有規格明文
禁止這件事（「程式碼審閱那一段的標題與 AI 分析那一段同層，而非其下一層」）。所以段落標題
是 `#`，總表小標題是 `##`。

### 十四、本地存檔的檔名固定

`download_issue_attachment()` 的 `save_path` 若傳目錄，檔名會取自伺服器的
`Content-Disposition` —— 源頭是上傳者打的字。傳一個我們自己決定的完整路徑
（`<workDir>/04_code_review_src.md`），與規格對 device 名稱的「MUST NOT 被用來組成檔案
路徑」同一個理由，並順帶解決 JIRA 允許同名多筆附件的覆蓋問題。

### 十五、大小上限兩道

**下載前**先看 JIRA 回報的 `size`，超過就不下載 —— 有人把一份幾十 MB 的 log 改名掛上來時，
不必為了之後要丟掉的內容先傳進來。**讀入後**仍然截斷，因為 `size` 是 JIRA 報的、不保證與
實際一致，而這一道才是真正保護信封的那一道。

兩道用**同一個數字**，不要兩個 —— 兩個數字就會有人問為什麼不一樣。數字本身放在實作的常數
裡而不寫進規格，與 `MAX_PROMPT_DIFF_BYTES` 的作法一致。

選值的考量：一份人看得完的 code review 總表大約幾 KB。上限要大到**正常使用永遠不會觸發**
（一個經常觸發的上限會讓人習慣性忽略那個截斷記號），同時把信封壓在合理範圍。

### 十六、編碼：`utf-8-sig` 且嚴格

`utf-8-sig` 同時吃掉位元組順序記號與純 UTF-8。不用 `utf-8` 的具體理由：`file_utils.read_file()`
用的是後者，一份「UTF-8 含 BOM」的 md（Windows 記事本多年來的預設）會在字串開頭留一個
`﻿`，落在總表小標題底下的第一個字元 —— 看不見，但會讓那一行的 markdown 解析歪掉。

**被否決的替代方案：先試 UTF-8、失敗退 cp950。** 上傳者是 Windows 上的工程師，Big5 檔案
確實可能出現。但猜錯編碼會產出一份看起來正常的亂碼報告；`errors="replace"` 會產出一份少了
幾個字卻回報成功的報告。兩者都比一個明確的訊息糟，而明確的訊息還能把問題推回源頭（請存成
UTF-8）。

`file_utils.read_file()` 的註解已經寫明它「非 UTF-8 的內容拋出 `UnicodeDecodeError`，不
靜默替換 —— 共用模組不替呼叫端決定壞掉的位元組可以忽略」。這一條與它一致。

順帶：二進位檔（有人把 zip 或 PDF 改名成 `.md`）走的是**同一個例外**，所以一段程式同時蓋掉
兩種情況，不會留下一個沒人想過的 traceback。

### 十七、原始下載檔留在工作目錄即自動符合需求

因為勾選除錯時工作目錄**就是**除錯目錄、未勾選時是會被移除的暫存目錄，所以把附件下載到
`<workDir>/04_code_review_src.md` 就自動得到「勾選時留著、未勾選時消失」，不需要任何分支
判斷。

### 十八、不另存候選清單，但 `debug.log` 記錄篩選結果

**被否決的替代方案：寫一個 `04_code_review_candidates.json`。** 「為什麼挑到這一個」是這
一步唯一會被質疑的判斷，另存一個檔最完整。但使用者不要多一個檔，而 `debug.log` 已經存在、
已經在寫 —— 記一行「看到哪些附件、依關鍵字篩掉了哪些」成本近乎零，而它是「檔名大小寫打錯」
唯一的診斷路徑（見 Risks）。

## Risks / Trade-offs

**[檔名大小寫打錯 → 靜默沒有那一段]** 上傳者寫成 `Codereview_v2.md`（小寫 r）時比對不到 →
走「沒有符合的附件」→ 整段不出現，而且沒有任何訊息。對使用者來說，「這張 issue 沒有 review」
與「review 在那裡但檔名大小寫錯了」在報告上完全一樣。
→ 這是「區分大小寫」與「沒找到就靜默」相乘的結果，不是新問題。緩解是 `debug.log` 記下看到
與篩掉的檔名（決策十八）—— 那是唯一的診斷路徑。

**[表格寫法無法保證]** 先要求「以分隔字元開頭 + 分隔列」。某個 device 的工具若產出沒有前後
分隔字元的表格，該 device 的**每一筆報告都只會有訊息**。
→ 這樣壞得很大聲、一眼看得到，而不是靜默貼出半張表。補救是加法式的（日後讓那個 device 多
宣告一項寫法，或放寬偵測）。反過來現在就改成寬鬆偵測，散文裡任何一個分隔字元都會被當成
表格開頭，那會產出一份看起來正常的錯誤表格。

**[升級後設定檔沒有新鍵 → 每次分析都在步驟 4 失敗]** 既有設定檔不會被建置覆蓋，所以新鍵不會
自動長出來。
→ 訊息同時點名環境變數與設定檔的鍵，可行動。README 已有「升級後對照 `example.json` 補鍵」
的說明。代價是那一次的 AI 費用已經付掉（決策四）。

**[人工上傳的附件可能與當前程式碼不同步]** 附件是工程師手動掛上去的，「最新一筆」不保證是
對這一版程式碼寫的。
→ 刻意不做時間差警告（規則就是取最新）。報告印出**上傳日期**，讀者自行判斷；出處的存在
本來就是為了回答「這份東西是什麼時候、哪一版產生的」。

**[同一節有兩張表格而第一張不是總表]** 取第一張可能取錯。
→ 可接受：那一節叫「總表」，裡面第一張表不是總表的機率很低，而且沒有任何與 device 無關的
依據能分辨（決策七否決了欄位檢查）。

**[中文標題沒有詞界]** `_heading_pattern()` 的「詞與詞之間空白容許」對
`風險評估表總表` 沒有作用（`split()` 只切出一個詞），所以 `## 風險評估表 總表` 比對不到。
→ 不處理。真的需要時由該 device 宣告自己的標題即可。

**[附件檔名是上傳者打的字]** 它同時進入 markdown 連結文字與（若不小心）本地路徑。
→ 連結文字轉義（決策十三所在的版面需求）；本地路徑固定不取自它（決策十四）。

## Migration Plan

沒有既有資料需要轉換。

- **`04_code_review.md` → `04_code_review.json`**：中間產物每次執行重新產生，沒有需要相容
  的舊檔。
- **既有 device 不受影響**：未宣告 `CODE_REVIEW_SOURCE_HEADING` 時落到預設值，行為與現在
  相同。
- **設定檔要手動補一個鍵**。這是既有的升級流程（設定檔不被建置覆蓋），症狀與訊息如 Risks
  所述。

**部署順序有一個約束要注意。** `scripts/` 每次建置無條件覆蓋，而 Qt 需要重新建置（
`kServiceKey[]`、`kStepArtifactName[3]`、case 3 與 case 4）。正常路徑沒問題 —— 一次建置
同時更新兩邊。但**只把 `scripts/` 複製到舊執行檔旁**的話，舊 Qt 不會注入新的環境變數，於是
步驟 4 一律因「關鍵字未設定」而失敗、整條流程做不出報告。兩邊要一起更新。

（反過來的順序是安全的：Qt 新、腳本舊時，多出來的參數被舊腳本忽略，協定是加法式的。）

## Open Questions

- **同一節出現多張表格時是否需要更精確的挑選依據。** 目前取第一張。等真的出現再議 —— 屆時
  可用的依據多半是該 device 自己的宣告，而不是一條全域規則。
- **是否支援沒有前後分隔字元的表格寫法。** 目前不支援，症狀明顯（見 Risks），補救是加法式
  的。
- **是否要讓 AI 分析參考 code review。** 那需要把取得附件搬到步驟 3 之前，也就得回頭面對
  決策一那個順序問題（key 的有效性尚未判定）。這是另一個 change 的題目。
