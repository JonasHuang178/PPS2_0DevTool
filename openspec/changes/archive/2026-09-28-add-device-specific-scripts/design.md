## Context

封存的 `add-ai-analysis-gitlab-mr` 留了兩個 Open Question：「`device` 的來源」與
「`handler` 的 dispatch 內容」。當時 UI 上沒有任何地方選 device，`script_info` 裡的
`handler` / `source` / `path` 也沒有任何人讀 —— 它們是更早一版實作的遺跡。

本 change 回答那兩題。答案是：**沒有 handler，軸是 device**，而 device 由環境變數指定。

工具在這件事上的角色需要先講清楚，因為它決定了 device 腳本住在哪裡：**工具是開發
device 腳本的環境**。腳本開發者拿到的是一份可執行的環境（執行檔加 `scripts/`），他在
執行檔旁邊改 `.py`、按下按鈕、立刻看到結果，不會重新建置 Qt。寫完之後那份目錄上傳到
本 repo，CI 就跟著有了。

既有的三條約束本 change 不動：固定五步、各步的腳本路徑寫死在 C++、Qt 端不含業務判斷。

## Goals / Non-Goals

**Goals:**

- 同一批入口腳本能依 device 產出不同的分析與報告，而共用的部分只有一份
- device 的新增不需要改任何程式碼 —— 放一個目錄進去即可
- 只想改一個鉤子的 device 不必複製其他鉤子
- CI 與工具端取得 device 的方式完全相同
- 認錯 device 名稱時立刻失敗，而不是靜默用了通用邏輯
- device 腳本寫壞時，錯誤訊息指得出是哪個 device 的哪個檔案

**Non-Goals:**

- **`script_utils/ai_utils.py`**。AI 呼叫的共用模組留待後續 change
- **各 device 真實的 AI 呼叫與 prompt**。這一輪 `default` 的 summary 仍回假資料 ——
  等 `ai_utils` 定案再寫，否則第一批 device 腳本會為了改用共用模組再重寫一次
- **讀取 JIRA 的內容**。本次只處理 key 的抽出與有效性判定
- **步驟 1 與步驟 4 的 device 化**。取得描述與程式碼審閱不因產品線而異
- **UI 上選擇 device**。單一設定值即可，日後要加下拉是加法式的改動

## Decisions

### 一、device 名稱走環境變數 `PPS_DEVICE`，工具端由 Qt 從設定檔注入

**決定**：腳本一律讀 `os.environ["PPS_DEVICE"]`。CI 由 runner 設定；工具端把設定檔的
值注入為同名的環境變數。

**理由**：這是憑證那條路徑的原樣複製（封存 design 決策五）。腳本端因此只有一條取值
方式，裡面**沒有任何判斷自己跑在哪裡的 if**。

工具端的機制已經存在 —— `serviceEnvVars()` 就是把設定鍵以「鍵名全大寫」注入環境變數，
只需在那個清單多一筆。

**設定鍵必須叫 `PPS_Device`**：那條規則是機械化的全大寫、不維護對照表，所以
`PPS_Device` → `PPS_DEVICE`。叫 `Device` 會得到 `DEVICE`，跟 CI 對不上。

**放功能區塊而不是 `Service`**：`Service` 的定義是「跨功能共用的服務端點與憑證」，
device 是這個功能自己的分析輸入，性質與 `Repo_List` 相同。

**替代方案**：

- 工具端直接讀設定檔、CI 讀環境變數 —— 腳本端變成兩條路徑，得認得兩種來源
- 工具端也要求使用者設系統環境變數 —— Windows 上改了要重開工具才生效，而且使用者得
  在兩個地方維護

### 二、單一設定值，不做 UI 選擇

**決定**：設定檔一個值，代表「這台機器在做哪一條產品線」。

**理由**：工具是開發 device 腳本的環境，開發者一次專注一條產品線。要換就改設定檔重開。

**已知代價**：同一個工具裡分析兩條產品線的 MR 要改設定檔並重開（設定只在啟動時讀）。
日後若常切，加一個 `Device_List` 與下拉選單是加法式的 —— 注入那一行不變。

### 三、空值用 default，未知則失敗

**決定**：

```
PPS_DEVICE 未設定或只有空白  ->  default
PPS_DEVICE = "ssd"，目錄存在  ->  ssd
PPS_DEVICE = "sdd"，目錄不存在 ->  失敗，訊息列出認得哪些
```

**理由**：兩種情況的意思不同。沒指定代表「沒有特別需求」，用通用邏輯是對的；指定了一個
不存在的名字代表**打錯字或忘記部署**，靜默退回 default 會產出一份用錯邏輯、而每一步都
回報成功的報告。

**替代方案（已否決）**：用設定開關讓使用者選「退回 default 還是失敗」。否決的理由是它
把危險的那一邊變成看不見的設定 —— 有人設成退回，半年後某份報告用錯邏輯，而沒人記得
有這個開關。這正是本專案文件一再點的那種失敗。

`PPS_DEVICE=default` 明著指定是合法的，而且比留空更清楚。

### 四、fallback 是逐鉤子的，不是逐 device

**決定**：兩層不同的行為，不要混在一起。

```
device 目錄不存在        ->  失敗（決策三）
device 目錄存在，
  但缺某個鉤子檔案        ->  用 default 的那個鉤子
```

**理由**：只想改報告風格的 device 若得複製一整支 summary，那份複本會跟著 default 漂移。
這與本專案把 `gitlab_utils` 收成共用模組、把兩個標題常數收成一份是同一條理由。

### 五、按名稱 import，不從資料組路徑

**決定**：device 是 `ai_analysis_gitlab_mr.device` 套件底下的子模組，用
`importlib.import_module()` 按名稱載入。全程不碰檔案路徑。

**理由**：封存 design 決策十四明文否決過「腳本輸出的字串變成被執行的路徑」。按名稱
import 完全不開那條路 —— `../../etc` 這種值連組成路徑的機會都沒有。

名稱先小寫化，再檢查只含英數與底線。

**連帶的命名約束**：device 名稱必須是**合法的 Python 識別字**，所以 `ssd-gen4` 不行，
要寫成 `ssd_gen4`。這個約束是 import 機制帶來的，寫進範本與文件。

**替代方案（已否決）**：`PPS_DEVICE_DIR` 指向任意目錄，讓 CI 與工具各指一份。在
「device 腳本最終會進本 repo」確定之後它就沒有必要了，而它會把路徑組裝與驗證的責任
搬回來。若日後 device 腳本改放到產品自己的 repo，這條要重新考慮。

### 六、認得哪些 device 由掃目錄決定

**決定**：掃 `device/` 底下不以 `_` 開頭的目錄。不維護註冊表。

**理由**：註冊表會跟目錄漂移，而錯誤訊息裡那份清單一旦不準就比沒有更糟。掃目錄也剛好
是「放一個目錄進去就是新增一個 device」這個目標的最直接實現。

`_template/` 因為底線開頭不會被當成 device，與 `scripts/_function_template.py` 同一個
慣例。

### 七、入口腳本保留外殼，鉤子只拿會變的那一段

**決定**：入口腳本（路徑寫死在 C++ 的那六支）保留信封處理、憑證取得、GitLab 呼叫、
產物落檔、錯誤訊息與 `progress` 回報；只把業務運算交給鉤子。

**理由**：另一種做法是每個 device 各有一支完整的腳本。那會讓 401 / 404 / TLS 的四種
使用者指引、圍籬長度計算、diff 截斷規則在每個 device 裡各出現一次，然後各自漂移。

這條界線剛好與本專案 Qt／Python 的分工同形：外殼負責契約，內臟負責運算。

### 八、輸入給滿，輸出收窄

**決定**：鉤子收到的參數比它「現在用得到的」更多；回傳的範圍則盡量窄。

`merge_to_md` 的鉤子收到描述、分析結構、程式碼審閱、repo、mr_iid、device，但**只回傳
「AI 分析標題底下那一段」**。

**理由（輸入給滿）**：只給分析結構的話，device 想做「這次的分析對照原始描述的哪幾點」
就沒有材料，而日後補參數要改所有 device 腳本的簽章。

**理由（輸出收窄）**：`# AI 分析結果` 那一行**同時是下一輪切段的邊界**（封存 design
決策二十四）。若 device 擁有整份報告，某個 device 把標題寫成別的字，下一輪步驟 1 就
找不到邊界 —— 整份舊報告被當成原始描述，再接上新的一段，於是疊起來，而每一步都回報
成功。而這個約束無法靠文件擋住：每個寫 device 腳本的人都得記得那一行不能改。

由入口腳本寫那一行，這個保證就是結構性的。

**已知代價**：device 不能改原始描述那一段的排版、不能調整節的順序、不能在 footer 加
自己的資訊。前兩項繞不過；第三項可以把內容放在自己那一段的結尾。

### 九、鉤子只回內容，`schema_version` 由入口蓋章，並在邊界驗證

**決定**：

- `summary` 鉤子回傳 `analysis` 的內容，**不含** `schema_version`
- 入口腳本蓋上版本號
- 入口腳本在收到鉤子回傳時**立刻驗證**結構，用的是步驟 5 渲染前那同一套檢查

**理由（蓋章）**：讓 device 自己填版本號，遲早有人複製範本時忘了改，於是拿到一個聲稱
是某版、實際是別的形狀的檔案。

**理由（驗證）**：這是真的踩過的。`summary` 欄位曾經變成巢狀物件，根因在步驟 3，症狀
卻爆在步驟 5，訊息是一句 `dict object has no attribute strip` —— 既沒說是哪個檔案也沒
說是哪個欄位。有了 device 之後這個距離更遠。驗在邊界，訊息才點得出是哪個 device 的哪個
檔案。

驗證函式因此由步驟 3（收到鉤子回傳時）與步驟 5（渲染前）共用同一份。

### 十、device 載入與執行的錯誤由載入器自己攔

**決定**：載入器攔住 import 與執行期的錯誤，組出帶 device 名與檔名的訊息再往上拋。

**理由**：開發者的迴路是「改 `.py` → 按按鈕 → 看結果」。而 Qt 的錯誤框只顯示結果信封
的 `message`，`detail` 裡的 traceback 不顯示。`SyntaxError` 的字串剛好含檔名行號，但
`'NoneType' object has no attribute 'get'` 這種什麼位置都沒有 —— 開發者只能開
`Debug_Mode` 去 console 撈。

自己攔下來組訊息是純 Python 的改動，而且能講得更精確（「device `ssd` 的 `summary.py`
載入失敗」比一個裸的例外好讀）。

**替代方案**：讓 Qt 的錯誤框在 `detail` 非空時一併顯示。那更根本、所有功能一起受惠，
但屬於外殼的改動，留給另一個 change。

### 十一、JIRA：mode 的分派在入口，抽取在 device

**決定**：

```
入口 mr_info.py
   jira_mode == "none"    ->  不叫鉤子，state = none
   jira_mode == "manual"  ->  不叫鉤子，用使用者輸入的值
   jira_mode == "auto"    ->  呼叫 device 的 jira_key 鉤子
```

**理由**：三選一是政策而非演算法。留在入口，否則每個 device 都要重寫同一段，而且可能
寫歪 —— 例如某個 device 在 auto 模式下卻採用了 manual 的值。device 只負責「怎麼從 MR
抽出來」。

CI 只有 auto 一種模式（`none` 與 `manual` 是工具畫面上的選項）。因此 `jira_mode` 的
預設值改為 `auto` —— 現在宣告的預設是 `none`，與 UI 預設（Auto）和 CI 的唯一模式都
不一致。

`jira_mode` 也唯讀傳給步驟 3，讓 device 能分辨「這個 key 是抽出來的還是使用者手填的」。

### 十二、步驟 2 自己連線 GitLab

**決定**：步驟 2 用 `gitlab_utils.get_mr_info()` 自行取得 MR，再把整理過的資料交給
`jira_key` 鉤子。

**理由**：`jira_key` 的預設規則是讀 MR 標題，而步驟 2 手上沒有標題 —— 步驟 1 的產物只有
描述本文（標題、作者、分支在先前的 change 中被刻意移除）。Qt 也不可靠：MR 表格有標題，
但手動輸入編號那條路徑沒有。

**已知代價**：同一個 MR 會被抓兩次（步驟 1 一次、步驟 2 一次）。換到的是每一步自給自足、
可以單獨以 `--request-stdin` 執行（本專案明文重視的性質），而且 Qt 與 CI 不必多傳任何
東西。在五步流程裡這個代價可以接受。

**替代方案**：步驟 1 把標題經 `data` 往下傳。CI 是用檔案串接的，那需要多一個產物檔，
破壞「一步一個檔」的命名；步驟 2 也不能再單獨執行。

**鉤子拿到的是整理過的欄位**（標題、來源分支、目標分支、描述、repo、編號），不是 GitLab
原樣的物件 —— 否則 GitLab 的幾十個欄位就成了對 device 作者的契約，日後想換就動不了。

**錯誤處理沿用共用實作**：抓不到 MR（連線失敗、401、404）時重用
`describe_gitlab_error()`，讓四種指引與步驟 1 一致，然後失敗並結束流程。

### 十三、有效性判定在步驟 3 的鉤子，狀態用三個欄位表達

**決定**：步驟 2 只抽取，不判定。判定在步驟 3 的 `summary` 鉤子（`default` 的規則是
JIRA key 的樣式：大寫專案碼加連字號加數字）。結構中以三個欄位表達：

```
jira_key    抽到的原值；沒有就空字串
jira_state  ok / none / invalid
jira_url    只有 ok 且伺服器位址有設才有值，否則空字串
```

**理由（為什麼不是一個欄位）**：曾考慮用 `jira_url` 一個欄位編碼 —— 有效就是網址、無效
就是 `NONE`。它撐不住，因為那個欄位會同時承載三件事：

| 情況 | 單欄位的結果 |
|---|---|
| mode=none | `NONE` |
| auto 抽到 `WIP`（無效） | `NONE` —— 與上一列無法區分，被拒絕的原值也不見了 |
| 有效的 key 但 `JIRA_SERVER_URL` 沒設 | 組不出網址 → 被判成無效，而 key 其實正確 |

最後一列是決定性的：那是設定問題，與 key 的對錯無關，卻會污染判斷。三個欄位各做一件事
之後，`jira_url` 也不再背哨兵值 ——「沒有網址」就是空字串，與 footer 第二行在
`CI_PROJECT_URL` 沒設時仍然印出編號是同一個處理方式。

**為什麼判定放步驟 3 而不是步驟 2**：抽取規則因產品線而異，判定規則也可能因產品線而異
（某條產品線的 key 格式不同）。兩者放在同一個 device 的掌控下才一致。

**`invalid` 時往下傳的仍是「沒有 key」的語意**，但原值保留在 `jira_key` 供 footer 顯示。

### 十四、報告出處記下 device 與 JIRA，版本分家

**決定**：

```
Script: v1.0 | Device: ssd v1.2 | AI Mode: Open AI | JIRA: WIP (invalid)
Gitlab Pipeline #1000 | Commit e456d23
```

- `Script` 是入口腳本與契約的版本；`Device` 是那個 device 自己的 `VERSION`
- 每個值前面都有名字 —— 沒有標籤的話（例如 `(Open AI / ssd v1.2)`）讀的人分不出哪個
  版本是哪個
- `JIRA` 依 `jira_state` 呈現：`ok` 印 key（`jira_url` 有值時做成連結）、`none` 印
  `NONE`、`invalid` 印**被拒絕的原值**加 `(invalid)`

**理由（印原值）**：`JIRA: WIP (invalid)` 直接告訴你標題寫成了 `[WIP] [PPS-1234]`；
`JIRA: NONE (invalid)` 只告訴你失敗了。

**理由（版本分家）**：同一份 MR 用不同 device 跑出來的報告不一樣。只有一個全域版本號的話，
兩份不同的報告會帶同一個版本，那一行就失去意義。

**device 沒寫 `VERSION` 視為錯誤**：footer 的版本號如果可以是空的，那一行就又說不清楚了。
範本裡就有這個常數。

**`invalid` 標記在 CI 特別重要**：CI 只有 auto 模式，而 auto 正是唯一會抽錯的模式
（`none` 與 `manual` 都是使用者明確給的）。CI 裡 warning log 沒有人看、中間步驟的
`message` 也不會被讀 —— footer 是唯一會被人看到的訊號。

### 十五、部分私有 helper 升格為 device 作者的公開 API

**決定**：`__init__.py` 裡幾個目前以 `_` 開頭的函式改為公開契約：圍籬長度計算、字串
正規化（`None` 收斂成空字串）、單筆 diff 的位元組上限，以及唯讀的 `AI_HEADING`。

**理由**：device 作者自己寫渲染時，這些東西**不能讓他重新發明**。寫死三個反引號的圍籬，
遇到內容含反引號的 diff 就會提前關閉程式碼區塊而爆版；不做 `None` 收斂，報告上會印出
`None`。

**已知代價**：這是 device 機制真正的長期成本 —— 多了一組對外 API，升格之後就不能隨便
改簽章。

### 十六、步驟 2 改名，`script_info` 攤平

**決定**：

```
ai_analysis_gitlab_mr_script_selector.py  ->  ai_analysis_gitlab_mr_info.py
action "script_selector"                  ->  "mr_info"
02_script_info.json                       ->  02_mr_info.json
```

`script_info` 攤平：`handler` / `source` / `path` / `status` / `device` 全部移除。

**理由（改名）**：舊名來自更早的實作，那時它真的在「選腳本」—— 而那正是封存 design
決策十四明文禁止的事。留著它，下一個讀 code 的人會去找一個不存在的選擇機制。

**為什麼是 `mr_info` 而不是 `jira_key`**：它現在的工作是取得 MR 的後設資訊，JIRA key
是它的第一個產物。步驟 1 原本會合成標題與分支、後來被移除，而步驟 2 現在本來就會抓
MR —— 哪天步驟 3 需要分支名，`mr_info` 是它天然的家。叫 `jira_key` 就得再改一次名。

**檔名只寫一次 `mr`**：本專案既有的慣例是檔名不重複前綴已有的字、action 字串自己完整
（`ai_analysis_gitlab_mr_description.py` 的 action 是 `mr_description`、
`..._summary.py` 的是 `ai_summary`）。所以檔名是 `ai_analysis_gitlab_mr_info.py`，
action 是 `mr_info`。

**為什麼移除 `device`**：device 現在從環境變數來，讓步驟 2 也回傳一份會變成第二個來源。

**現在改最便宜**：路徑在 C++ 只有一個常數、action 只有一處、產物檔名還沒有任何 CI 腳本
依賴它。

### 十七、程式碼審閱那一段由步驟 5 寫出自己的標題

**決定**：步驟 5 自己寫出該段的標題（與它處理 AI 分析那一段的方式相同），步驟 4 只負責
內容。

**理由**：現在步驟 4 的產物自帶 `##` 標題而步驟 5 原樣接上，於是它縮在 `# AI 分析結果`
底下，讀起來像是分析的子節，而它在語意上是與分析並列的一段。目前 `fetch_code_review`
固定為假所以還看不到，一開啟就會現形。

由步驟 5 寫出所有節的標題，「報告有哪幾節、各在第幾層」就只有一個地方決定。

## Risks / Trade-offs

| 風險 | 緩解 |
|---|---|
| device 腳本寫壞讓整條流程失敗，而訊息看不出是哪裡壞的 | 載入器自己攔錯誤並組出帶 device 名與檔名的訊息（決策十）；鉤子回傳在邊界立刻驗證（決策九） |
| device 作者自己寫渲染，寫死圍籬導致含反引號的 diff 爆版 | 圍籬計算升格為公開 API 並寫進範本（決策十五） |
| 某個 device 改了 AI 分析那一行標題，破壞下一輪的切段 | 那一行由入口腳本寫，device 碰不到（決策八） |
| `device/default/` 每次建置被 repo 的版本覆蓋，開發者直接改它會不見 | 寫進文件：要客製就新增自己的目錄，不要改 default。他自己新增的目錄不會被覆蓋也不會被刪除（`scripts/` 的複製只覆蓋與新增） |
| 報告上的 `Device: ssd v1.2` 在上傳 git 之前是自報的，無從追溯 | 這是「工具當開發環境」的固有代價。上傳之後即可追溯 |
| 同一個 MR 被抓兩次 | 有意識的取捨，換每一步自給自足（決策十二） |
| device 名稱必須是合法 Python 識別字，`ssd-gen4` 不行 | 寫進範本與文件；日後真有這種名字再考慮改載入方式（決策五） |
| 新增 `PPS_DEVICE` 的注入需要改 Qt，而實作環境沒有工具鏈 | 只有一行、與旁邊五筆同一個寫法；驗收項目明列「需 Windows 實機」 |
| 未知 device 直接失敗，而 device 腳本尚未上傳時 CI 會掛 | 這是有意的：CI 用的 device 必須在 repo 裡。開發期間用工具，上傳後 CI 才會指定該 device |

## Migration Plan

沒有既有資料需要轉換。三處與現況不相容，都在本 change 內一次完成：

1. **步驟 2 改名**：Qt 的腳本路徑常數與 action 同時改。沒有任何 CI 腳本依賴舊名
2. **`script_info` 攤平**：步驟 3 目前讀 `script_info.ai_summary.handler` 只為了印 log，
   移除即可
3. **schema 升到 3**：`03_summary.json` 是流程中的中間產物，每次執行重新產生，沒有需要
   相容的舊檔。步驟 5 對更舊的形狀（`{"summary": "一段文字"}`）維持既有的相容處理

`PPS2_0DevTool.example.json` 新增的鍵不會傳播到既有部署 —— 症狀是 `PPS_DEVICE` 為空、
於是用 `default`，與現況行為相同，不需要使用者做任何事。

## Open Questions

- **`ai_utils` 的形狀**。決定之後，`default` 的 summary 鉤子才能從假資料改為真的呼叫 AI。
  在那之前 device 作者若要自己寫 HTTP，每個 device 會各有一份重試與錯誤處理
- **JIRA 內容的讀取**。本次只處理 key；要不要讓鉤子拿到 issue 的標題、狀態等，留待
  `jira_utils` 的用法定案
- **`default` 的 JIRA key 樣式**。本輪採大寫專案碼加連字號加數字（能把 `[WIP]`、
  `[Draft]` 這類常見前綴擋掉）。若實際慣例允許小寫，要決定是否正規化成大寫再往下傳
- **device 腳本最終放哪個 repo**。本輪假設本 repo，CI 因此直接取得。若日後改放產品自己
  的 repo，決策五中被否決的 `PPS_DEVICE_DIR` 要重新考慮
