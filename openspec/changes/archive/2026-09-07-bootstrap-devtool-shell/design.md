## Context

見 [proposal.md](proposal.md) 的 Why。此處只記錄影響技術取捨的現況與限制。

**起點狀態**：repo 只有 LICENSE 與 README，沒有任何原始碼。設計文件 `IMPLEMENTATION.md` §3 所列的「目前的程式碼狀態」實際上是**目標結構**；§1.3 引用的 v1.4.0 commit `5e651cc` 在本 repo 中不存在。因此 §5.9 / §5.10 標示為「已存在，沿用」的元件（除錯環形緩衝、設定讀取、共用 UI 服務、系統匣、單一實例鎖、崩潰處理）全部需要新寫。

**技術限制**：Qt5 + qmake，Windows 端使用 Qt Creator + MinGW。macOS 僅用於確認編得過，因此 Windows 專屬 API 一律以條件編譯隔離。Python 腳本必須同時在 Windows 與 Linux 執行。

**設計原則**：Qt 只負責讓使用者「選擇」，業務邏輯全在 Python。每一個功能是一個 tab，功能之間互相獨立。

**與既有設計文件的關係**：本文件記錄 33 條決策，其中 12 條與 `IMPLEMENTATION.md` / `PYTHON.md` 目前的內容不一致（下方以 **[偏離]** 標記）。這兩份文件的同步更新不在本 change 範圍內。

## Goals / Non-Goals

**Goals:**

- 讓「新增一個功能」不需要修改任何框架程式碼 —— 只加功能自己的檔案、tab、設定區塊與腳本
- 讓舊版反覆出現的四類缺陷在框架層被結構性擋掉：設定鍵漂移、通道混用、結果被結束碼丟棄、介面被部分資料污染
- 讓腳本在 Qt 之外（命令列、持續整合）以相同的契約可用
- 端到端可驗證：用範本腳本跑通 Qt 送信封到 Qt 解析結果的完整路徑

**Non-Goals:**

- 不追求腳本崩潰時的最大可觀測性 —— 已接受「`Debug_Mode` 關閉時崩潰無線索」的取捨（見 D16/D17）
- 不追求對違規腳本的容錯 —— 違反通道分離的腳本會明確失敗而非被靜默救回（見 D10）
- 不設計功能之間的資料流編排；腳本接力由呼叫端逐次傳遞，框架不提供管線抽象

## Decisions

### 一、範圍與版本

**D1 白紙起步。** repo 為空，本 change 建立全部檔案。

**D2 版號從 v2.0.0 起。** 波及 `version.h`、About 對話框，以及設計文件中所有寫著 `v1.4.0` 的範例。

### 二、Qt 執行模型

**D3 腳本執行採非同步 callback。** **[偏離]**

`IMPLEMENTATION.md` §5.3 給的簽章以 out-param 回傳結果，那是同步形狀，而 §5.5 要求非同步、可取消、不開巢狀事件迴圈 —— 兩者不可能同時成立。同步簽章只能靠阻塞等待或巢狀事件迴圈實作，前者會凍結事件迴圈（跑馬燈停轉、取消鈕按不下、Windows 數秒後將視窗標為沒有回應），後者被 §5.5 明文禁止。

*替代方案*：(a) 訊號式 —— 每個功能需 connect/disconnect 並自行判斷結果歸屬，樣板碼多且容易漏接；(b) 同步加巢狀事件迴圈 —— 重入風險高，執行期間使用者仍能觸發其他 UI 動作，只靠「一次一支」擋不住。

*選 callback 的理由*：呼叫端程式碼形狀最接近線性思考；因為 D28（一次只執行一支）保證同時最多只有一個 callback 在飛，生命週期單純。

**D23 取消時不呼叫 callback。** **[偏離]**

規格要求「取消後畫面完全不動」。不呼叫 callback 是**物理保證** —— 功能根本沒有機會碰介面，不需要依賴每個功能作者都正確地寫出取消分支。

*替代方案*：呼叫 callback 但帶取消標記，讓功能區分失敗與取消。目前找不到需要區分的場景：介面鎖定與對話框都由外殼管理，功能沒有東西需要清理。

**D24 只認取消鈕；Escape 與視窗關閉都不算取消。** **[偏離]**

`QProgressDialog` 預設 Escape 等同取消，標題列也有關閉鈕，三者都會發出取消訊號。誤觸 Escape 會砍掉一次長時間的 AI 呼叫；又因 D23 不呼叫 callback，畫面什麼都不會發生，使用者只會覺得「按了沒反應」。需要以子類別攔掉按鍵事件與關閉事件，並移除關閉鈕提示旗標（讓鈕直接消失，而不是留著但沒反應）。

**D29 對話框立即顯示。** **[偏離]**

`QProgressDialog::setMinimumDuration()` 預設 4 秒。在對話框實際顯示之前沒有互斥遮罩，主視窗仍可操作 —— 直接違反「執行期間主視窗鎖定」。設為 0 讓對話框立即顯示、立即鎖定。

*代價*：極短的腳本會讓對話框閃現。可接受 —— 本工具的腳本以 HTTP、AI 呼叫、大檔解析為主，本來就要數秒。

*替代方案*：折衷設 200–300 毫秒。不採用，因為那只是縮短空窗期而非消除它。

配套：`setRange(0, 0)` 才會呈現跑馬燈，且絕不呼叫 `setValue()`（一呼叫就切回百分比模式）。

**D26 重複啟動回 false 加警告，不跳訊息框。**

對話框是應用程式互斥的，人不可能觸發重複啟動。真正會撞到這條的只有程式化的腳本接力。那是程式缺陷，不是使用者操作錯誤 —— 把程式缺陷用訊息框丟給使用者，他也不知道能做什麼。

**取消狀態機**：以「閒置 / 執行中 / 取消中」單一狀態管理，而非數個布林旗標。關鍵競態是「腳本正常結束的同一瞬間使用者按下取消」—— 兩個訊號都會進入佇列且順序不保證。單一狀態的規則很簡單：取消中狀態收到結束通知一律丟棄；閒置或取消中狀態收到執行請求一律回 false。等待 3 秒後強制終止必須以計時器實作，不能阻塞等待。

### 三、Qt 結果處理

**D10 移除 stdout 解析的退回掃描。** **[偏離]**

`IMPLEMENTATION.md` §5.4 保留「由後往前找左大括號逐一嘗試」作為 fallback。移除理由有二：其一，硬性限制已規定腳本不得印任何東西到標準輸出，fallback 的作用是在違規時**靜默救回**，而靜默救回的結果就是違規腳本永遠不會被修好（文件要求記警告，但警告只在 `Debug_Mode` 開啟時可見）；其二，原演算法對「JSON 之後才被污染」的情況本來就無效，救不了它宣稱要救的一半情況。

*替代方案*：改用括號配對掃描出所有頂層區塊取最後一個可解析者（O(N)，前後污染都能救）。不採用 —— 那是更好的容錯，但容錯本身才是問題。

*曾考慮的緩解*：解析失敗時附上標準輸出尾端，讓開發者一眼看出誰污染了通道。因 D16 決定不收集尾端而一併放棄。

**D33 無法啟動 Python 與腳本崩潰給不同訊息。**

`FailedToStart` 代表設定的執行指令根本不存在（例如設定寫 `python` 但機器上只有 `python3`），與腳本內容錯誤是完全不同的問題。D16 移除尾端收集之後，使用者拿不到其他線索，訊息本身就必須說清楚。

同理，**啟動前先檢查腳本檔案存在**：否則 Python 會以結束碼 2 結束、訊息在錯誤輸出，而錯誤輸出不被收集，使用者只會看到「腳本沒有回傳結果（結束碼 2）」，完全查不出是路徑打錯。

**D30 工作目錄與相對路徑基準都是執行檔目錄。** **[偏離]**

設計文件的設定檔範例使用相對路徑（`scripts\my_action.py`），但從未定義相對於什麼。若不設定行程的工作目錄，會繼承 Qt 行程的當前目錄，而那取決於啟動方式（雙擊捷徑、命令列、開發環境執行三者不同）—— 同一份設定檔在不同啟動方式下會有不同結果。

固定為執行檔所在目錄，與 `PYTHONPATH` 加入的 `scripts` 目錄一致。絕對路徑照樣支援。

### 四、Qt 外殼

**D31 未設定 `Visible` 時預設隱藏。**

*替代方案*：預設顯示。那會在設定檔漏寫時露出一個所有設定都缺的 tab，使用者點下去才發現是壞的。

*選隱藏的理由*：開發新功能忘了加設定時 tab 會消失，這個困惑的成本較低，且 `Debug_Mode` 一開就能從警告看到原因。

**D32 設定檔缺失或損毀時中止啟動。**

每個功能區塊都必須提供執行 Python 的指令，沒有設定檔時所有功能都無法運作。讓程式帶著空設定啟動只會讓使用者在每個 tab 都撞牆。與既有的「檢查 Python 3」啟動檢查同一類。

**D25 + D28 console 關閉鈕保持可用，關閉即結束程式，但先清理子行程。**

Windows 關閉由 `AllocConsole()` 建立的 console 時會送出關閉事件並在數秒後強制終止行程 —— 這正是預期行為，不需額外處理。副作用是若當下有腳本在執行，該子行程會成為孤兒（`QProcess` 的解構不會執行）。註冊 console 控制處理常式，在收到關閉事件時先終止子行程，成本約十行，行為不變。

注意：因為關閉主視窗是隱藏至系統匣，`Debug_Mode` 開啟時結束程式的路徑有兩條 —— 系統匣的結束項與關閉 console。這是刻意的。

**D6 不遮罩憑證。** 憑證本來就明文放在設定檔，由每位使用者填自己的值。

**設定讀取的分層**：查詢不存在的功能時回傳空物件而非錯誤，把「設定缺漏」的偵測交給腳本層的必填檢查（D20）。好處是錯誤訊息能精確到缺哪一個鍵，而不是籠統的「找不到設定」。

### 五、信封契約

**D22 + D27 信封移除工具身分欄位，改走環境變數。** **[偏離]**

原設計中工具身分同時存在於信封的 `tool` 欄位與 `TOOLNAME` / `TOOLVERSION` 環境變數 —— 同一份資料兩條通道，正是會長出「兩邊不一致而沒人發現」的形狀。擇一保留環境變數。

*已知代價*：環境變數在人手動執行命令列時不存在，依賴它的腳本在 Qt 之外拿不到工具身分。這是可接受的 —— 空值在該情境下是**誠實的答案**（它確實不是被工具呼叫的），腳本應能在缺少它們時正常運作。

*分層*：讀取環境變數是**入口腳本**的職責，共用模組仍然不得讀取環境變數（共用模組四條規則之三未被破壞）。信封處理層不代讀，因此 `parse_request` 只回傳四個鍵。

**D14 傾印模板內嵌 `config` 而非引用設定檔。** **[偏離]**

原設計以 `config_file` 引用設定檔，理由是避免憑證散落在各腳本的傾印檔。但在 D7（一支腳本即一個功能，無功能名稱概念）與 D8（信封處理層不解析設定檔結構）之下，引用方式**無法決定要取設定檔的哪一區塊**，只能把整個檔案給腳本 —— 於是兩種投遞方式拿到的 `config` 結構不同（一邊是功能區塊，一邊是含根鍵與所有功能的完整檔案），腳本被迫寫兩套取法。

改為內嵌後兩條路徑結構完全一致。原本的反對理由已因 D6（不遮罩憑證）而不成立。

**D15 移除命令列旗標投遞路徑。** **[偏離]**

投遞方式從三種減為兩種。參數宣告的四個欄位沒有一個變成廢物，只是用途轉移：型別與必填改由信封處理層驗證，預設值改為模板預填與信封缺值時的回填，說明改為服務說明輸出與模板的說明區塊。

*連帶影響*：`--help` 變得更重要 —— 它是使用者在傾印模板之前唯一能知道「這支腳本要什麼」的地方。

**D20 設定鍵以宣告物件而非字串清單宣告。**

宣告帶必填旗標與說明，與參數宣告對稱。真正的價值在必填檢查：舊版設定鍵拼錯只會讓程式拿到空值繼續跑，帶著空憑證去呼叫 API 得到 401，使用者於是去檢查憑證是否過期 —— 找錯方向。必填檢查讓失敗發生在**進入業務邏輯之前**，訊息直接指出缺哪一個鍵。

*替代方案*：純字串清單。較簡單，但無法產生說明，也無法做必填檢查。

**D7 一支腳本即一個功能。** 因此不需要功能名稱常數或旗標。

**D9 + D18 傾印模板為空值，鍵由每支腳本自行宣告。** 與 D20 同一個機制。

### 六、診斷與可觀測性

**D4 診斷輸出預設 INFO，詳細旗標開啟 DEBUG。** **[偏離]**

`PYTHON.md` §9 的範例程式碼寫死 DEBUG 等級且未提供切換函式，與 `IMPLEMENTATION.md` §6.2 的敘述不符。以後者為準。

**D16 + D17 移除輸出尾端收集；`Debug_Mode` 關閉時不收集錯誤輸出。** **[偏離]**

`PythonRunnerResult` 不再有尾端欄位。腳本真正崩潰時，訊息只有「腳本沒有回傳結果」加結束碼。

*已知代價*：`Debug_Mode` 關閉的使用者回報問題時，追蹤訊息已被丟棄且**無法復原**，只能請他開啟 `Debug_Mode` 重跑。若該崩潰不易重現（例如特定資料觸發），該次線索永久遺失。

*緩解*：`Debug_Mode` 開啟時錯誤輸出的每一行都經由診斷輸出進入 300 行環形緩衝，開發情境下的線索已免費存在。缺口只在 `Debug_Mode` 關閉的情境。

*被放棄的設計*：原本規劃尾端為「最後 30 行且不超過 4 KB，排除進度行、保留一般診斷行」—— 排除進度行是關鍵，否則處理數千筆的腳本崩潰時尾端會全是進度訊息而把追蹤訊息擠出視窗。此設計連同 D16 一併放棄，若日後需要可直接沿用。

**格式對齊**：Python 與 Qt 的訊息混在同一個 console，時間戳記含毫秒、等級名稱補成固定寬度。

**編碼**：注入 `PYTHONUTF8=1` 保證腳本輸出 UTF-8，Qt 端一律以 UTF-8 解碼。若使用系統地區編碼解碼，在繁體中文 Windows（cp950）上所有中文訊息都會變成亂碼 —— 而診斷訊息與進度階段文字大量使用中文。

## Risks / Trade-offs

- **`Debug_Mode` 關閉時腳本崩潰無任何線索**（D16/D17）→ 訊息中包含結束碼；請使用者開啟 `Debug_Mode` 重跑；不易重現的崩潰接受線索遺失。此為明確接受的取捨。
- **移除退回解析後，違規腳本會直接失敗**（D10）→ 這是刻意的：讓違規明確可見而非靜默容忍。風險在於訊息不夠具體（因 D16 無法附上標準輸出內容），需在文件與範本中清楚說明通道分離規則。
- **對話框立即顯示會讓極短腳本閃現**（D29）→ 可接受；本工具的腳本以數秒起跳的工作為主。
- **取消不呼叫 callback，功能無法區分失敗與取消**（D23）→ 目前無此需求；若日後出現，可加入取消專用的通知而不破壞既有契約。
- **環境變數傳遞工具身分，命令列情境下取不到**（D22/D27）→ 空值在該情境下語意正確；腳本必須能在缺少時運作，此點已寫入規格。
- **取消的競態處理錯誤會導致畫面被已取消的結果污染**（D23）→ 以單一狀態機而非多個布林旗標實作；規格中已列出「取消與結束同時發生」的情境作為測試案例。
- **設計文件與本 change 有 12 處不一致** → 文件同步為獨立工作；在完成前，本 change 的 specs 與 design 為權威來源。

## Migration Plan

無既有部署需要遷移 —— repo 為空，本 change 建立初始實作。

舊版 v1.4.0 的五個功能已全部移除，未來逐一重新設計；舊版程式碼有大量已知缺陷，不作為實作參考。
