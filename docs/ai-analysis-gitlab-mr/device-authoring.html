開始

三件事，不到五分鐘

1
複製範本，改成你的名字
cp -r device/_template device/ssd
目錄名會被當成模組名 import，所以必須是合法的 Python 識別字： 小寫英數與底線、不以數字開頭。ssd_gen4 可以，ssd-gen4 不行。
2
在 __init__.py 宣告 VERSION
這一個一定要有，沒宣告會直接失敗。 它會印在報告末尾（Device: ssd 1.2）。改了產出方式就把它往上加 —— 不加的話，新舊兩套邏輯產生的報告會帶同一個版本號。
3
刪掉你不想覆寫的那幾支
五支全都是選用的。只想改報告版面？那就只留 merge_to_md.py， 其餘四支刪掉 —— 缺的會自動用 default 的。
# 只想改報告版面的 device，合法而且推薦長這樣： device/ssd/ __init__.py VERSION = "1.0" ← 必要 merge_to_md.py ← 你唯一要寫的 # 其餘四支不存在，自動落回 default/
不要修改 device/default/
它在 repo 裡，而每次建置都會無條件覆蓋。 你自己新增的目錄因為 repo 裡沒有同名檔案，不會被覆蓋也不會被刪。

回退是逐鉤子的

不是「整個 device 找不到就用 default」，是一支一支找

PPS_DEVICE=ssd，這筆 MR 的種類是 bug summary.py（因種類而異，找三層） ① device/ssd/bug/summary.py ← 有就用它，結束 ② device/ssd/summary.py ← 再找這裡 ③ device/default/summary.py ← 最後的後備 jira_key.py（不因種類而異，找兩層） ① device/ssd/jira_key.py ② device/default/jira_key.py PPS_DEVICE=sdd（打錯字） ✗ 直接失敗，訊息列出目前認得哪些 device
認不得的 device 是錯誤，不是退回 default
打錯字或忘記部署時，靜默改用通用邏輯會產出一份用錯邏輯、 而且每一步都回報成功的報告 —— 那比直接失敗糟得多。
但認不得的種類相反，它視同「沒有種類」
種類是 MR 作者在標題裡打的字，不是部署問題。 要讓它變成錯誤的話，在 __init__.py 宣告 STRICT_TYPE = True。

三個會靜默出錯的陷阱

它們都不會讓任何一步失敗

只寫了 mr_type.py，忘了 jira_key.py
如果你們的標題格式與 default 不同，jira_key 會沿用 default 的規則（取第一個方括號），於是安靜地抽到錯的東西。 症狀只有報告末尾一行 JIRA: Alpha (invalid) —— 要跑完、讀到末尾， 而且要知道那一行本來該長什麼樣，才看得出來。
標題格式與 default 不同的話，這兩支通常要一起寫。
render() 回傳了 dict 而不是字串
入口把回傳交給 contract.plain()，而它會靜默 str() 非字串 —— 實測 plain({'overview': 'x'}) 回的是 "{'overview': 'x'}"。那段字面會印進報告，而五個步驟全部回報成功。
自己寫死三個反引號當程式碼圍籬
內容本身含反引號的 diff（改到 markdown 檔就會）會讓程式碼區塊 提前結束，而報告仍然「成功」產出。用 contract.fence_for(code) 算長度。

常見問題

開始寫之前會想問的

我一定要寫五支嗎？
不用。一支都不寫也是合法的 device（只要 __init__.py 有 VERSION），只是行為與 default 完全相同。
可以重用 default 已經寫好的程式碼嗎？
可以，明著 import 就行：
from ai_analysis_gitlab_mr.device.default import summary as base
它是普通的 Python，沒有東西擋你。
改了鉤子要重新建置嗎？
不用。每一步都是獨立的 Python 行程 —— 存檔之後下一次按按鈕就生效。
怎麼知道我的 device 真的被載到了？
跑一次，看報告末尾出處那一行的 Device 欄位。勾 Add Debug file 的話，中間產物也會留在你指定的目錄裡。
device 名稱可以寫大寫嗎？
設定檔可以 —— 比對前一律轉小寫，所以寫 SSD 找得到 ssd。但目錄名本身必須是小寫。連字號不行，會收到一則明確的訊息要你改成底線。
兩個 device 可以共用程式碼嗎？
可以，普通的 Python import。共用的東西放哪裡由你決定。
一定要分種類（type）嗎？
不用。沒有子目錄就是所有 MR 用同一份 summary 與 merge_to_md。
我們的 code review 報告格式不一樣，要怎麼改？
在你的 device 底下放一份 parse_code_review.py， 從 _template/parse_code_review.py 複製出來改。你會拿到現成的全文 （查附件、下載、解碼都在入口做完了），要做的只有兩件事：擷取要進報告的那一段、判定結論。
節名與預設不同的話，在 __init__.py 宣告 CODE_REVIEW_SOURCE_HEADING，入口會把它當 heading 傳給你。
不要放進種類目錄 —— 這一支不依種類解析，放了也不會被載入。 需要支援第二種格式時，另開一個 device。
為什麼 parse_code_review 不能依種類分？
因為審閱報告的格式是 device 的屬性 —— 一個 device 底下只有一種，不會因為這一筆 MR 是 bug 還是 feature 而不同。
它跑在步驟 4，技術上看得到種類，所以這是刻意的決定而不是限制。 spec 把它寫成了禁令並用 scenario 鎖住，免得下一個人把它當成疏漏改掉。
寫壞了會怎樣？
語法錯或 import 失敗 → 訊息帶檔名與行號；執行期例外 → 訊息點名是哪一個 device 的哪一支鉤子，並說明那是腳本問題不是來源文件問題。
但回傳值的形狀錯了多半不會報錯 —— 見上面那三個陷阱。
複製範本 → 宣告 VERSION → 只留你要覆寫的那幾支。
確切的鍵名不必背，範本每個檔案的 docstring 就是權威來源。
