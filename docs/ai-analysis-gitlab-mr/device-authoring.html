檔案結構

入口腳本與擴充腳本

入口腳本 —— 流程本身，五條產品線共用
一步一支，固定五步照跑。
你不會動到它們，也不需要為了新增一條產品線改它們。

開始

三件事

1
複製範本，改成你的名字
cp -r device/_template device/ssd
目錄名會被當成模組名 import，所以必須是合法的 Python 識別字：
小寫英數與底線、不以數字開頭。
ssd_gen4 可以，ssd-gen4 不行。
2
在 __init__.py 宣告 VERSION
這一個一定要有，沒宣告會直接失敗。
它會印在報告末尾（Device: ssd 1.2）。
改了產出方式就把它往上加 —— 不加的話，新舊兩套邏輯產生的報告會帶同一個版本號。
3
刪掉你不想覆寫的那幾支
五支全都是選用的。
只想改報告版面？那就只留 merge_to_md.py， 其餘四支刪掉 —— 缺的會自動用 default 的。
# 只想改報告版面的 device，合法而且推薦長這樣： device/ssd/ __init__.py VERSION = "1.0" ← 必要 merge_to_md.py ← 你唯一要寫的 # 其餘四支不存在，自動落回 default/
不要改 device/default/
它是所有 device 的共同後備：
每一支沒有被覆寫的擴充腳本 都會落到它身上，別條產品線的也一樣。
改 default/ 等於同時改掉所有人的行為。
要不一樣的做法，在自己的目錄裡放一支同名檔覆寫它就好。

回退是逐支的

不是「整個 device 找不到就用 default」，是一支一支找

PPS_DEVICE=ssd，這筆 MR 的種類是 bug summary.py（因種類而異，找三層） ① device/ssd/bug/summary.py ← 有就用它，結束 ② device/ssd/summary.py ← 再找這裡 ③ device/default/summary.py ← 最後的後備 jira_key.py（不因種類而異，找兩層） ① device/ssd/jira_key.py ② device/default/jira_key.py PPS_DEVICE=sdd（打錯字） ✗ 直接失敗，訊息列出目前認得哪些 device
認不得的 device 是錯誤，不是退回 default
打錯字或忘記部署時，靜默改用通用邏輯會產出一份用錯邏輯、 而且每一步都回報成功的報告 —— 那比直接失敗糟得多。
但認不得的種類相反，它視同「沒有種類」
種類是 MR 作者在標題裡打的字，不是部署問題。
要讓它變成錯誤的話，在 __init__.py 宣告 STRICT_TYPE = True。

"""看懂別人的 code review 報告，並判定這份審閱的結論。 查議題附件、挑最新那一份、擋大小上限、下載、解碼都在入口腳本 —— 那些要 JIRA 權杖，而權杖不交給 device 的程式碼。你拿到的是現成全文。 """ import ai_analysis_gitlab_mr as contract def parse(inputs): # heading 是你在 __init__.py 宣告的 CODE_REVIEW_SOURCE_HEADING， # 沒宣告就是契約的預設值。自己的切法也可以。 table = contract.extract_risk_table(inputs["text"], inputs["heading"]) total = 0 for index, row in enumerate(_rows(table), 1): count = _count_of(row[-1]) if count is None: # 表格不是這個形狀 —— raise，報告上留一行 ⚠️ 說明原因。 # 讀得懂但就是判不出結論的話回 REVIEW_RESULT_UNKNOWN， # 結論那一行就不印。兩種都不要猜：印一個錯的 PASS 比不印更糟。 raise contract.RiskTableError( u"總表最後一欄的第 %d 列是 %r，不是數量" % (index, row[-1]), u"這一份規則把最後一欄當數量，全部列加總為 0 判定通過。", u"CODE_REVIEW_COUNT_NOT_A_NUMBER") total += count # 一列資料都沒有也是 0，也就是 pass —— 那張表的意思就是「沒有項目」。 verdict = (contract.REVIEW_RESULT_PASS if total == 0 else contract.REVIEW_RESULT_FAIL) # risk_table 原樣放，不要自帶 ## 標題 —— 那一行由步驟 5 寫出， # 它才知道自己在第幾層。 return contract.code_review_parsed(risk_table=table, review_result=verdict)

怎麼新增一個 device？
照這個順序
1

cp -r device/_template device/ssd

沒放的擴充腳本會用哪一份？
假設 PPS_DEVICE=ssd，這一筆 MR 的標題是 [PPS-1234][Bug] 修正重試上限，擷取出來的種類是 bug。
而 ssd 的資料夾裡只放了兩支：
device/ ├── default/ 五支都在，誰都可以退到這裡 └── ssd/ ├── summary.py ③ 覆寫了 └── bug/ └── merge_to_md.py ⑤ 只有 bug 這種 MR 用

那這一筆 MR 的五支，各自會用到哪一份：

步驟 device/ssd/bug/ device/ssd/ device/default/
②jira_key 不看種類 — jira_key.py
②mr_type 不看種類 — mr_type.py
③summary — summary.py summary.py
④parse_code_review 不看種類 — parse_code_review.py
⑤merge_to_md merge_to_md.py — merge_to_md.py

一列一支，由左往右找，第一個有檔案的就用。
五支各找各的 —— 覆寫一支，不會影響其他四支。

最左邊那一欄只有 ③ ⑤ 用得到。
② 的兩支跑在種類出來之前（bug 就是它們判出來的）， ④ 則是刻意不分種類。

⚠️ 沒有 default/bug/ 這一欄， 也不會有。
種類名稱是各 device 自己的字彙，你的 bug 不保證等於別人的 bug。

「不分種類那一份」是指直接放在 ssd/ 底下、沒進種類資料夾的那幾支：

device/ssd/ ├── summary.py 不分種類那一份，什麼種類都用它 └── bug/ └── merge_to_md.py 只有 bug 這種 MR 用

所以種類擷取不到時，整個跳過 ssd/<種類>/ 那一層，直接用 ssd/；ssd/ 也沒放才退到 default/。

⚠️ 不合法的字串（緊急、bug fix） 視同沒有種類，不會報錯 —— 那是 MR 作者打的字，不是部署問題。
要讓它變成錯誤的話，在 __init__.py 宣告 STRICT_TYPE = True。

code review 報告怎麼判定通過？要換規則怎麼寫？
DEFAULT 的做法
規則
在 ## 風險評估總表 那一節取第一張表， 最後一欄當數量，加總為 0 就是 pass
範例
| 類別 | 風險等級 | 數量 | | 記憶體 | 高 | 0 | 加總 0 → pass | 執行緒 | 中 | 2 | 加總 2 → fail
當 0
純數字當數量；-、—、無、 N/A、none、空白一律當 0 —— 報告常用這幾種寫法表示「這一列沒有項目」，不收的話一張正常的表 會因為一個破折號就判不出結論。
整張表只有表頭、一列資料都沒有，同樣是 0，也就是 pass。
報錯
3 件、~5、>10 這種帶了字的寫法一律報錯，不猜 —— 猜錯的方向是把一份有風險的審閱判成通過，而報告上看不出來。
某一列的欄數與表頭對不起來時同樣報錯，不拿最後一格將就。

💡 只是節名不同的話不必寫擴充腳本 —— 在 __init__.py 宣告 CODE_REVIEW_SOURCE_HEADING 就好。
