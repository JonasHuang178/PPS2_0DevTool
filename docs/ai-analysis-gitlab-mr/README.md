# AI Analysis GitLab MR

> 這個功能的細節：畫面、五步流程、報告長什麼樣、產物與設定。
>
> - 要寫自己的 device（客製分析邏輯與報告版面）→ [device-authoring.md](device-authoring.md)
> - 要不開 Qt 跑（命令列或 CI）→ [cli.md](cli.md)
> - 工具的整體架構 → [最外層 README](../../README.md)
> - 規格 → [`openspec/specs/ai-analysis-gitlab-mr/spec.md`](../../openspec/specs/ai-analysis-gitlab-mr/spec.md)

在工具裡瀏覽某個 GitLab 專案的 Merge Request，挑一筆交給 AI 分析，結果以
markdown 呈現在結果視窗。

> **目前的狀態**：五個步驟都已連上真正的來源。第 1、2 步連 GitLab；第 3 步連
> GitLab（取差異）、JIRA（取議題內容）與 AI 服務；第 4 步連 JIRA（取附件）；
> 第 5 步沒有外部依賴。
>
> 沒設定 AI 端點時第 3 步不會失敗，而是產出替代內容，並在首行言明未經過 AI ——
> 開發期還沒有端點時整條流程仍要能跑完才驗得到。

分析單位是**一個 repo 的一個 MR** —— 兩個清單都是單選。

## 行為

**進入這個分頁不執行任何腳本。** Repository 清單來自設定檔，Merge Request 清單
一律由使用者按重新整理才取得。與 Single Building 的「進入即載入」相反：這裡每次
載入都是一次網路請求，照做的話每次切到這個分頁都會被一個互斥的對話框擋住。

**切換 repository 或改動查詢條件會清空 MR 清單。** 否則畫面上顯示的是前一個
repository 的 MR，而按下 AI Analysis 時採用的卻是當前選取的那一個。

**`AI Analysis` 在條件不足時停用，且不說明原因** —— 與 Single Building 的既有
作法一致。條件是：選了 repository、指定了 MR、（勾了除錯時）存放目錄非空、
（選了手動 JIRA 時）key 非空。

**手動輸入的 MR 編號會自我修正。** 貼上 `!123` 或一整條 MR 網址都會被收斂成
編號 —— 使用者最自然的動作就是從瀏覽器複製。

## 兩個顯示過濾器

`Filter` 群組裡的兩個過濾器作用於**已經取回的那批資料**，所以它們與
`Merge Request Parameter` 是兩個分開的群組 —— 後者改動會清空清單並需要重新取得，
前者立即生效且不發出任何請求。

| | 作者 | 標題排除 |
|---|---|---|
| 候選／輸入 | 自該次取回的資料推導，顯示 `名稱 (筆數)`，可複選 | 三個欄位（開頭／結尾／包含），各自逗號分隔多筆 |
| 生效時機 | 勾選即時 | **輸入結束**（Enter 或移開焦點） |
| 重新整理後 | 候選重建、選取清空 | 不變 |
| 全空時 | 等同不過濾 | 不排除任何項目 |

兩者之間是 AND，同一欄多筆關鍵字之間是 OR。

**四個欄位排成單一欄的表單**，標籤右對齊在同一欄、輸入控件起於同一個位置：

```
      Author  [候選清單                  ]
 Starts with  [__________________________]
   Ends with  [__________________________]
    Contains  [__________________________]
```

先前是「Author 一塊、三個排除欄位一塊」並排，於是畫面上同時有兩種對齊方式，而人眼會先看到
那個落差、再看到內容；候選作者少的時候，固定高度的清單框下半部還是空的。代價是群組比先前高、
表格矮一截 —— 該群組預設收合，展開是使用者主動要求看它的時候。

**關鍵字一律是字面文字。** 不支援萬用字元也不支援正規表示法 —— `*` 與 `?` 都當普通字元
比對，與 Single Building 的過濾同一條慣例。想精確藏掉 WIP 就把方括號打進去（`[WIP]`），
那比「開頭」模式更準，也不會誤中 `修正 WIP 流程的說明` 這種標題。

**比對區分大小寫。** 失敗方向比較安全：打錯大小寫的後果是「該藏的沒藏起來」，看得見；
不分大小寫則可能藏掉不該藏的，看不見。

**每一筆關鍵字會去掉頭尾空白，空的關鍵字一律丟掉。** 後者不是細節 —— 空字串是所有標題的
子字串，不丟的話一個多餘的逗號就會讓整張表格一筆不剩，而畫面上看不出成因。使用者打字打到
`skip,` 那一瞬間正是這個情況。逗號是分隔符，所以**關鍵字本身不能含逗號**。

**過濾條件一改就清空表格的選取。** 否則使用者可能在看不見那一筆的情況下按下 `AI Analysis`，
而整條流程會對著一筆他看不到的 MR 跑完並回報成功。選取一空，`AI Analysis` 自動停用。

**`Filter` 預設收合**，但那行統計**留在摺疊之外** —— 收合時仍然看得見「共 60 筆，顯示 48」。
這一點是刻意的：排除規則的預設值來自設定檔，所以使用者可能**什麼都沒做**就有 MR 不顯示；
統計跟著收起來的話，那件事就徹底隱形了。

達到單次取回上限的提示也在同一行持續顯示，不再跳一次性的訊息框。達到上限意味著**某些作者
根本不會出現在候選清單裡**，而使用者正是在按掉那個框之後才開始在候選裡找人。

## MR 表格的欄寬

標題欄是唯一會伸縮的，其餘四欄固定。固定的那幾欄的寬度是**量出來的**（以表格實際的字型量
內容加儲存格內距），不是估的 —— `merged` 要 74、`Jonas Huang` 要 114，而原本的 70 與 110
各差幾像素，於是**每一列**都被截斷，狀態欄更是四種值在畫面上都變成 `…`。

| 欄位 | 寬度 | 為什麼 |
|---|---:|---|
| MR | 60 | 編號 |
| Status | 85 | 容得下最寬的 `merged`，留一些給別的字型與 DPI |
| Title | 伸縮 | 掃視時真正在看的那一欄 |
| Author | 150 | 容得下「名 姓」這種常見長度 |
| Created | 115 | 日期加排序指示器的箭頭 |

**Author 刻意不追求容得下所有名字。** 再長的名字永遠存在，而固定欄每多一像素，標題欄就少
一像素。截斷的那幾筆靠**提示文字**補上全名 —— 沒有提示文字時，「這一欄放不下」就等於「這個
資訊看不到」，那才是真正的缺陷；寬度只能讓截斷少發生。

Status 不設提示文字：四種值現在全部放得下，加了只是每次滑過都跳出一個與畫面上一模一樣的字。

## MR 表格的預設排序

每次載入（重新整理、或查詢條件改變而重建表格）都回到**依 Created 由新到舊**。使用者要挑的
幾乎都是最近那幾筆；沒有這一行的話，Qt 會依表頭預設的第 0 欄遞增排，第一列是編號最小、
也就是最舊的那一筆。

排序依的是資料裡的**完整時間戳**，畫面只顯示到日 —— 否則同一天的多筆排不開，而最近的那
幾筆常常就在同一天。

使用者自己點欄位改排序仍然有效，那個選擇留到下一次重建為止。重建是一批新資料，回到預設
才可預期。

設定寫在 `applyMrHeaderLayout()` 的最後一行，與欄寬同一個地方 —— `QStandardItemModel::clear()`
會讓表頭重新初始化，排序指示器跟欄寬一樣會被打回預設，所以兩者本來就必須在同一個時機重設。

> `Created` 欄寬是 115 而不是剛好容得下日期的寬度：那一欄現在固定帶著排序指示器的箭頭，
> 箭頭佔的是欄內的寬度，90 的話 `2026-09-30` 會被截成 `2026-0…`。

## MR 表格的對齊

四個固定寬度的短欄位（MR、Status、Author、Created）置中，**Title 欄靠左**，五欄都垂直置中。

短欄位靠左會在右側留一片空白，與置中的表頭對不齊；Title 欄則相反 —— 它是唯一的長文字欄，
置中之後每一列的起點隨標題長短而異，一整排掃下來是跳的，而那一欄正是用來挑出要分析的那一筆
的。表頭維持置中（表頭是標籤，掃視時看的是內容那一欄的起點）。

對齊在建列的那個迴圈裡**以一條規則一次套用**，不逐欄分開設 —— 逐欄設的話，日後新增一欄就會
漏掉，而漏掉的症狀看起來像是沒對齊，不像是少寫了一行。規則的預設是置中，Title 欄是唯一的
例外。表頭不必另外設：`QHeaderView` 的水平表頭預設就是置中。

Title 欄用的是 `AlignLeft | AlignVCenter`，不是 `AlignLeft` —— 後者的垂直方向未指定，文字會
貼著儲存格頂端，與其餘四欄差半行。

## 連按兩下開啟 GitLab

| 位置 | 開啟 | 網址來源 |
|---|---|---|
| MR 表格的**標題欄** | 該筆的 Merge Request 頁面 | 取得清單那一步回傳的 `web_url` |
| Repository 清單的項目 | 該專案的 GitLab 主頁 | `Service.Gitlab_Server_URL` + 專案路徑 |

標題欄以連結的外觀呈現（藍字加底線，滑過變手形游標），而**只有標題欄會開頁面** ——
外觀把範圍講清楚了，所以不需要解釋「為什麼雙擊作者欄沒反應」。

**單擊不開啟**，只選取。單擊必須留給選取，那是按下 `AI Analysis` 的前提；單擊即開會讓
「只想選一筆」變成不可能。這個落差寫在標題欄的 tooltip 裡。

`Gitlab_Server_URL` 沒設定時，連按兩下 repository 會跳錯誤訊息框**點名那個設定鍵**，而不是
開一個組不完整的網址 —— 瀏覽器只會說「找不到伺服器」，那句話指不出要去改執行檔旁的設定檔。

**選取中的那一列，標題欄仍然是連結色。** 這需要一個只掛在標題欄的委派自己畫文字：項目的
`ForegroundRole` 只覆寫 `QPalette::Text`，而選取時畫的是 `HighlightedText`，再被外殼那條
`QTableView::item:selected { color: … }` 蓋掉。只改 palette **沒有用**（量過像素），因為
`QStyleSheetStyle` 的覆寫發生在委派交出 option 之後。

委派讓樣式照常畫背景與選取高亮，只把文字留給自己 —— 所以整列仍然整列高亮，標題欄不會被挖掉
一塊。使用者按下 `AI Analysis` 之前必然先選取某一列，所以「選取中」正是他最可能想點開那個
頁面的時候。

## 分析流程

按下 `AI Analysis` 啟動一條**固定五步**的流程：

| 步 | 腳本 | 產物 |
|---|---|---|
| 1 | `..._description.py` | MR 描述 |
| 2 | `..._info.py` | `jira_key` 與 `mr_type`（自行連 GitLab 取 MR 一次，兩個鉤子各自抽） |
| 3 | `..._summary.py` | AI 分析結果 |
| 4 | `..._code_review.py` | 風險評估總表與審閱結論（自 JIRA 議題的附件取得，由 device 的 `parse_code_review` 鉤子解析） |
| 5 | `..._merge_to_md.py` | 合併後的 markdown |

**五步全部執行，Qt 端不跳過任何一步。**「要不要真的做事」由腳本看參數決定
（例如第 4 步收到的 `jira_key` 為空、或 `jira_state` 不是 `ok` 時就不發任何請求、
回報成功且不落檔）。這是為了讓同一批腳本能被 CI/CD 的 shell 直接串接 —— 分支若寫在
Qt 端，CI 那側就成為第二份編排實作，兩份必然漂移。

可照抄的 pipeline 範例在 `ci/pps-ai-analysis.gitlab-ci.yml`，說明見 [cli.md](cli.md)。

**第 4 步刻意沒有「要不要取」的布林開關。** 由 `jira_key` 與 `jira_state` 兩個值同時
承載「要不要做」與「對誰做」，就不會出現「開關為真但沒有 key」這種自相矛盾的狀態。
`jira_state` 來自第 3 步 —— key 的有效性是那個 device 的政策、由它的鉤子判定，Qt 只是
原樣轉送，不重判。

**腳本路徑固定寫死在 C++**，不取自任何步驟的回傳資料。哪一段運算因 device 而異，
由環境變數 `PPS_DEVICE` 決定（見 [device-authoring.md](device-authoring.md) 的「device」一節），同樣不取自回傳資料。

**「種類」是這條規則的明確例外。** 它由第 2 步從 MR 解出來（多半是標題），再決定第 3、5
步用哪一份鉤子 —— 也就是說，MR 標題會影響載入哪個模組。範圍是收死的：名字必須通過
`^[a-z_][a-z0-9_]*$`（擋掉路徑穿越），而且必須對應到一個**已經部署在該 device 底下**的
目錄。所以標題只能在既有的選項之間挑，帶不進任何新的程式碼，也指不到別的位置。

**任一步失敗即停**，以一個錯誤訊息框指出第幾步與該步腳本寫的原因，畫面不變。

**`## 詳細資料` 只在這次真的用了 JIRA 議題時出現。** 條件是分析結構裡的 `jira_state`
為 `ok` 且 `jira_key` 非空 —— 也就是步驟 3 採用了那張單子：

| `jira_state` | 意思 | 這一節 |
|---|---|---|
| `ok` | 採用了那張單子 | **出現** |
| `none` | 沒有要用 JIRA | 不出現 |
| `invalid` | 抽到字串但不是 key（例如標題第一個方括號放成 `[WIP]`） | 不出現 |

組不出網址時（沒設 `Service.Jira_Server_URL`）仍然印出 key 的文字，只是不做成連結 ——
知道是哪一張單子，比因為做不成連結就整節消失有用。

分析本身什麼內容都沒有時，連這一節也不放：它是對其他內容的註解，單獨存在時產出的是一份
只說「詳情請看別處」的報告。這與涵蓋範圍不計入「是否有可合併的內容」是同一條規則。

> **這是報告裡唯一提到那張單子的地方。** 出處那一段曾經印過 `JIRA: <key>`，後來移除了
> （理由見該輪：那個形狀讀不出它是一個入口），所以 key 一度只存在於產物的資料裡。另外要注意**它不負責「抽錯了」那個訊號** —— `invalid` 在報告上目前完全不可見，
> 而持續整合環境只跑自動抽取，正是唯一會抽錯的模式。
>
> 這一節住在 device 的 `merge_to_md` 鉤子裡，所以**有自己那一份的 device 不會自動獲得
> 它**，要的話得自己寫（判狀態、取 key 與 url、組一行）。

幾個不是隨手決定的地方：

**四個 `#` 標題都由步驟 5 寫出**，步驟 1 與步驟 4 的產物都不冠標題。標題屬於
報告不屬於描述 —— 冠在步驟 1 的產物上，那一行會跟著報告被貼回描述，下一輪再讀進來；
而步驟 4 自帶標題的話，它無從知道自己會被放在哪一層。

**`# Code Review 報告` 與 `# AI 分析結果` 同層。** AI 分析那一段的**內容**用的是 `##`
（`## Summary`、`## Code Changes`），所以 code review 若也用 `##`，在畫面上就會跟那些
內容並列，讀起來像是分析的一部分 —— 而它在語意上與分析並列，不從屬於它。

**多行的地方不靠「段落內的換行」。** markdown 的段落內換行是**軟換行** —— 轉譯後變成一個
空白，於是多行擠成一行。報告裡有兩處是多行的，各用了適合自己形狀的寫法：

| 哪裡 | 寫法 | 為什麼 |
|---|---|---|
| 審閱的日期／作者／連結 | 引言裡的**清單項目** | 它們是一組欄位，清單本來就是這個形狀 |
| 末尾出處的四行 | 一個 `<sub>` 包住，中間以 `<br>` 斷開 | 整段是同一則出處，只是縮小的四行文字 |
| 一筆發現的理由 | 該筆之下的**子清單**（縮排兩格） | 幾句都在講這一筆，子清單讓歸屬看得出來 |

**不用「行尾兩個空白」**（markdown 的硬換行寫法）—— 它是看不見的，編輯器、linter 與貼上
動作都會清掉行尾空白，而那一段的正確性就靠它。一個看不見又隨時會被清掉的正確性等於沒有。

> 每一筆發現底下的理由**先前是例外**（刻意讓 GitLab 把它併進該筆 bullet 的同一段）。
> 現在它與總覽用同一套斷行，斷得出兩句以上時就是該筆之下的子清單，不再依賴併段。只斷得出
> 一句時仍是縮排的一行 —— 那一行沒有要被斷開的地方，所以併段與否都讀得下去。

**指向同一個位置的多筆發現收在一起，那段 diff 只貼一次。** 模型常把同一段程式碼拆成
數筆來講（「這裡調高了上限」、「這會拖長失敗時間」），各附一次的話同一段 diff 會一字不差
地重複出現，讀的人得自己比對才知道那是同一段。

三筆同一個 `hunkHeader` 的 `code_changes`，報告長這樣 —— **diff 在該組的最後一筆**：

````markdown
### 1. `File1.cpp`

- Title1
  reason1。
- Title2
  reason2。
- Title3
  reason3。
  <details>

  ```diff
  @@ -312,4 +321,24 @@ void File1::Init()
  -    old();
  +    newA();
  +    newB();
  ```
  </details>
````

前兩筆同一個位置、第三筆指向另一個位置時，就是兩組，各自的 diff 在各組最後：

````markdown
- Title1
  reason1。
- Title2
  reason2。
  <details>

  ```diff
  @@ -312,4 +321,24 @@ void File1::Init()
  ```
  </details>

- Title3
  reason3。
  <details>

  ```diff
  @@ -400,8 +410,30 @@ void File1::Run()
  ```
  </details>
````

- **diff 放該組的最後一筆** —— 整組要講的幾件事先讀完，再看它們共同指向的那段程式碼。
  這與「diff 不得落入理由最後一行之下」不衝突：收合區塊縮排兩格，是該筆理由子清單的
  **兄弟**，仍隸屬於該筆發現
- **分組的鍵是模型回的 `hunkHeader`，不是切出來的 `diffCode`。** 位置解析不出來時
  `diffCode` 全是空字串，那幾筆就無從分辨彼此 —— 而「位置寫歪了」恰好是最需要分組的情況
  之一（新增檔案的標頭最常被寫歪）。鍵的取法三層：讀得出行號就用那組行號（帶不帶
    函式名、結尾那對 `@@` 在不在都算同一個）；讀不出但字串非空就用原字串；兩者皆無則退回
  `diffCode`（版本 5 以前的產物沒有 `hunkHeader`）
- **位置用 `contract.hunk_range_of()` 的寬鬆讀法比，不用嚴格的 `hunk_header_of()`。**
  模型對新增檔案常回 `@@ -0,0 +1,433`（掉了結尾的 `@@`）—— 嚴格讀法會把它當成「沒給位置」，
  於是那幾筆各自成組，而那正是這個功能要處理的情況。寬鬆讀法連它一起認，而且把省略的行數
  補成 1，所以 `@@ -1 +1 @@` 與 `@@ -1,1 +1,1 @@` 也併得起來
- 模型交錯著講（第一個位置、第二個、又回到第一個）時，**同一個位置的幾筆會被收到一起**，
  各組依首次出現的次序排列。必須如此 —— 中間各筆是靠「與最後那一筆相鄰」表達它們講的是
  同一段
- **既沒有位置標示也沒有 diff 的那些不會被併成一組。** 它們之間沒有任何可比對的東西，
  併在一起只是因為「都是空的」
- 這一段住在 device 的 `merge_to_md` 鉤子裡，所以**有自己那一份的 device 不會自動獲得
  它**（與 `## 詳細資料` 同理）

**Code Review 那一段刻意只放總表。** 全文留在 JIRA 上那份附件裡，靠 `>連結:` 那一行
回去看。四行資訊裡值為空的那一行整行不印；日期只取到日，不做時區換算（印出的就是
上傳者當時看到的那一天）。

```
# Code Review 報告

> - 結果: ❌ FAIL
> - 日期: 2026-09-10
> - 作者: Jonas
> - 連結: CodeReview_20260910_092900.md

## 風險評估表

| 類別 | 風險等級 | 數量 |
...
```

**結果那一行排在最前面。** 日期／作者／連結是「這份東西從哪來」，而結果是「它說了
什麼」—— 讀的人要的是後者，排在出處後面等於要他先讀完三行才看到結論。判不出來時那一行
整行不印。

**default 的判定規則：風險評估總表的最後一欄是數量，全部列加總為 0 判定通過。**

- 加總而不是逐列檢查，因為「有沒有任何項目」正是那張表要回答的事
- **合計列不必偵測。** 數量不會是負的，所以重複計算不可能翻轉結論：全 0 時重複加還是 0，
  有非 0 時重複加還是非 0
- **不檢查最後一欄的標題文字。** 各 device 的欄位名不保證相同（數量／Count／件數／個數），
  而這一份是 default —— 寫一張字彙表的結果是某個沒列到的詞被誤判成「不是數量欄」。真正
  要的是「能不能加總」，直接看值就知道；錯誤訊息會印出實際讀到的標題與那一格的內容
- `-`、`–`、`—`、`N/A`、`無`、空儲存格都當 **0**。中文文件很常用這些表示「沒有」，不收
  的話一張完全正常的表會因為一個破折號而判不出結論
- `3 件`、`~5`、`>10` 一律**不收**。收了就得猜那個修飾詞是什麼意思，而猜錯會讓一筆有
  風險的審閱被判成通過
- 一列資料都沒有（只有表頭與分隔列）也是 0，也就是 pass —— 那張表的意思就是「沒有需要
  列出來的項目」

**取不到總表時那一段仍然出現**，內容換成一行 `⚠️` 訊息，而日期／作者／連結**照樣印**
—— 那時連結的價值最高，讀者點進去就能自己看全文。只有「沒有 JIRA key」「key 無效」
「議題上沒有符合的附件」三種情況才整段不出現，因為那些是「這筆本來就沒有」而不是
「取失敗了」。

**鉤子失敗不中斷流程，而訊息分三種** —— 該去改的東西不同：

| 情況 | 報告上那一行 |
|---|---|
| 文件不合約定（`RiskTableError`） | `⚠️ 風險評估總表最後一欄「備註」的第 1 列是 '已確認'，不是數量` |
| 鉤子載不進來（語法錯、import 失敗） | `⚠️ device ssd 的 parse_code_review 有語法錯誤（檔名與行號）` |
| 鉤子的程式錯誤（任何其他例外） | `⚠️ device ssd 的 parse_code_review 執行失敗：KeyError: 'rows'（這是該 device 的腳本問題，不是來源文件的問題）` |

後兩種要**點名 device 與鉤子**。沿用第一種的句子的話，使用者會跑去查 JIRA、查權限、查
附件在不在 —— 全都沒問題，真正該改的是那支腳本。完整的 traceback 進除錯輸出的
`code_review_hook_error.txt`。

入口攔 `Exception` 而不只攔 `RiskTableError`：鉤子是使用者寫的，一個 `KeyError` 不該殺掉
一份已經完成、已經付費的 AI 分析。回傳值的形狀也在入口擋 —— 讓一個缺鍵的 dict 流到下游，
症狀會是報告裡那一段安靜地空白。

> ⚠️ **判不出結論時表格也不會進報告。** 鉤子為此 `raise`，而入口收到例外就不落檔，所以
> 報告上只有那一行 `⚠️`。這是明知的取捨：好處是「有結論」與「沒結論」不會混在一起，
> 代價是一張擷取成功的表格會因為最後一欄加不起來而消失。

**搜尋用與渲染用是三個各自獨立的常數**（都在 `ai_analysis_gitlab_mr/__init__.py`）：

| 常數 | 用途 | device 可覆寫 |
|---|---|---|
| `CODE_REVIEW_SOURCE_HEADING` | 在**附件那份文件**裡找總表那一節（預設 `## 風險評估總表`） | ✅ |
| `CODE_REVIEW_HEADING` | 寫進**報告**的段落標題 | ❌ |
| `CODE_REVIEW_TABLE_HEADING` | 寫進**報告**的總表小標題 | ❌ |

不合成一份是刻意的：改我們報告的小標題不該影響去別人文件裡搜尋什麼，反之亦然。
這與 `AI_HEADING` 剛好相反 —— 那一個同時是「寫出去」與「切回來」的同一個邊界，所以
**必須**只有一份來源。

**總覽與每一筆發現的理由都排成逐行的清單。** AI 回來的總覽是一句接一句的**一整段**
（prompt 要的就是「三到五句」），每一筆發現的理由也是，而且通常更長。那一段在結果視窗會
依寬度折成一片文字牆，貼到 GitLab 則是一個段落 —— 兩邊都難以掃讀。斷行依來源的形狀決定，
三條互斥、先到先用：

| 來源的形狀 | 報告上 |
|---|---|
| 已經含有換行 | 原樣，一個字都不動 |
| 同一行內自帶由 1 起算、連續遞增的編號 | 保留編號，逐行排成 `1. ` `2. `（`1、`、`1)`、`(1)` 正規化成 `N. `，否則 GitLab 不認） |
| 以上皆非 | 依全形句末標點斷開，逐行排成 `- ` |
| 只斷得出一段 | 原樣（單項清單是噪音） |

**只認全形 `。！？`。** 半形那三個幾乎都是誤切 —— `.` 出現在 `v1.0`、`0.5`、`e.g.`，
`!` 出現在 `!7` 這種 MR 編號，`?` 出現在查詢字串。整個方案能成立就是靠全形句號不會出現
在數字或識別碼裡。

**有序編號必須「由 1 起算、連續遞增、至少兩個」，且編號後面不可緊跟數字。** 這兩道守衛
把版本號這個最可能的誤判來源消掉：`版本 1.0 與 2.0 都要測` 不會被切成兩點。

**接著在每一行之內，全形冒號之後補一個 `<br>`。** `：` 在模型的回覆裡幾乎都是「標籤：
內容」的分界（`原因：逾時從 3 秒拉到 30 秒`），那兩半是不同層次的東西，擠在同一行時標籤
會被內容淹掉：

````
- 調高了重試上限：<br>從 3 次改成 10 次。
````

渲染後是兩行，而那一筆仍是同一個清單項目。

- **只認全形 `：`，理由與句末標點完全相同。** 半形的 `:` 出現在 `C:\build`、`http://`、
  `10:30`，以及 `Api_URL` 用來切 shareCode 的那個分隔冒號 —— 認它就是在這些地方全部切壞
- **用 `<br>` 而不是 markdown 原生的「行尾兩個空白」。** 理由是縮排：理由排成縮排兩格的
  子清單，而行尾空白那種寫法要求續行自己對齊縮排，對不齊就變成新段落 —— 而插入換行的時候
  還不知道外層會縮幾格。`<br>` 是行內元素，縮多少格都成立。行尾空白另外還會被編輯器、
  linter 與 `strip()` 清掉，而清掉之後看不出曾經有過
- **三種情況不補**：冒號在結尾（補了只是懸空的換行）、後面已經是 `<br>`（模型自己寫了，
  不疊第二個）、連續數個冒號（整串當一個分界，只補一次）。補完會把緊跟的空白吃掉
- **不套用在「來源已自帶換行」那一條。** 那條分支存在的理由就是來源自己做過版面決定了，
  在它的行裡再插入換行正是覆寫那個決定

**斷行在步驟 5 做，產物裡的 `overview` 與 `reason` 完全不動。** 產物存的是 AI 說了什麼，
版面由它推導 —— 改掉原文之後，想換一種版面就只能重新花錢問一次 AI。附帶的好處是**既有的
`03_summary.json` 重跑步驟 5 就會變好看**。實作是 `contract.as_list()`，總覽與理由共用
同一個函式，device 的鉤子也可以直接用。

**理由的子清單縮排兩格，不是四格。** 量過兩個轉譯器，結論不一致，只能選一邊：

| 縮排 | CommonMark（GitLab） | python-markdown |
|---|---|---|
| 兩格 | 子清單正確巢狀，`<details>` 與它同層、仍掛在該筆發現之下 | 不認巢狀 —— 理由各句被拉成與標題同層 |
| 四格 | 同樣正確 | `<details>` 被吸進子項目，圍籬變成行內程式碼，**diff 整段壞掉** |

選兩格：報告的目的地是 GitLab，兩格在那裡兩件事都對；而四格在 python-markdown 下壞掉的
是 diff，比「清單少一層巢狀」嚴重得多。

**diff 與理由的子清單同層**，隸屬於該筆發現。縮排錯一層的話收合區塊會掛在最後一句底下，
讀起來像是只有那一句才有對應的程式碼。沒有標題的發現則各句直接當該筆的條目 —— 那時子清單
沒有父項可依附，多包一層會變成一段縮排卻沒有歸屬的文字。

**`# AI 分析結果` 同時是切段的邊界。** 步驟 1 靠它把上一輪的分析從描述裡切掉，所以
「寫出去的字串」與「切掉用的字串」只有一份來源（`__init__.py` 的 `AI_HEADING`），
比對式也是由它導出。改標題只要改那一行 —— 但既有描述裡若還留著舊標題就切不掉了，
代價與補救見 design.md 決策二十四。

**每次執行全部重新生成，只有原始描述被保留。** 把整份報告貼回 MR 描述再跑一次，
舊的分析與出處會一起被切掉重產，不會累積。

**末尾的出處是一段縮小的文字，四行各回答一個問題：**

| 行 | 回答 | 沒有內容時 |
|---|---|---|
| `Device` | 用哪一套實作（含種類） | 整行不出現 |
| `腳本` | 哪一版通用骨架 | **永遠都在** |
| `AI` | 哪個模式、哪個模型 | 整行不出現 |
| `產生方式` | 誰在哪裡產生的（工具／CI 的 pipeline 與 commit） | 整行不出現 |

報告被貼到討論串之後就脫離了產生它的環境，`腳本` 那一行是「這份分析是哪一版產生的」唯一的
答案，所以它永遠都在。改了報告的產出方式，請把 `SCRIPT_VERSION` 的第二碼加一（見「腳本的
版號」）。

**兩個版號並列**：`Device` 那一行是該 device 的，`腳本` 那一行是通用層的。第一碼一致代表
同一代；不一致時讀的人自己對照得出來 —— 程式不擋也不加標記。

**斷行用 `<br>` 而不是真的換行**：段落內的換行是軟換行，轉譯後會變成一個空白，四行會
擠成一行（與審閱那三行是同一個坑）。`<br>` 是明確的斷行，在任何轉譯器下都成立。

**整段只有一個 `<sub>`，包住四行**。轉譯後是單一個 `<p><sub>…<br>…</sub></p>`：`<sub>`
與 `<br>` 都是 inline，inline 包 inline 巢狀合法，段落裡的 `**` 與反引號照常轉譯。先前
一行一個 `<sub>` 是因為那時各行是**清單項目**，而 `<sub>` 包不住清單這種 block 元素
（外層包法產生 `<p><sub></p>…<p></sub></p>`，兩個孤兒標籤多半被 sanitizer 丟掉：字沒有
變小，但你以為有）。清單消失之後這個限制就不存在了。這兩件事都是量過轉譯結果才確定的。

**分隔只用 ASCII**：標示與值之間一個半形空白，同一行內兩組值之間 ` | `（與 CI 那一行
本來就在用的分隔一致）。先前用的全形空白、`·` 與全形斜線 `／` 在等寬字型下寬度不定，
貼到 GitLab 也不保證照原樣保留，而它們做的事半形字元就做得到。

> 出處**不再顯示 JIRA 與涵蓋標示**。涵蓋的損失有限 —— 有缺口時「分析涵蓋範圍」那一整段
> 仍然會出現。JIRA 則有真實損失：持續整合環境只有自動取得一種模式，而那正是唯一會抽錯的
> 模式，移除之後一個抽錯的 key 在 CI 上沒有任何地方看得見。這是明知的取捨；要補回來的話，
> 最小的做法是「只在 invalid 時顯示」。


**diff 收在 `<details>` 裡。** 一筆 finding 的 diff 可能幾十行，攤開會把報告的可讀性
吃掉。`<details>` 之後那個空行是必要的，少了它 GitLab 不會把裡面當 markdown 解析。

> 結果視窗是 `QPlainTextEdit`，**不渲染 markdown** —— `<details>` 與連結在工具裡都是
> 原樣的文字，收合也不會發生。這個排版是為了「貼到 GitLab」那一側。

## diff 取不到內容：GitLab 的收合

GitLab 的 diff 大小限制比直覺低得多 —— **單一 patch 到門檻的 10%（預設 200 KB 的 10%，
約 20 KB）就會被「收合」**，而收合的檔案在 API 回來的 `diff` 欄位是**空字串**。網頁上看得到
是因為它點開才另外載入。

症狀很好認：送進 prompt 的差異只剩幾行檔名。

```
diff --git a/src/a.cpp b/src/a.cpp
diff --git a/src/b.cpp b/src/b.cpp
```

工具的處理分三段：

| | 做什麼 |
|---|---|
| 正常 | 走 `/diffs`，不多打任何一次 API |
| 出現空內容 | 改以 `/changes` + `access_raw_diffs=true` 重取（直接向 Gitaly 取，不受資料庫端的限制），**兩者取內容較多的一份** |
| 重取仍然一行內容都沒有 | **步驟 3 失敗，不送進 AI** |

**為什麼不一律走 `/changes`**：它已標記為 deprecated（API v5 移除），而且較慢、較耗資源。
`/diffs` 則**沒有任何參數**可以繞過收合 —— 它只吃 `page`、`per_page`、`unidiff`。

**為什麼重取之後要比較、不無條件採用**：`access_raw_diffs` 有已知缺陷，在某些版本上它自己也
回空的。比較「有內容的檔案數」再決定，重取失敗時至少不會比原本更糟。

**為什麼沒有內容時要失敗**：對著幾行檔名做出的分析看起來完全正常 —— 模型會給出流暢的總覽與
發現，而它沒有看過任何程式碼。讓它成功交出去比失敗糟得多，因為使用者不會知道要懷疑它。
訊息會指出成因，並說明這是伺服器端的設定（管理者在 Admin → Settings → General → Diff limits
調整）。

> `/diffs` 的每頁筆數是 **30**，不是其他清單用的 100：多個 GitLab 版本在這個端點收到大於 30
> 的 `per_page` 時直接回 500。而那個 500 不會觸發退回 `/changes`（退回只在 404 時發生），
> 所以它會變成一個指不出原因的「GitLab 查詢失敗」。

## 分析涵蓋範圍：報告少了檔案時怎麼看

一支改了 90 個檔案的 MR，`## Code Changes` 卻只有兩三個檔案 —— 這份報告要能說出那是
為什麼。缺口分四類，**每一類的下一步完全不同**，所以分開列，不合成一個比例：

| 報告上的那一行 | 意思 | 怎麼處理 |
|---|---|---|
| N 個檔案的差異超過送出上限，沒有送進分析 | 差異太大，整個檔案沒進 prompt | 調高 `MAX_PROMPT_DIFF_BYTES`，或分批（尚未實作） |
| N 個檔案的差異內容是空的 | 二進位檔、只有模式變更，或 GitLab 沒給內容 | 多半無能為力；GitLab 自身的 diff 上限要在伺服器端調 |
| N 個檔案已送進分析，但 AI 沒有回報 | 模型**完全沒提到**那個檔案 | 調 prompt，或換模型 |
| N 筆回報的路徑在差異中找不到對應的檔案 | 模型給了一個不存在的路徑 | 調 prompt（通常是它自己編了檔名） |

另外還有第五類，**不算缺口**：

| 報告上的那一行 | 意思 | 怎麼處理 |
|---|---|---|
| N 個檔案依設定排除，沒有送進分析 | 命中了三個 `Skip_*` 設定之一（見「不必分析的檔案」） | 要改設定，或什麼都不必做 |

它與上面四類並列但性質不同：那是**你的決定**，不是機制失手。所以沒有 ⚠️，`has_coverage_gap()`
也不數它 —— 只有排除、沒有其他缺口時整節不出現（每份報告都加一句「依設定略過 2 個」是噪音，
而那個設定是你自己填的）。但只要有別的缺口，那一節就會順便列出它。

> **這兩類同時出現，幾乎一定是「同一個檔案的路徑寫法對不上」而不是兩件事** —— 模型回的
> 那個路徑沒人認得（進第四類），它本來想指的檔案因此沒人認領（進第三類）。`debug.log` 會
> 把兩邊的實際字串並排印出來：
>
> ```
> 路徑比對失敗：鉤子回報了 ['/dev/null']，而這些送出的檔案沒人認領 ['src/core/xxxx.cpp']
> ```
>
> **新增檔案的 `/dev/null` 是這個狀況最常見的來源，而且是我們自己造成的。** 新增檔案的
> 檔頭是 `--- /dev/null`（由 `_render_file_diff()` 補上，少了它這份 diff 餵給任何吃
> unified diff 的工具都會失敗），而 `OUTPUT_SPEC` 要求模型「檔名要與上面 diff 裡出現的
> 一致」—— 那個哨兵於是成了一個看起來合法的答案。
>
> 兩邊都處理了：`OUTPUT_SPEC` 明說哨兵不是檔名、要用 `diff --git` 那一行的路徑；而
> `parse_reply` 收到哨兵時用 `contract.resolve_reported_path()` 回頭問 diff 把它收斂成
> 真正的路徑（只有一個新增檔案就是它；多個就用 hunk 標頭挑；還是分不出來就原樣留著並記
> 一筆警告 —— 猜錯會把 A 檔案的發現掛到 B 檔案上，而每一步都回報成功）。
>
> 收斂做在 `parse_reply` 這一處，不在下游各個比對點放寬：鍵一改好，涵蓋範圍與
> `hunk_of()` 兩邊自然都正確。留到下游就變成每個讀 `mrDiff` 的地方各認一次哨兵，那是
> 三份會漂移的規則。

幾個不是隨手決定的地方：

**那一段只在有缺口時出現。** 絕大多數的 MR 不會有缺口，每份報告都加一段「涵蓋
21/21」只是噪音。

> 出處那一行**曾經**常駐一個 `Coverage: 3/21 檔案（MR 共 90）`，當作零成本的常駐訊號；
> 重整出處版面那一輪與 JIRA 欄位一起移除了（出處收斂成四問，涵蓋範圍不屬於其中任何一問）。
> 於是**沒有缺口時報告沒有任何涵蓋訊息** —— 失去的只有「一切正常」這個訊號，有缺口時這一段
> 本來就會出現。要補回來的話補在這一段裡，不要補回出處。

**第三類（AI 沒有回報）不等於出錯。** 一個只改了空白的檔案，模型略過它是合理的。
那一行陳述的是事實，不是判定 —— 與另外三類並列，讀的人自己看得出哪一個才是問題。

**「有回報」＝ `mrDiff` 裡有這個鍵，不要求它底下有發現。** 模型老實回
`"a.cpp": []`（這個檔案看過了，沒有值得注意的地方）算**已回報**，不計入第三類 —— 那是
交代過了，不是漏掉。算成漏掉的話，報告會對一個誠實回答的模型指控「AI 沒有回報」，而使用者
照著那個訊息去調 prompt 是找錯方向。

所以 `files_reported`（模型提到的檔案數）與報告裡實際列出的檔案數**可以不同**：後者只有
帶著發現的那些，空清單的檔案在渲染時整個略過、編號也不跳號。要在 log 上分辨這兩件事，
`debug.log` 的 `files=20/2` 就是「提到 20 個、其中 2 個有話說」。

> 這一行曾經寫成 `if items:`（空的整個丟掉），於是涵蓋範圍把「明說沒問題」與「根本沒提」
> 併成同一類。丟掉的理由（底下什麼都沒有的標題會讓人以為內容漏掉了）本身沒錯，但那是
> **渲染**該解決的事，而渲染端本來就是這樣做的。

**數量精確，路徑清單有上限**（`MAX_COVERAGE_PATHS`，預設 50 筆）。超過時清單末尾會
寫「其餘 N 筆未列出」。拿清單長度當數量的話，一支改了幾千個檔案的 MR 會讓報告說
「3 個檔案未回報」而實際上是 3000 個。

**涵蓋範圍由入口腳本算，device 的鉤子不能提供也不能覆寫。** 它正是用來檢查那支鉤子
回報了多少的 —— 讓被檢查的一方提供數字，這個機制就等於不存在。同理，那一段的渲染
也由步驟 5 寫出，不交給鉤子。

**那一段不計入「有沒有東西可合併」。** 它是對其他內容的註解；只有它的話，產出的是
一份只講自己涵蓋多少、而什麼都沒涵蓋的報告。

## 除錯分析檔

勾選 `Add Debug Analysis file` 時，Qt 在流程啟動**前**建立
`<Save_Analysis_File_Dir>/gitlab_mr_result_<repo>_<mr>_<時間戳>/`，並把路徑傳給
每一步。目錄建立失敗（路徑打錯、沒有寫入權限）會在按下按鈕的當下就跳錯誤框，
流程不啟動 —— 不會等到跑完前三步才發現寫不進去。

```
gitlab_mr_result_lw-os_123_20260912_143012/
  01_description.md
  02_mr_info.json
  03_summary.json
  04_code_review.json
  04_code_review_src.md  自 JIRA 下載回來的原始附件（沒取到附件時不會有）
  05_report.md
  ai_prompt.txt        實際送給 AI 的完整 prompt
  ai_reply_1.txt       AI 的原始回覆（每次嘗試各一個檔）
  ai_reply_2.txt       重問過才會有
  bad_analysis.json    鉤子回傳的結構沒通過驗證時才會有
  bad_code_review.json 步驟 4 的結構沒通過驗證時才會有
  debug.log
```

`04_code_review_src.md` **是原始附件、不是擷取結果** —— 擷取到的總表在
`04_code_review.json` 裡。留著它的理由是「擷取對不對」只能拿原文比對；而它自動只在
勾選除錯時存在，因為工作目錄那時**就是**除錯目錄（未勾選時是流程結束後會被整個移除
的暫存目錄），不需要任何額外判斷。

它的檔名固定，**不取自附件本身的檔名** —— 那是上傳者打的字，拿它組路徑與規格禁止
「device 名稱用來組成檔案路徑」是同一類風險，順帶也解決 JIRA 允許同名多筆附件的
覆蓋問題。

**調 prompt 就是看 `ai_prompt.txt` 與 `ai_reply_1.txt`。** 這兩份都不進 log ——
prompt 含整份 diff（也就是原始碼），回覆動輒幾萬字元。除錯檔是唯一看得到它們的地方。

每一次回覆**寫在解析之前**，各自成檔：重問成功不會蓋掉失敗的那一次，而失敗的那次
才是線索。

`debug.log` **失敗時也會寫**，內容是該次失敗的訊息、代碼與細節；鉤子拋出例外時細節
是完整的 traceback。只在成功時記錄的話，最需要那份紀錄的時候剛好沒有。

**未勾選時整條流程不產生任何檔案。** 報告內容一律經由回應的 `data` 送回，
結果視窗從那裡取內容，Qt 從不開檔。

## 憑證

GitLab 與 JIRA 的端點與權杖放在設定檔的 `Service`，由功能注入為環境變數
（鍵名的全大寫形式）：

```
GITLAB_SERVER_URL    GITLAB_ACCESS_TOKEN    GITLAB_VERIFY_SSL
JIRA_SERVER_URL      JIRA_ACCESS_TOKEN
```

同一條注入路徑上還有幾個不是憑證的值（都在 `Function` 底下、不在 `Service`，因為它們
只屬於這個功能）：

```
PPS_DEVICE                                 <- PPS_Device
PPS_SCRIPTS_CODEREVIEW_FILE_STARTSWITH     <- PPS_Scripts_CodeReview_File_StartsWith
PPS_PROJECT_AI_ANALYSIS_SKIP_FILENAMES     <- PPS_Project_AI_Analysis_Skip_Filenames
PPS_PROJECT_AI_ANALYSIS_SKIP_EXTENSIONS    <- PPS_Project_AI_Analysis_Skip_Extensions
PPS_PROJECT_AI_ANALYSIS_SKIP_DIRS          <- PPS_Project_AI_Analysis_Skip_Dirs
```

`PPS_Scripts_CodeReview_File_StartsWith` 是第 4 步用來篩選 JIRA 附件的**檔名前綴**
（例如 `CodeReview_`）。它**沒有預設值** —— 沒設定時第 4 步直接失敗並同時點名環境變數
與設定鍵，整條流程結束。給它預設值的話，漏設時會靜默改用一個部署者沒選的前綴，而症狀
是「議題上明明掛著附件，報告裡卻沒有那一段」。

比對**區分大小寫**、只認 `.md`、只認**開頭**（不是包含）。副檔名寫死在腳本裡不可配置：
可配置的話有人會指到 `.docx` 或 `.zip`，於是二進位內容被貼進報告，而每一步都回報成功。

### 不必分析的檔案

一支 MR 常常夾著幾個對「程式碼有什麼變化」毫無資訊的檔案：產生出來的 `.json`、翻譯檔、
圖檔、第三方的整包來源。它們照樣吃掉 prompt 的位元組預算、照樣要付 token 的錢，而模型
對它們能說的話沒人想看。三個設定各管一層，**任一命中就排除**：

| 設定鍵 | 比對 | 例 |
|---|---|---|
| `PPS_Project_AI_Analysis_Skip_Filenames` | 檔名（basename）一模一樣 | `AUTHORS` 命中 `docs/AUTHORS`，不命中 `AUTHORS.md` |
| `PPS_Project_AI_Analysis_Skip_Extensions` | 副檔名一模一樣，**不含那個點** | `json` 命中 `cfg/a.json`；`Makefile` 沒有副檔名，永遠不命中 |
| `PPS_Project_AI_Analysis_Skip_Dirs` | 位於該目錄**或其子目錄**之下，路徑自根目錄起算 | `test/skip` 命中 `test/skip/x.cpp` 與 `test/skip/deep/y.cpp`，不命中 `test/skip_file.cpp` |

```json
"PPS_Project_AI_Analysis_Skip_Extensions": "json;ts;png;svg",
"PPS_Project_AI_Analysis_Skip_Dirs": "third_party;tools/generated"
```

- **一個設定填多個值用分號 `;` 分隔。** 不是逗號 —— 逗號在 Linux 與 macOS 上是合法的
  檔名字元，一個叫 `a,b.cpp` 的檔就永遠填不進來；分號在 Windows 與 POSIX 的路徑裡都不
  合法。每一段會去頭尾空白，空段忽略
- **比對區分大小寫，與 git 一致。** git 的路徑本來就分，不分的那一邊會在「同名但大小寫
  不同的兩個檔」上排除掉一個你沒打算排除的檔案。代價是 `PNG` 填錯大小寫會安靜地不生效
- **分成三個設定而不是一套樣式語法。** 一個寫成 `test` 的值，在三種意圖下分別是「叫
  test 的檔」、「`.test` 結尾」、「`test/` 底下」。合成一個就得發明一套樣式語法，而使用者
  得先學那套語法才能排除一個目錄
- **目錄要連子目錄一起排除**，而且要求那個 `/` 邊界。只排除直接放在該目錄裡的檔案，等於
  要求你把每一層子目錄都列進設定，新增一層就會安靜地漏掉；而少了 `/` 邊界就是字串前綴
  比對，`src/a` 會順便打到 `src/abc/` 整個目錄
- **副檔名只認最後一個點之後那一段。** `a.tar.gz` 的副檔名是 `gz`。設定值寫 `.json` 也
  收（前導的點會去掉），兩種寫法都有人用，擋掉一種只是多一個坑
- 三個都沒填時整層不啟用（`contract.skip_filter()` 回 `None`），`skipped` 是空清單而不是
  「排除了 0 個」—— 兩者在日誌上看起來不同

**排除發生在位元組上限之前。** 上限是逐檔累加到滿為止的一刀；篩在後面的話，一個你不打算
分析的大檔已經吃掉預算、把真正要看的檔案推進 `dropped` 了 —— 而那一筆缺口指向「上限要調」，
完全指錯方向。實測（上限 300 bytes、一個大 `.json` 排在中間）：

| | 完整送出 | 超過上限 | 依設定排除 |
|---|---|---|---|
| 不排除 | `src/a.cpp` | `cfg/big.json`、`third_party/lib.c`、**`src/b.cpp`** | — |
| 排除 `.json` 與 `third_party/` | `src/a.cpp`、`src/b.cpp` | 無 | `cfg/big.json`、`third_party/lib.c` |

**涵蓋範圍知道這件事，這是必要的。** 被排除的檔案收在第五類 `skipped`，而且**不算進
`missing`** —— 少了這一條，涵蓋層的重查（`Recheck_Count`）會為了一個你刻意排除的檔案一次
又一次重問，而它永遠補不回來。`skipped` 不算缺口（`has_coverage_gap()` 不數它），所以只有
排除、沒有其他缺口時報告不會多出一節；但只要有別的缺口，那一節就會順便列出被排除的那些，
否則「我的檔案為什麼不在報告裡」完全看不出原因。`files_changed` 仍是這支 MR 真正的檔案數，
不隨設定改變。

**全部被排除時這一步失敗**，訊息點名三個環境變數與實際被排除的檔案（錯誤碼
`MR_DIFF_ALL_SKIPPED`）。不沿用「GitLab 沒有提供差異內容」那一段：那段話叫人去找管理者調
伺服器端的 diff 大小限制，而這裡真正的成因是自己填的規則太寬，改那邊也沒用。

`gitlab_utils.get_mr_diff_detail()` 收的是一個通用的 `exclude`（可呼叫物件，收路徑回
bool），**不認得這三個設定** —— 判斷哪些檔案不必分析是這個功能的政策，而那支是共用的
GitLab 存取；把政策寫進去就等於讓每一個用它的功能都繼承別人的規則。

> **注意這是每個部署只會撞一次的成本。** 第 4 步跑在第 3 步之後，所以設定檔少這個鍵時，
> 使用者是**付完 AI 費用、等完那兩分鐘之後**才看到錯誤訊息，而那一次沒有報告。檢查刻意
> 只留在腳本那一道（一個地方一個真相），代價寫在 design.md。

**腳本只從環境變數讀這些值，不從 `config` 讀。** 這樣 CI/CD 設定同名的環境變數
就能執行同一批腳本，腳本端只有一條取值路徑。AI 的端點、金鑰與模型名則走 `params`。
兩者都不會出現在行程的命令列上。

`GITLAB_VERIFY_SSL` **未設定時視為不驗證**。這是刻意的取捨：目標環境是否使用
自簽憑證尚不確定，而驗證失敗會讓功能完全無法使用。代價是關閉驗證時存取權杖
會暴露給連線中間人，且被攔截時沒有任何徵兆。確認伺服器有正規憑證之後，把
`Service.Gitlab_Verify_SSL` 設為 `"true"` 即可，不需要重新建置。自簽但想驗證的話
把 `REQUESTS_CA_BUNDLE` 指向公司的 CA 憑證。

⚠️ **是 `REQUESTS_CA_BUNDLE`，不是 `SSL_CERT_FILE`。** 本專案的 REST 全走
`requests`，而它只認 `REQUESTS_CA_BUNDLE` 與 `CURL_CA_BUNDLE`；`SSL_CERT_FILE`
是 Python `ssl` 模組的變數，`requests` 不理它。設錯的症狀是「憑證明明指過去了還是
驗證失敗」—— 看起來像憑證有問題，實際上那個變數從頭到尾沒被讀。

**AI 服務的 TLS 驗證同樣預設關閉**，理由一樣（地端服務多半用自簽憑證）。它讀的是
環境變數 `AI_VERIFY_SSL`，設為 `true` 才驗證。不放設定檔是因為 Qt 只注入
`kServiceKey[]` 列出的 Service 鍵，加一個新鍵要動 C++ 並重新建置。

憑證驗證失敗**不重試** —— 一張不被信任的憑證不會在兩秒後變得被信任，重試三次只是
把註定的失敗等三倍。訊息會直接說是憑證驗證失敗。

## 已知行為

- 單次取回上限 100 筆，不翻頁。達到上限時 `Filter` 的狀態行會**持續**顯示「已達上限，
  名單可能不完整」—— 表格是單選的，取回上千筆不會讓「挑一筆」更容易，範圍太大時該做的是
  調緊查詢條件。
- **達到上限時，某些作者不會出現在 `Filter` 的候選清單裡。** 候選是從取回的那 100 筆推導的，
  他的 MR 全部落在被截掉的部分時就沒有他。上面那行提示就是為了這個情況而持續顯示。
- 流程被取消時，已經建立的除錯目錄不會被清掉（規格明文：流程不保證外部副作用的
  原子性）。目錄名含時間戳，不會互相覆蓋。
- 取消發生在 AI 那一步時，已送出的請求可能照樣計費，而畫面完全不變。
- device 的鉤子是使用者寫的，所以它可能壞掉。載入或執行失敗時訊息會指出是哪一個
  device 的哪一個鉤子（含語法錯誤的檔名與行號）；回傳的結構不對則在**產生它的那
  一步**就失敗，而不是兩步之後的渲染。
- **第 4 步取不到 code review 時不會讓流程失敗**，而是把原因寫成報告裡那一段的內容。
  只有「缺設定鍵」與「缺 JIRA 端點或權杖」這兩種部署缺漏才結束流程 —— 分界是「能不能
  在本機判定」，理由見 design.md 決策五。
- **附件檔名的大小寫打錯會安靜地沒有那一段。** 比對區分大小寫，而「沒有符合的附件」
  走的是「這筆本來就沒有」那條路（整段不出現、沒有訊息），所以它與「議題上真的沒掛
  review」在報告上長得一模一樣。唯一的診斷路徑是開啟 `Debug_Mode` 後看 `debug.log`
  裡那一行「看到哪些附件、篩掉哪些」。
- **人工上傳的附件可能與當前程式碼不同步。** 規則就是取最新一筆，不做時間差警告；
  報告印出上傳日期，讀者自行判斷。
