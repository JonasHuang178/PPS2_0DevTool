為什麼不用 Qt 也跑得起來

Qt 從來就不是執行者，它只是填表的人

🖱️
Qt 工具
幫你填好一份信封，
丟給腳本，收結果。
→
⚙️
你 / CI
自己寫那份信封，
丟給同一批腳本。

腳本對兩個呼叫端長得一模一樣：憑證只從環境變數讀、產物只由 out_path 決定、 log 全走 stderr。所以沒有「CI 專用的腳本路徑」要維護。

開跑之前

設好環境變數,建一個工作目錄

# 憑證與設定走環境變數 export GITLAB_SERVER_URL=https://gitlab.example.com export GITLAB_ACCESS_TOKEN=... export JIRA_SERVER_URL=https://jira.example.com export JIRA_ACCESS_TOKEN=... export PPS_SCRIPTS_CODEREVIEW_FILE_STARTSWITH=CodeReview_ # 第 4 步要,無預設值 export PPS_DEVICE=default # 省略即 default # 工作目錄:五步的產物都落在這裡 W=/tmp/pps-work && mkdir -p "$W"
AI 的四個設定不在環境變數裡
ai_api_url、ai_api_key、ai_model、 ai_mode_name 走第 3 步的 params,所以會落在請求檔裡。 跑完立刻刪掉那個檔案;在 CI 上還要在 after_script 再刪一次 —— 它連失敗的 job 也會跑,而 artifacts 收的是整個工作目錄。
不要設 PYTHONPATH
每支入口腳本自己把 scripts/ 插進 sys.path。 設了反而測不出那條規則有沒有被遵守。

五步各自做什麼

每一步:吃什麼 → 做什麼 → 吐什麼

五步全部都要跑,不要自己判斷該跳過哪一步。 「要不要真的做事」由腳本看參數自己決定 —— 判斷寫在 shell 裡就會有第二份規則,而兩份一定會漂移。

產物怎麼串

每一步的輸出是下一步的輸入

01_description.md ──┬────────────────────────────┐ │ │ 02_mr_info.json ──┼──┐ │ jira_key, mr_type │ │ │ ↓ │ ↓ 步驟 3 │ 步驟 5 │ │ ↑ 03_summary.json ←──┘ │ │ jira_state ──┐ │ │ ↓ ↓ │ 步驟 4 │ │ │ 04_code_review.json ←┘ （可能不存在） ─────────────┘ ↓ 05_report.md

步驟 1 與 2 可以互換順序,其餘不行。

跑完長什麼樣

五個可收合的區段,加一包 artifacts

▸ 步驟 1/5：取得 MR 描述 00:02 ▸ 步驟 2/5：JIRA key 與 MR 種類 00:03 ▸ 步驟 3/5：AI 分析 02:17 ← 唯一會久的 ▸ 步驟 4/5：程式碼審閱報告 00:04 ▸ 步驟 5/5：合併為 markdown 00:01 Uploading artifacts... pps-work/01_description.md pps-work/02_mr_info.json pps-work/03_summary.json pps-work/04_code_review.json pps-work/05_report.md ← 這份就是報告

GitLab 的可收合區段會在標題旁顯示那一步的耗時,所以一眼看得出慢在哪裡。 失敗時 artifacts 照樣上傳(when: always),才查得出是哪一步少了什麼。

範例刻意處理掉的坑

照抄 ci/pps-ai-analysis.gitlab-ci.yml 就避開了

AI 金鑰會落在第 3 步的請求檔裡
AI 四項走 params 不走環境變數。範例在步驟 3 之後立刻刪, 並在 after_script 再刪一次。
不要在 shell 裡判斷「第 4 步要不要跑」
永遠跑它,讓它自己依 jira_key 與 jira_state 決定。 在 CI 再判一次就有了第二份規則。
第 4 步沒落檔時,第 5 步的那個鍵要整個拿掉
不是放空字串。步驟 5 收的是路徑,路徑給了就必須存在。
-v 會讓 job log 變很大
它打開 DEBUG 等級。job log 有大小上限(預設 4 MB), 一支大 MR 有可能撞到 —— 而被截掉的是尾端,也就是結果信封所在的位置。

常見問題

在命令列或 CI 上最常被問的

要先裝什麼？
Python 3，加上一個第三方套件：requests（pip install -r requirements.txt）。沒有別的相依。
可以只跑其中幾步嗎？
可以 —— 每一步都是獨立行程。但要照相依關係把前面的產物餵進去，否則那一步沒有輸入可讀。
一定要用 GitLab CI 嗎？
不用。腳本不認得任何 CI，它只讀信封與環境變數。Jenkins、GitHub Actions 一樣跑得動 —— 只是可照抄的範例目前只有 GitLab 那一份。
失敗了怎麼查？
範例的 artifacts 設 when: always，失敗也留；加 -v 打開 DEBUG 等級；那一步的結果信封在 stdout 的最後，裡面有失敗原因。
可以同時跑好幾支 MR 嗎？
可以，各給各的工作目錄就行。腳本之間不共用任何狀態。
權杖會不會外洩？
GitLab 與 JIRA 的權杖走環境變數，不經過命令列，所以不會出現在行程清單上。
AI 的四項走 params，會落在第 3 步的請求檔裡 —— 那個檔案用完要刪。
產物一定要落檔嗎？
不用。out_path 不給就不寫任何檔案，結果只出現在 stdout 的回應信封裡。
設好環境變數 → 依序跑五支 → 拿 05_report.md。
完整的參數表在 cli.md,可照抄的 pipeline 在 ci/。
